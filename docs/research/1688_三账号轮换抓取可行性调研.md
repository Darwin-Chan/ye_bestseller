# 1688 三账号轮换抓取可行性调研

研究日期：2026-09-20。承接 [`1688账号密码自动登录调研.md`](1688账号密码自动登录调研.md)（2026-09-18）与 [`1688_IP代理与登录可行性调研.md`](1688_IP代理与登录可行性调研.md)（2026-09-20）；并与 [`技术路线与反爬评估.md`](技术路线与反爬评估.md)（2026-09-04）已定的「多账号分片：每账号一个 profile + 一个粘性 IP」设计对照。

**本次要判定的需求**：三个账号，每隔二十分钟切换一个账号登录 1688 继续抓取库存；每个账号固定一个 IP、浏览器版本、专用 profile、CDP 自动化特征和设备指纹。

**边界**：只涉及账号所有者授权的自有账号；未提交凭据、未测试真实账号登录、未做刻意触发风控的实验。取证限制：本机 WebFetch 对所有域名不可用（环境级限制，连对照域名也被拦），1688/阿里官方页面类证据全部来自搜索引擎索引摘要、**未逐字打开核对**（来源表逐条标注）；浏览器机制类证据做了两类核对：官方文档/规范/源码（经官方镜像可达），以及本机安装的 Playwright 1.62.0 打包源码（第一手，[L5]）。

## 结论

**总判定：需求可以「做出来」，但需求里隐含的「三个互相独立的身份」在同一台机器上做不到；「每隔二十分钟切换登录」中「登录」这一步是自我加码——profile 保留登录态时切换根本不需要重新登录，而每多一次登录就多一个风险信号。「20 分钟」这个节拍在本仓库没有任何观测支撑，应先测量（单账号究竟为什么停、被什么停），再决定要不要轮换、按什么节拍轮换。**

1. **工程构件全部可落地。** 每账号一个专用 profile（不同 `--user-data-dir` 的多实例受支持，[C2]）、每账号固定出口 IP、串行轮换，都不需要重写现有采集结构，只需要在配置与会话层加一层「账号绑定」。其中两个关键机制事实必须写进实现：(a) Playwright 的 `proxy` 参数在 `connect_over_cdp` 下**不生效**——本机安装的 1.62.0 里 Python 侧 `connect_over_cdp()` 签名根本没有 `proxy` 参数，打包源码中 `proxy` 只被翻译成浏览器启动参数 `--proxy-server`，接管路径不读取它（[L5][P1][P2]），所以每账号的固定 IP 必须通过浏览器启动参数设置；(b) 默认策略下 WebRTC 流量**不经代理**（RFC 8828 §5.1），页面仍可能通过 STUN 拿到真实公网 IP，把「每账号固定 IP」打穿——必须显式设置 `disable_non_proxied_udp` 一类策略（[W2][E3]）。

2. **「三账号看起来互相独立」做不到；能达到的目标是「每个账号自身前后一致」。** 三个 profile 在同一台机器上共享全部硬件级指纹（GPU/WebGL 渲染器、字体、屏幕、CPU/内存、时区等硬件级信号跨 profile 完全相同；Chromium 官方技术文档原话：这类信号可「被用于跨不同浏览器 profile 与隐私浏览会话关联用户活动」[B1]；同一机器不同浏览器之间这些信号的稳定性已达 96%–100% [B2]）；若三个账号实名在同一身份证下，平台侧本来就知道它们同属一人（1688 官方客服页：一个身份证最多 3 个实名账户，[A4]）；阿里系风控具备设备指纹能力是官方文档事实（阿里云设备风控服务、设备令牌、多开/模拟器标签、增强版返回可跨会话追踪的设备唯一 ID，[A6][A7]）。因此正确的工程目标是「每个账号始终走同一条路径、指纹保持稳定」，而不是「伪造三套互不相同的指纹」。

3. **「每隔二十分钟切换账号登录」应改成「每隔二十分钟切换账号会话」。** profile 会保留登录态，切换用「关掉当前浏览器、打开下一个账号的浏览器」即可，不需要登出、也不需要重新登录；三个账号各自把登录做一次即可（沿用现有 `login_chrome.py` 的人工登录 + 复用）。若每次切换都重新登录，三个账号合计约 72 次登录/天，而阿里官方（国际站）明确说过：登录环境可信任度「需要一定的资料积累」，频繁清理 Cookie/历史会反复触发验证码（[A5]，注意对象为国际站）——登录频率从每天 O(1) 变成几十次，是新增信号而不是缓解。

4. **「20 分钟」这个数字没有依据，属于未核实。** 1688/淘宝没有任何官方公开的风控触发条件或登录态有效期（多轮检索未获得，见「未核实清单」[A5] 相邻项）；本仓库的 `guard.py` 里已有按滚动窗口统计的 deny 账本和事件日志（`event_log`），但从未把 deny 与「本会话已连续运行多久/多少请求/哪个账号/哪个 IP」做过归因。先做离线归因和两个小规模对照实验（见「决定性实验」），「轮换是否有用、节拍多少」应当由测量结果决定。

5. **CDP 自动化特征无法按账号区分，只能整机统一。** 现有做法（普通进程 + 具体调试端口 + CDP 接管、有头、不加 `--enable-automation`）下 `navigator.webdriver` 保持 `false`：Chromium 源码注释写明「指定具体端口更可能是附加调试器，应保持浏览器行为与不受自动化控制时一致」（[C1][W1]）。但 Playwright 接管会调用 `Runtime.enable` 等 CDP 域，这是已知的可检测面（第三方项目 rebrowser 称 Cloudflare、DataDome 等在真实拦截中使用该手法；可信度中，未取到厂商一手文档，[R1]）。这个特征由驱动框架决定、属于整机，不按账号区分——需求里「每个账号固定一套 CDP 特征」若指「互不相同」则无机制实现；若指「每个账号始终走同一条接管路径」则值得做，且现状已基本如此。低成本收尾项：调试端口不要用默认 9222，三个实例各给一个非默认端口（零成本；「反爬会扫 9222」无一手证据，见未核实清单）。

6. **「每账号固定一个浏览器版本」机制存在，但对身份隔离没有贡献，维护成本真实。** Edge 有官方更新策略可钉住/回滚版本（TargetVersionPrefix、RollbackToTargetVersion 等，[E2]），官方也为自动化场景提供固定版本的 Chrome for Testing（[F1]）；但 TLS 指纹（JA3/JA4）由「浏览器构建版本 + 平台」决定、不按 profile 区分，且 Chromium 自 2023 年起逐连接随机化 TLS 扩展顺序，JA3 每次连接都可能在变（[S1][CL1][C7]）——换版本只影响 UA/Client Hints/TLS 面，不影响硬件指纹。单机跑三个不同版本意味着三份浏览器二进制的安装与更新维护，且一个长期冻结的旧版本本身会随时间变成异常（真实用户会更新）。建议三个 profile 用同一版本、随正常更新节奏。

7. **多账号共用一台机器的关联后果要由设计承担，而不是靠轮换掩盖。** 无论串行轮换还是并发，三个账号在平台侧共享同一设备指纹、同一行为模式（同一批店铺、相似访问顺序与节奏、相近时间窗），是一个相互关联的簇。一个账号触发滑块/保护/deny 时，同设备的另外两个账号会被一起打分。工程上应把「账号级失败」当全局事件处理：单账号触发验证 → 只停该账号、记录原因、报告给人，不用「换账号」把信号绕过去（沿用 `guard.py` 现有「停止并等人」的语义，而不是自动切换）。

8. **合规定性不变。** 1688 网站法律声明禁止未经许可用机器人、爬虫、自动化程序或模拟用户操作获取站内内容（[A1]）；《阿里巴巴服务条款》要求账户仅限本人使用、密码不得共用（[A2]）；《不当获取使用信息的处理规则》把租借/共享账号、爬虫获取信息列为违规，处罚含违约金、搜索降权、账户关闭（[A3]）。多账号轮换不改变这个定性；「自有账号、数据自用、低频、不绕过验证」仍是本项目既定边界（[L4]）。另外，开放平台的合法路径（授权 API）协议明文禁止「请求用户账号密码凭据」和「为用户自动登录 1688 网站提供代理身份验证凭据」（[A9]）——意味着「账号密码自动登录抓取」无法通过开放平台合法化，两条路是分开的。

## 网络层：每账号固定出口怎么成立

- Playwright 的 `proxy` 选项只在它自己启动浏览器时生效（翻译为 `--proxy-server` / `--proxy-bypass-list` 启动参数）；`connect_over_cdp` 接管已启动浏览器时不应用任何代理配置。本机核对（Playwright 1.62.0）：Python 侧 `connect_over_cdp()` 签名只有 `endpointURL/timeout/slowMo/headers/isLocal/noDefaults/artifactsDir`，无 `proxy`；打包源码中接管路径 `browserOptions` 不读取 `options.proxy`，而 `launch` 路径将 proxy 推入 `--proxy-server=`（[L5]）。**结论：每账号固定 IP 走浏览器启动参数，不走 Playwright 配置。**
- `--proxy-server`（及 `--proxy-bypass-list`）是 Microsoft Edge 与 Chromium 官方文档化的启动开关（[E1][C8]）。
- WebRTC 是默认敞开的泄漏面：RFC 8828 的原则是「默认 WebRTC 流量不应经过代理」，只有强制模式（Chromium 的 `disable_non_proxied_udp`）才让媒体流量走代理（代理不支持 UDP 时退化为 TCP）（[W2][E3]）。Chromium 默认把 host 候选中的局域网 IP 替换为 mDNS `.local` 名（[C9]），但公网侧 STUN 反射候选仍可能暴露真实出口。对每个账号实例同时设置代理和 `disable_non_proxied_udp`，是「固定 IP」成立的前提；否则页面里的第三方脚本（含风控脚本）仍可能读到代理之外的地址。RFC 8828 还写明：私网地址足以让「隔离的浏览上下文」（如普通与隐私模式）互相判定处于同一设备并关联会话——「同设备可关联」在网络标准文本里是被明确承认的现象（[W2][B7]）。
- 代理凭据仍按前篇调研的边界：放仓库外凭据存储，不进 TOML/日志/命令行（[L2] 现有配置对凭据零暴露）。

## 多实例与专用 profile

不同 `--user-data-dir` 的多实例受支持，每个目录是一个独立的单实例域；两个运行中的实例**不能**共享同一个 user data dir——第二个进程会把命令行转发给已有实例并退出，或报 `PROFILE_IN_USE`（Chromium 文档原话「two running Chrome instances cannot share the same user data directory」；Playwright 也把这两类输出识别为「profile 已被占用」[C2][P3]）。仓库现在每个会话用一个专用目录（[L2]），三个账号就是三个目录、三个调试端口、三个代理，没有结构障碍。注意 Chrome 136 起「默认数据目录 + 远程调试开关」不再生效，必须配合非默认 `--user-data-dir`（[F1][C4]）——仓库用的是自定义目录，不受影响；Edge 是否同步了该限制**未核实**（相关检查在 Chromium 源码里默认只对 Google Chrome 品牌开启，[C4]）。

## 调试端口与自动化特征现状

- **`navigator.webdriver` 现状为 false，且这是有意的设计。** WebDriver 规范层面它表示「浏览器处于远程控制之下」（[W1]）；Chromium 的实现里，`--enable-automation`、无头、`--remote-debugging-pipe`、`--remote-debugging-port=0`（ChromeDriver 方式）会置 true，而**指定了具体端口号时故意不置**——源码注释原文大意：「调用方给了具体端口，更可能是要附加调试器，应保持浏览器行为与不受自动化控制时一致」[C1]。仓库的启动方式（普通进程 + 具体端口 + CDP 接管 + 有头）正好落在 false 这一侧；对照之下 Playwright 自己 `launch` 走 pipe，测试断言 webdriver 为 true（[L5][P3]）。
- **接管不是零痕迹。** Playwright 连接后会对它新建/导航的页面调用 `Runtime.enable`（本机 1.62.0 打包源码中多处；亦是公认的 CDP 检测面，[L5][R1]）、在隔离世界运行工具脚本；`__playwright__binding__` 仅在用到 expose 类能力时注入，当前版本没有 `__pwInitScripts` 这类标记（[L5]）。这些痕迹由驱动框架决定，三个账号经同一路径接管就共同拥有、无法按账号区分——「每个账号固定一套 CDP 特征」在这层没有可操作对象。
- **网页对调试端口的探测面：** Chrome 111 起对来自非白名单 origin 的 WebSocket 连接直接 403（`--remote-allow-origins`，[C3]）；对 localhost 的请求正被 Local Network Access 权限门控收编（Chrome 142 起有权限提示，「公网→回环」属其管辖；WebSocket 等通道当时尚未纳入，[F2]）。「反爬脚本会扫 9222 端口」这一说法**未取到一手证据**（仅第三方反检测产品把端口探测列为防御项），但把默认端口换掉是零成本动作。

## 浏览器版本与 TLS 指纹

- 版本固定的机制：Edge 更新策略 `TargetVersionPrefix`（限制更新到指定版本）/`RollbackToTargetVersion`（回滚）等（[E2]）；注意 `UpdateDefault` 策略注明仅适用于加域 Windows，个人机上要靠注册表策略可用性未逐一验证；自动化场景的官方出口是 Chrome for Testing（固定版本、专为自动化）（[F1]）。降级后的旧版跑新 profile：Chromium 官方有「版本降级处理」——能读的文件继续用，不能读的保留并提示体验可能降级（[C5]），所以技术上不致命。
- 但对「身份」没有贡献：TLS 指纹按「浏览器构建版本 + 平台」区分，不按 profile；且 Chromium 自 2023 年起逐连接随机化 TLS 扩展顺序（BoringSSL `permute_extensions`，Chromium 无条件开启），JA3 对 Chrome/Edge 已「每次连接都可能不同」（[S1][CL1][C7][BORINGSSL]）；TLS 指纹测量研究还显示 Chrome 同一设备就能产生至少 4 种 ClientHello 指纹，依赖库更新也会改变它（[B6]）。UA 侧同样不划算：Chromium 的 UA 缩减把版本钉成 `Chrome/<大版本>.0.0.0`（补丁号恒为 0），Windows 的平台版本等需服务器主动请求的高熵 Client Hints 才有一点区分度、且值可能被浏览器打乱（[B6]）。用同一台机器上三个不同版本去「显得像三个用户」，收益未证实，维护成本（三份安装、三份更新）确定；硬件级信号本身不随浏览器版本变化（推论，依据跨浏览器稳定性 [B2] 与 Windows 平台版本来自 OS [B6]，见未核实清单）。

## 设备指纹与跨账号关联

- **同一台机器上，跨 profile 不变的信号**（一手依据为 MDN/Chromium 官方文档，[B1]）包括：WebGL 的 GPU 厂商/渲染器字符串（`WEBGL_debug_renderer_info`，直接来自显卡驱动）、逻辑 CPU 核数、内存档位（取整后上报）、屏幕参数与 devicePixelRatio、系统时区（默认取运行时系统时区）、系统语言、系统字体集合、媒体设备（未授权时只见默认设备，授权后设备名暴露硬件型号；deviceId 按 origin 加盐、随清 Cookie 重置）、Client Hints 中 Windows 的平台版本（来自 OS 而非浏览器）。这些值由硬件与系统决定，换 profile、换 IP、换浏览器版本都不改变——这正是「每账号一套独立指纹」在单机上无从谈起的根本原因。
- **跨 profile 关联有直接实证。** NDSS 2017 跨浏览器实测（Table IV）：同一台机器的不同**浏览器**之间，时区与 CPU 核数稳定性 100%，JS 字体 96.52%、AudioContext 97.48%、屏幕比 97.57%——跨浏览器尚如此一致，同浏览器的不同 profile 只会更一致（Canvas/WebGL 渲染产物跨浏览器不同（8.17%/15.39%），但同一浏览器跨 profile 相同）（[B2]）。Chromium 官方技术文档明确写道：这类机器级信号「可被用于跨不同浏览器 profile 与隐私浏览会话关联用户活动」（[B1]）；RFC 8828 也从标准层面承认：私网地址足以让「隔离的浏览上下文」互相判定同设备并关联会话（[W2][B7]）。
- **关联强度**（论文实测）：Panopticlick（EFF）组合指纹至少 18.1 bits（约 1/286,777），94.2% 的 Flash/Java 浏览器唯一；AmIUnique（INRIA）89.4% 唯一；跨浏览器指纹方案在同一数据集识别 99.24% 用户、唯一性 83.24%、跨浏览器稳定性 91.44%；真实大规模流量中唯一性降到 33.6%，但非唯一指纹「脆弱」——个别属性一变就变唯一；FP-Stalker 证明指纹随时间频繁变化仍可跨时间链接（平均 54.48 天，26% 超过 100 天）（[B2]）。
- **「伪造指纹」是风险面而不是解决方案。** FP-Scanner 证明反指纹措施引入的「不一致」可被检测、甚至被还原出原始值；FP-Inconsistent（2024，用半百万请求实测 20 家 bot 服务）发现一致性规则能把对 DataDome 的规避率压低 48.11%；Shape Shifter（DIMVA 2020）实测 4 款反检测浏览器，「与真指纹最轻微的差异也会暴露」；Chromium 官方文档直言「大改设置的用户反而更容易被唯一识别」（[B3]）。本项目用真实浏览器、不做任何伪装，正是避开这一整类信号面。
- **行业公开承认设备指纹用于多账号关联。** Cloudflare Turnstile 的 Ephemeral ID 官方文档自我描述为「不依赖 cookie 地把访问者行为关联到特定客户端设备」，官方教程的示例查询就是「找出一小时内创建多个账号的设备」；Arkose Labs 的 Device ID 官方文档写明用途包括「关联跨多个会话或账号的活动」；Sift 官方博客把「同一硬件配置/浏览器指纹/设备 ID 短时间内出现在多个注册中」直接列为自动化活动的强指标（[B4]）。学术侧，Sybil 检测（SybilGuard）与真实社交网络假号测量（Renren）是经典工作；FP-Redemption 记录了 12 家安全公司在注册/登录/支付页采集指纹的正当用途（[B5]）——登录环节本来就被期望看到稳定一致的设备指纹：这是「保持稳定」值得做、而「按账号伪造」不可行的又一重理由。
- **平台侧确认：** 阿里云官方文档有「设备风控服务」产品（设备令牌、模拟器/多开等风险标签；增强版返回可跨会话追踪的设备唯一 ID）（[A6][A7]）——阿里系风控具备设备指纹与设备关联能力是官方文档事实（具体 1688 站内是否部署同款产品**未核实**）。此外若三账号实名于同一身份证，平台知道同属一人（[A4]）——**身份层的关联无需任何指纹技术即可成立**，这是本需求最根本的边界。

## 平台规则、登录环境与「持续抓取」

- 条款侧（均为官方页面经检索摘要，未逐字核对）：法律声明的「信息限制」条（[A1]）、服务条款 4.2.3（账户仅限本人使用）/4.3（转让限制）/4.7（密码保密）（[A2]）、处理规则的违规形态与处罚（[A3]）。
- 登录环境信任：阿里官方（国际站）问答称验证码机制「非常严格」，未在 30 分钟内输入验证码、频繁清理浏览器历史与 Cookie 会导致后续登录反复要求验证，且「系统需要一定的资料积累来检测登录环境是否可信任」（[A5]）。这条支持「保持环境稳定」的方向，也同样支持「不要频繁登出登入」——登录事件本身就是需要重新积累信任的时刻。
- 1688 客服中心另确认「已登录却反复被要求再次登录」可能与浏览器禁用第三方 Cookie 有关（[A8]）——登录态载体对 Cookie 配置敏感，轮换实现时应保持三个 profile 的 Cookie 设置一致、且不要用会清 Cookie 的启动参数。
- 登录态有效期、风控阈值：**无官方公开细则**（见未核实清单）。

## 决定性实验（最小验证计划）

全部低风险：用现有日志做离线归因 + 小规模冒烟；不刻意触发风控、不反复登出登入、不动生产节奏。

| # | 实验 | 方法 | 通过条件/产出 |
|---|---|---|---|
| E1 | deny 归因（离线，先行） | 读 history：`event_log`/deny 记录与轮次、店铺、时间戳关联，统计「本会话已运行时长/已访问页数」与 deny 的关系 | 得到 deny 与运行时长/请求量的经验阈值（或证明不相关）；这是「20 分钟」有无依据的第一份证据 |
| E2 | 会话存续测量 | 账号 A 专用 profile 登录一次（人工），关闭浏览器，分别隔 20 分钟 / 2 小时 / 隔夜重开，检查是否仍需登录 | 若隔夜免登录 → 轮换永远不必伴随登录，需求应改写为「切换会话」 |
| E3 | 触发因子对照（小规模） | 固定账号、换出口 IP 前后对比 deny/验证出现率；固定 IP、换账号重复同样页数 | 判断限流按 IP 还是按账号计（各 1-2 家店、数十页量级，出现验证即停） |
| E4 | 多实例冒烟 | 三实例同开（三个 profile、三个非默认端口、三个代理 + `disable_non_proxied_udp`），跑少量页面 | 稳定运行、资源占用可接受；无直连回退、无 WebRTC 泄漏（用受控回显页验证出口） |
| E5 | 轮换一周期冒烟（仅当 E1-E4 支持） | A→B→C 各约 20 分钟串行接管，记录每段的 deny/滑块/耗时/中断点 | 与单账号同时长基线比较，验证轮换是否真的降低中断率 |

## 对本项目的接入建议（设计建议，尚未实现）

1. **配置形态**：`[browser]` 的单值键（`user_data_path`/`attach_port`）演进为账号绑定列表，例如 `[[accounts]]`：`name`、`user_data_path`、`attach_port`（各账号一个非默认端口）、`proxy`（主机端口；凭据引仓库外存储）。`Config` 仍是单会话形状，新增一层「账号绑定」负责选择当前账号，不把账号概念渗进采集路径（[L2][L3] 的现有边界——会话模块不认识账号）。
2. **每账号浏览器启动**：`--user-data-dir=<该账号>`、`--remote-debugging-port=<该账号端口>`、`--proxy-server=...`（固定出口）、以及 WebRTC 防泄漏策略；保持现有的「普通进程启动 + CDP 接管 + 有头」路径不变（这是 `webdriver=false` 现状的结构性来源，[L1][C1]）。
3. **轮换实现**：串行 open/close 三个会话即可，直接复用 `browser_pw.open_session()/close_session()`（ADR-0025 的单活动会话模型不用改）；切换 = 关闭当前浏览器（**不登出**）→ 打开下一账号。若未来要并发三实例，需要扩展 ADR-0025 的单会话账本，那是更大的改动，先不做。
4. **账号级失败记账**：`DenyTracker` 增加账号维度（现在是按店铺 + 整轮，[L7]）；单账号命中滑块/保护 → 只停该账号、记录、报告给人，不自动切换账号「绕过去」（与现有「停止并等人」语义一致）。
5. **日志与凭据**：沿用既有安全边界——不记 Cookie/密码/完整 URL；代理凭据走 Windows 凭据存储；三个 profile、三个会话的状态互不串联导出。轮换日志里记录「切换的原因」（到时长 / 触发验证 / 人工要求），让轮换对人是透明的。
6. **停止条件**：单账号日配额 + 连续 N 次需人工即整体停（沿用 `fail_rate_limit` / `human_pause_minutes` 现语义）；「换账号继续」不能被实现成静默重试。
7. **前置门槛**：E1/E2 的测量结果出来之前，不建议先开发轮换——如果单账号当前根本不触发 deny，三账号轮换是纯增复杂度；如果触发，先确认是 IP 维度还是账号维度（E3），再决定「轮换」还是「降速」。
