## 结论

当前最先要做的是补齐“SKU 程序基线提取/回放”，然后再开始人工标注和参数实验。现在不应直接调整 `candidates`、`min_score`，也不应新增 LLM 调用来试参数。

原因是当前运行库没有可供回放的 SKU 判断结果：

- `F:\AI\bestseller_runtime\data\matching.sqlite` 中，`sku_judgments` 为 0 行，`sku_recommendations` 为 0 行，`sku_imports` 为 0 行。
- 同库中的 `judgments` 有 4103 行，`recommendations` 有 16 条快照，但这些是商品级记录。最新可回放快照包含 878 个商品、590 个商品组；成员身份是 `shop_key + offer_id`，没有 `sku_id`。
- 现有 `tools/replay_groups.py` 的输入入口固定读取最后一条 `recommendations.payload`，再从 `evidence` 读取商品证据；它调用的是商品级 `matching.scored_pairs`、`_judged_edges` 和 `assemble_groups`。因此它能验证商品级回放，但不能直接回放 `.scratch/sku-grouping-research-update/label-pack/` 中的 SKU 候选集。
- 现有样本包的 `program_context.csv` 和成员表中的程序字段仍是“待当前流程回放后填充”，不能用候选来源或商品级分组代填。

## 对原研究计划的更新

原计划中“先回放当前流程，再建立 Q33=C 人工参照组”的方向仍然正确，但需要把第一步单独拆出来：

### 先做：SKU 基线提取/回放工具

工具应保持只读、离线、零新增模型调用，至少完成以下工作：

1. 以样本包中的 `member_key`、`shop_key`、`offer_id`、`sku_id` 为输入边界。
2. 从运行库读取 SKU 名称、商家编码、图片和版本信息，或明确报告缺失证据。
3. 读取 SKU 缓存中的判断边和多候选推荐；当前没有记录时，明确输出“无 SKU 缓存基线”，不能回退成商品级结果。
4. 复用生产 SKU 召回、编码合法性、边读取和组装实现，避免复制一套研究逻辑。
5. 为每个样本集输出：当前程序组、判断状态、候选来源、候选边数、已判断边数、缓存命中数、推荐结果、调用次数、token、费用和耗时字段。没有缓存的字段填空并标明原因。
6. 对 1–10、11–25、26–50 三层分别汇总；特别记录 26–50 层的跨商品来源，不把它当作真实同款组。

如果生产 SKU 代码尚未在目标运行环境实际执行，工具应先输出“无法取得 SKU 程序基线”，然后转入一个小规模、明确授权的基线运行工单。该工单应先固定当前模型、提示词、证据格式和配置，只跑 34 个候选集，不做参数搜索。

### 然后做：人工参照组

只有程序上下文回填后，业务人员才开始 Q33=C 标注：

### 最后做：参数和流程比较

拿到“程序基线 + 人工参照组”后，才执行 `candidates`、`min_score`、SKU 名称召回、编码规则和三种人工流程实验。每个方案统一记录纯度、同款召回率、完整组恢复率、误桥接率、LLM 费用、人工分钟数和总处理时间。本轮 80%/80%/10% 只是测量目标，不作为上线门槛。

## 这次核验没有回答的问题

- 当前 34 个样本集的 SKU 判断边和推荐结果是什么；缓存中没有这些结果。
- 50 SKU 组在当前配置下实际会调用多少次模型、消耗多少 token、产生多少费用。
- SKU 名称进入召回、`candidates` 或 `min_score` 调整后，纯度、召回率和误桥接率如何变化。
- 50 SKU 大组中单条误判正边是否会扩散成误桥接大组。

这些问题都依赖 SKU 程序基线和人工参照组，不能由当前商品级缓存推断。

## grill-with-docs 确认结果

本轮对仍未确认的设计事项完成了 grill，并已确认按以下边界推进：

- `sets.csv` 与 `members.csv` 是唯一候选输入边界；候选来源只作说明，样本包字段作为展示主数据，运行库只用于 SKU 缓存和证据验证。
- 缺少 SKU 缓存、当前候选集未命中、证据版本不可用分别报告为 `no_sku_cache`、`candidate_set_cache_miss`、`evidence_unavailable`；程序字段留空，不回退商品级缓存。
- `program_context.csv` 保持成员级，候选集级和分层汇总写入独立 JSON 报告。
- 第一阶段只读、离线、零新增 LLM 调用；固定配置运行如有需要，另立阶段并取得明确授权。
- 回放复用生产 SKU seam；部分缓存只逐条回放可验证结果，不能在缺少完整语境时构造完整程序组装。
- “缓存程序基线”与“固定配置运行基线”作为正式术语分开使用。

这些决定已记录在 [ADR-0060](../adr/0060-sku-program-baseline-replay.md)、根领域词汇和本研究的完整 spec 中。

## 只读实现与真实样本回放结果（2026-10-24）

已实现 [tools/replay_sku_baseline.py](../../tools/replay_sku_baseline.py) 及离线测试。工具以 `sets.csv` 和 `members.csv` 为唯一候选边界，使用 `shop_key + offer_id + sku_id` 作为 SKU 身份，复用生产 `sku_lifecycle.cache_signature()` 构造带 SKU 规则版本的判断缓存署名，并以只读 URI 打开运行库。它不写缓存、不创建 SKU 表行、不调用 LLM，也不把商品级缓存用于 SKU 字段。

真实样本回放使用 `F:\AI\bestseller_runtime\data\matching.sqlite`，输出到 `.scratch/sku-grouping-research-update/label-pack/program_context.csv` 和 `.scratch/tool-output/sku-baseline-replay-20261024.json`。结果为 34 个候选集、536 个成员，状态为 `no_sku_cache=22`、`evidence_unavailable=12`；运行库的 `sku_judgments=0`、`sku_recommendations=0`、`sku_imports=0`，商品级 `judgments=4103`、`recommendations=16` 只作为未回退审计事实。三层分别为 12/46、12/184、10/306 个候选集/成员，26–50 层有 3 个跨 offer 构造候选集。回放模型调用、token、费用均为 0，运行库 SHA-256 回放前后相同。

实现还明确了部分证据缺失边界：候选集只要有成员无法验证当前证据，就报告 `evidence_unavailable`，同时记录缺证据成员身份；其它成员已有的有效判断边仍可逐条展示，但不组装完整程序组。由于生产缓存表没有可反查成员身份和证据版本的索引，当前 key 未命中不能被进一步解释为旧证据版本。


## 实现收口与当前限制（2026-10-24）

针对 provenance 审查，本轮回放器已增加生产证据版本门禁：只要 SKU 缓存非空，样本成员必须显式带有生产 evidence_version 才允许验证判断缓存键；不能用 members.csv 的展示字段临时重建生产 snapshot。缺少该字段的成员会计入 unverified_evidence_count 和 unverified_evidence_member_keys，候选集报告为 evidence_unavailable。当前样本包没有可供真实 SKU 缓存命中的生产 SKU 结果，因此本轮真实状态仍是 no_sku_cache=22、evidence_unavailable=12。

缓存摘要现在分别记录 sku_judgment_rows、sku_recommendation_rows、当前配置署名命中行，并记录 evidence、visual_evidence 和 judgment_imports 的存在性、列名和行数。候选边统计明确标记为样本成员两两组合；每个候选集也记录零模型调用、token、费用和耗时字段。只有推荐缓存而没有判断缓存时，状态使用 no_sku_judgment_cache，避免把推荐缓存误称为可回放判断边。

针对性离线测试共 8 项通过。生产签名隔离测试已尝试运行，但当前测试环境无法打开并清理既有临时数据库目录，失败原因属于隔离环境限制，不是 SKU 回放断言失败。
