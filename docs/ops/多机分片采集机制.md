# 多机分片采集：机制

采集分散到多台机器（各用自己的 1688 账号与浏览器 profile），数据仍是一份：任何一台都能看到
全部机器合起来的库存。本文件是这套机制的**全文**（等价于原先只存在开发机 `.scratch/` 里的
设计期 spec，且按当前实现校对过）；怎么装、怎么验的步骤在
[三机上机清单](三机上机清单.md)，术语在 [CONTEXT.md](../../CONTEXT.md)，
正式决定在 [ADR-0031](../adr/0031-cross-machine-merge-decided-by-package-claim.md) /
[ADR-0034](../adr/0034-machine-identity-and-role-change.md) /
[ADR-0035](../adr/0035-prepare-is-the-open-gate.md) /
[ADR-0037](../adr/0037-paced-throttling-and-deny-ladder.md)。

## 1. 角色与前提

| | 采集机 | 纯汇总机 |
| --- | --- | --- |
| `machine.role` | `collector` | `merge_only` |
| 干什么 | 采集 + 导出 + 汇总 | 只汇总与展示（采集入口被明确拒绝） |
| 1688 账号 / 浏览器 profile | 每台一套，专用 | 不需要 |
| 交换区凭据 | git 读写（只写自己的 raw 库；判断库各写各的）、COS 读写限 `img/*` | git 供判断库发布（采集通道的「不写」靠角色闸门，不靠凭据）、COS 只读 |
| 进机器名册 `machines.json` | 是 | 否（可在采集机之外任意追加） |

- 机器编号 `machine_id` 一经定下**终身不变**（包、周计划、合并账都按它认机器）；角色是档位、可随时间变，
  换角色时编号与配套账号/profile 留在原机器上。
- **判断库各写各的，与角色档位无关**（[ADR-0039](../adr/0039-cross-machine-judgment-set.md) 决策 3）：
  每台生产机一本 `judged-<机器>`，转成纯汇总机之后照样发布判断集。Gitee 上「按库收窄」做不到
  （部署公钥只读、账号公钥对名下所有库可写），所以「只写自己那本」是**纪律**——由此
  「纯汇总机只持只读凭据」修订为**只约束采集通道**：COS 用只读 AK（真凭据），`raw-*` 的
  「不写」由**角色闸门**承接（导出这半自动跳过）。
- 机器之间**零直连**：只主动出网，不要求任何一台被外部连入。
- 既有单机语义（轮次、同日去重、详情预算、失败率、人工介入）原样保留，**逐台各自成立**；
  「至多一个界面实例、至多一个采集进程」按每台机器计。
- 周界按 **ISO 周**（周一为周首），日期一律用北京时间。

## 2. 交换区

### 库布局（Gitee 私有库，一机一库 + 计划库 + 判断库）

| 库 | 谁写 | 放什么 |
| --- | --- | --- |
| `raw-<机器>` | 只有该机器自己 | `data/<年>/<周>-<机器>.db.gz` 与同名 `.manifest.json.gz`（图片清单） |
| `plan` | 各机写自己那份 + 计划发布者 | `plan/<年>-W<周>.json`（机器读，为准）+ 同名 `.md`（人核对）；`published/<机器>.md`（各机各写各的）；根目录 `shops.csv`（共享店铺清单）与 `machines.json`（名册） |
| `judged-<机器>` | 只有该机器自己（各写各的，纪律；见 §1 凭据口径） | `data/judgments.db.gz`（本机判断集的发布包，覆盖同名路径、旧版留在 git 历史） |

- 每台机器 clone 全部库；**一机一目录**天然免文本冲突。
- 写规则：push 前先 `pull --rebase`；被 non-fast-forward 拒绝就重试，至多 5 次（认证被拒、
  网络不可达不重试，原样报错）。
- 容量（测算值，见 [三机汇总通道调研](../research/三机汇总通道调研.md)）：每个 raw 库每年约
  150 MB；Gitee 免费额度是单库 500 MB / 单文件 50 MB / 账号共 5 GB——接近 400–500 MB 时换新库、
  旧库转只读（结构化包与图片永久保留）。
- 不设中心索引文件：「谁发布了什么」靠包自描述 + `published/<机器>.md`。

### 包（一次导出的产物）

- **包 = 一个 SQLite 文件**，提交前压成 `.db.gz`。里面是交换集七表（见 §6）+ 一张键值元数据表
  `exchange_meta`：`machine_id`、`week`、`generated_at`、`format_version`（导出程序口径版本，
  现为 `v2`）、`crawl_in_progress`（导出时本机采集是否在跑），以及每表一行计数 `rows_<表名>`
  （含 `rows_sku_image_versions`）。
- **格式版本与兼容方向**（[ADR-0045](../adr/0045-sku-images-follow-main-image.md)）：`v2` = 加
  SKU 图流水（`sku_image_versions`）。汇总侧对这张新表**软容忍**——`v1` 旧包没有它，照收，
  只是这批包没有 SKU 图（这半为无）；原来那六张表维持硬要求，缺一张仍是「不是交换集里的包」，
  当场报错。反向也成立：旧程序读 `v2` 新包无需改动（多出的表与元数据键被忽略）。
- **图片清单** `<周>-<机器>.manifest.json.gz`（几 KB）与包**同一次提交**，列出该包引用的图片 key 集；
  汇总机按它比对本地已有 key、只拉缺失的。
- 图片字节走对象存储，**不进包、不进 git**；包内 `product_image_assets` 行只带元数据。
- 导出是**一致性快照**，不锁正在跑的采集——与采集并行是允许的，「半截的一天」由周报说明。

### 图片（对象存储）

- 私有桶；key 内容寻址：`img/<sha256 前 2 位>/<sha256>.<扩展名>`；以传字节为主，只传新增。
- 凭据一机一把、限桶内 `img/*` 前缀（纯汇总机只读 Get/Head）；密钥在仓库外，配置只记档位。
  桶与密钥的建法见 [腾讯云 COS 上机手册](腾讯云COS上机手册.md)。

### 判断集通道（`judged-<机器>`）

- **判断集**（模型判断、视觉描述、判断证据索引、人工决定账本；词条见
  [CONTEXT.md](../../CONTEXT.md)）走**独立一条通道**：每台生产机一本 `judged-<机器>` 私有库，
  clone 在交换区根下、与 `raw-<机器>`、`plan` 并列；发布与收取挂在交换台里、手工触发：
  默认随整趟执行、也能单独跑（`--only publish|collect`），动作词与交换集的「导出／汇总」
  分开用。
- 发布形态 = 一个 `.db.gz`（落在 `data/judgments.db.gz`，覆盖同名路径、旧版留在 git 历史）；
  **身份 = 内容 SHA-256**（与周包同规）：同内容重发是空操作，重复收取幂等。包里不带图片字节。
- 两个库（判断缓存与人工决定账本）的位置从分析配置（`config/analysis.toml` 的
  `matching.cache` 与 `analysis.store`）读；没配分析配置时判断集这半跳过并写明原因，
  采集包那半照常。
- **收取名单与采集名册解耦**：名单 = 交换区里**实际存在的** `judged-*` 库（建好、clone 下来
  就进名单）；判断的生产者集合 ≠ 采集机集合，转角色撤出名册不影响判断集照收照发。谁还没建库、
  还没发布过、目录不是克隆，收取都只给可读说明，不挡别家。
- 消费语义与验收口径（署名并存、只消费同署名；决定不冲突即生效、冲突一律回到人面前；来源列）
  在 [ADR-0039](../adr/0039-cross-machine-judgment-set.md) 与 CONTEXT.md 的
  「判断集」「发布（判断集）」「收取（判断集）」「判断库」词条。

## 3. 周计划

### 输入（唯一权威：plan 库，只取已发布的事实）

- 根目录 `shops.csv`：共享店铺清单，**UTF-8 带 BOM**（`load_shops` 先试 `utf-8-sig`，编码错了
  只会静默乱码；带 BOM 的 Excel 双击也不乱码）。
- 根目录 `machines.json`：机器名册，形如 `["m1","m2","m3"]`，**顺序即平局顺序**。
- 本机 `config/shops.csv` 是共享清单的**副本**，开轮前按内容哈希判方向同步：只本机变 → 推送；
  只库里变 → 拉取覆盖；**两边都变 → 停下把两版给人看，不猜**；推不动（网络或凭据没配好）不拦开轮，
  用本机现值并告警。
- `active=1` 的店才进计划（`active=0` 的行留着但不参与）；**机器永不写这列**。
- 名册增减 = 改 `machines.json`，**下一份计划起生效**；新机器无历史不设约束，历史无需迁移
  （每份计划文件自带快照）。

### 生成与发布

- 任何一台机器**打开采集程序时**检查本周计划：不存在就生成、发布到 `plan` 库并落库——
  没有固定的"计划机器"。**先到先发布**：本周计划已存在就只读，发布后当周不重算。
- 计划 JSON 字段：`week`、`generated_at`、`generated_by`、`params`（约束窗口 1 周、平衡窗口 4 周）、
  `algo_version`、`shops` 快照（店号 + 页数 + 名称）、`machines`、`assignments`，
  以及核对信息（放宽 / 每店可选机器数 / 空手）。`pages` 空缺或非法 → **拒绝生成并点名**缺哪几家。
- 历史页数取各周计划里的**旧值**（不因后来改页数重算）；本周采集预算以**计划快照**为准
  （计划说 23 页就采 23 页）。
- 同名 `.md`（人核对）：抬头（周编号与日期范围、口径行、较上周 ±）→ 按机器分组的表
  （店铺 / 名称 / 页数 / 上周 / 轮换 ✓ 或"首周"）→ 末尾核对行（合计与极差、相邻周同机器违例数、
  每店可选机器数最少值、放宽数、空手）。

### 分配算法（确定性）

- **硬约束**：同一店铺相邻周不由同一台机器采——按**计划文件的指派**判定，不按实际采集结果
  （这是三台各自独立算出同一份计划的前提）；首周与回归店（上一条历史计划里没有这家店）不设约束。
- **软目标**（大件优先贪心）：店铺按页数降序、店号升序依次处理；给某店挑机器时比分 =
  该机「近 3 周被指派页数之和 + 本周已分页数」，平局比本周已分页数，再平局按名册顺序。
- 空手（店少于机器）合法；无解兜底：候选为空时丢最老的一条约束、保住相邻周，计划里记「放宽」
  ——约束 1 周 + 至少 2 台机器时永不触发。
- 同一输入重跑逐格一致（`generated_at` / `generated_by` 是发布事实，不参与逐格对照）。
  逐格基准钉在 [tests/fixtures/plan_parity_expected.json](../../tests/fixtures/plan_parity_expected.json)
  与 [tests/test_weekly_plan.py](../../tests/test_weekly_plan.py)。

## 4. 采集程序里的准备串与降级

打开界面（命令行则开跑前）走同一步**准备串**：
**pull 计划库 → 同步店铺清单（哈希判方向）→ 确认本周计划（不存在就生成并发布）→ 把整周计划落库
→ 缺口检查告警（只告警不拦）**。

- 计划落进**本机计划表**（`weekly_plan`，**不入交换集**）：存整周的 `assignments` 不只本机那几行
  （账目与报告要对照"计划说了什么"）；界面与命令行读**同一份**落库计划。
- 开始页默认勾选 = 计划里归本机、且今天还没采够的店（已采商品数 ≥ 页数×30 的默认不勾，可手工勾上重采）；本机本周没店是合法正常态（界面明说，不报错）。
- **页数四层优先**：命令行 `--pages-per-shop`（人工冒烟，界面从不发）> 计划快照 > 店铺 `pages`
  > 全局 `max_pages_per_shop`。界面不提供改预算的入口。
- 轮次范围仍以**轮次自身**为准（计划是意图；"实际采了哪些"由 `rounds.run_date × shop_rounds` 回答，
  周报用它对照缺口）。轮次范围在北京日内锁定：中途改计划要先中止本轮，否则开轮报范围不符（退出码 3）。
- **越权只剩一种**：店在计划内、但本周归别人 → **放行并上报**（界面默认不勾、文案点名归谁，
  记进轮次备注与本机计划外账；汇总侧成为带说明的冲突）。理由：拒绝会挡住正当补采，
  而真正被破坏的是"相邻周不同机器"这条风险分散约束，所以文案要让人看见破坏的是哪一条。

| 情形 | 口径 |
| --- | --- |
| pull 成功 + 本周计划在 | 正常 |
| pull 成功 + 本周计划不在 | 生成本周计划并发布；三台同时生成靠先到先发布，push 被拒就重读 |
| pull 失败 + 本地已落库本周计划 | 用本地那份（发布后当周不重算，本地即权威）；界面标注「未能确认最新」 |
| pull 失败 + 本地没有本周计划 | **界面不开轮**（闸门）：给理由与「重试准备」；逃生口只在命令行 `run.py --ignore-plan`，走"自由采集 + 记账为计划外" |
| 清单同步推不动 | 不拦开轮，用本机现值并告警 |
| 纯汇总机 | 不检查、不生成、不发布（不采集） |

缺口检查（只读交换区，比对本机落后哪些店哪些天）只告警、不自动合并——汇总始终手工触发。

## 5. 数据交换台（`exchange.py`，双击壳 `dist\inventory_exchange.exe`）

- **一次运行**：检查 → 导出 → 发布判断集 → 拉取 → 汇总 → 收取判断集 → 报告；手工触发，
  启动后先导出、再汇总。命令行 `--only export|merge|publish|collect` 只跑其中一个动作，
  `--week 2026-W37` 补历史，`--window` 开小窗口；同一台机器同一时刻至多一次运行
  （窗口与命令行同规）。
- **退出码**：`0` 干净 / `1` 有需要人看一眼的（缺口、冲突、别人的包还没来、判断集这趟新记下的冲突）/
  `2` 本机没做成事（含判断集没发出去、没收进来）。
- **导出**：一致性快照 → `.db.gz` → push `raw-<本机>`；图片只传新增；包内记 `crawl_in_progress`。
- **汇总**：对每个别人的包按 §7 逐包导入；账里已有该包哈希的安静跳过。
- **判断集两条动作**：发布（§2 的 `judged-<本机>`，同内容空操作）与收取（名单 = 交换区里
  实际存在的 `judged-*` 库，逐家按内容摘要幂等导入）。两条动作互不依赖，与采集包那半也不
  设先后；两个库的位置从分析配置（`config/analysis.toml` 的 `matching.cache` 与
  `analysis.store`）读，没配分析配置就整半跳过并写明。判断库缺失、还没 clone、别家还没发布
  都只给可读提示，不中止其余步骤。
- **纯汇总机**：保留「导出」入口并写明"本机是纯汇总机，跳过"（不藏掉）；**判断集照常发布**
  （判断库各写各的，与角色档位无关，见 §1）。
- **周报**：`<交换区根>/报告/<年>-W<周>.md`，**一周一份、同周重跑重写同一份**（状态累积，不是日志相加），
  开头一行「本次运行」说明这一次做了什么。固定六节：**本机发布**（包名/提交/行数/图片新增与跳过）·
  **收进来的包**表（来源/周/行数/新增/覆盖/冲突/图片/结果，已导入过的标"已导入过 → 跳过"）·
  **判断集**（本机发布了几条判断 · 收进了谁的判断集 · 采纳了几条人工决定并点名来源 ·
  冲突几条并点名双方——冲突从本机冲突账现读，只增不自动消解）·
  **缺口与还没来的** · **冲突** · **下次该做什么**。逐次流水另在 `logs/exchange.log`。
- 缺口 = 计划里该采到的（店铺 × 日期）在收到的包里找不到；补不回来的历史缺口如实记、不催办。
  报告是**本机视角**的（冲突明细从本机导入账读）。

## 6. 汇总语义（各机收敛到同一份库的判据）

**交换集**（七表，分析最小集）：`shops`、`inventory`、`products`、`skus`、
`product_information_versions`、`sku_image_versions`、`product_image_assets`。完整证据
（`snapshots` / `event_log` / `raw_pages`）不进交换集。

**观测表**（`inventory`、`product_information_versions`）——一次采集就是一次观测：

- 取胜单位是**「一个 (日期, 店铺) 的一次采集」**；判据 = `(该店该日最后一次成功采集时刻, machine_id)`
  的**全序**。时刻不单独存：它就是该 `(shop_key, observed_date)` 在
  `product_information_versions.observed_at` 上的最大值；**包侧与本机侧跑同一段推导代码**
  （本机采集同样算出自己的 claim，本机 10:00 采的不会被别人 09:00 的包覆盖）。平局按 `machine_id`
  字典序；包级 `generated_at`（导出时刻）**不作判据**。
- 键相同的行由取胜方**整行替换**（不逐列拼）；键不同的一律保留；相反粒度（单规格/多规格）
  **整组取胜**；多规格 SKU 集合不同时取**并集**。

**SKU 图流水**（`sku_image_versions`）——按观测表的做法落库、但**不参与取胜裁决**：

- 逐行先查后写（键 = `(店铺, 商品, SKU, 观测时刻, COALESCE(内容哈希,''), COALESCE(失败原因,''))`），
  已存在即跳过、新行计入；**不依赖唯一索引在不在**——老库上它可能没建起来，那种库上
  `INSERT OR IGNORE` 挡不住重复，先查后写才挡得住（版本表先例同一课）。
- 各机观测天然互异：同键只可能是同一次观测的重复，没有哪个版本更值得留——既不进取胜方账、
  也不进冲突账（claim 裁决只管上面两张观测表）。
- `v1` 旧包缺这张表 = 这半为无、照收（见 §2 的格式版本与兼容方向）；其余六张表维持硬要求。

**身份表**（`products`、`skus`、`shops`）——没有观测，只有"这张脸长什么样、什么时候见过"：

- **交换律合成**：`first_seen_at` 取 MIN、`last_seen_at` 取 MAX；描述列（`product_name`、
  `product_url`、`main_image_url`、`sku_name`、`shops.shop_name` / `shop_url`）按最近一次观测取胜，
  平局按 `machine_id`。

**幂等、事务与投影**：

- 包身份 = 包文件内容 **SHA-256**；本机导入账记「我导过这个哈希」，同哈希再来直接跳过。
- **整包一个事务**：失败全回滚，重跑等价于首次导入；**同一批包以任何顺序导入得到同一份库**。
- 版本表去重键是表达式唯一索引 `(shop_key, offer_id, observed_at, COALESCE(content_hash,''),
  COALESCE(image_error,''))`，导入走 `INSERT OR IGNORE`（`content_hash` 可能为 NULL，而 SQLite
  唯一索引里 NULL 互不相等）。
- 导入一律**显式投影列**，禁止 `INSERT ... SELECT *`（旧包的列集可能多一列/少一列）。
- **先拉图、再插行；仍缺的照插**，缺口如实列进报告；导入事务期间该连接 `foreign_keys=OFF`
  （图片字节走独立通道，本来就可能后到；"这次观测发生了"是既成事实）。

**对本机采集计算的影响**：同日去重**参与**（导入行正是"今天已有成功观测"本身）；今日大盘与开始页
吃到导入行；本轮计数 / 失败率 / 孤儿检查**免疫**（读的是不在交换集、且按 `round_id` 归属的数据）。
本期**不区分**"我采的"与"导入的"（行级溯源见 §8）。

**冲突留痕**：冲突 = 同一 (日期, 店铺) 上出现两个不同 `machine_id` 的 claim（来源：越权、降级逃生口、
换周交接不清）。「谁赢」由判据决定、各台一致；「我见过这个冲突吗」取决于该机导入过哪些包。
明细记进**本机导入账**（日期、店铺、双方 `machine_id`、双方采集时刻、胜负、败方被覆盖与保留的行数），
**不入交换区**。

**两条在案约束**：

- 导入会重排 `product_information_versions.id`，分析侧**不要**把它当作跨机稳定的标识
  （要么接受、要么改用内容派生标识）。
- **程序与库必须一起升**：`inventory.diff` 退役后旧程序写新库是硬失败（`no column named diff`）；
  每台机器升级后首次开库自动付一次迁移（连接即迁移），无需人工操作。

## 7. 上机步骤编号（权威）

程序里的提示语（「照上机清单第 4/9 步…」）引用这套编号——**不要重编号**；逐步命令与判据见
[三机上机清单](三机上机清单.md)。

采集机 14 步：1 Edge 在位 → 2 装 Python → 3 clone 代码 + 装依赖 → 4 建运行根 →
5 浏览器配置与 `login_chrome.py` 扫码 → 6 冒烟采集一轮 → 7 写 `machine_id` → 8 Gitee SSH →
9 clone 交换库（本机 raw + plan）→ 10 COS 桶与 AK → 11 名册与共享清单 → 12 第一次打开界面（走准备串）→
13 首次数据交换台 → 14 判断库（建 `judged-<机器>`、clone、写判据：推自己那本成功）。

纯汇总机 8 步（不装采集那半）：环境（跳过 chromium）→ clone 代码 + 建运行根 → 凭据
（COS 只读 AK；Gitee 公钥照常注册——判断库要发布）→ clone 交换库 → 角色写 `merge_only` →
冷启动跑一轮交换台（收全历史包）→ `python analyze.py` 能出数 → 判断库（建库、clone、写判据）。

## 8. 验收口径（一期真实运行）

一周真实运行跑完之后（不以单元测试代替），三台 + 纯汇总机各跑一次交换台，然后：

- 三台各自完成本机份额（计划表 × `rounds.run_date × shop_rounds` 逐条对照，缺口逐条带当天轮次终态当说明）；
- 三台各自发布了本周包；报告里「还没来的包」为空或已有说明；
- 任取两台逐表一致（交换集里承载取胜结果的六张表，SKU 图流水在内）；数据逐表一致 ⇒ 同一份
  数据上分析产出同一份结果；
- 计划核对行「相邻周同机器 0 处」；
- 纯汇总机一次冷启动重放成功：一轮收全交换区历史包、各表有数、图片按清单从 COS 补齐
  （首次全量约 150 MB 量级）。「各表有数」不含 `sku_image_versions`——历史补齐阶段它本来就
  可能为空（判据在 `tools/acceptance_check.py` 的核心表集）；它的图字节照归「按清单补齐」
  那一半核。

核对工具：`python tools/acceptance_check.py`（五条口径的读法写在它的模块 docstring 里）；
跑法与判据在 [三机上机清单](三机上机清单.md) 的「三机验收」一节。

## 9. 本期不做

自建服务器 / VPS / 内网穿透；实时或秒级同步；单机多账号轮换（已被三机分片取代）；
完整证据（`snapshots` / `event_log` / `raw_pages`）进汇总；展示层的行级溯源；
三份全量库的备份与恢复策略；缺口的催办节奏；基线快照（任意一台发全量包加速冷启动）。
备选通道（Syncthing 当交换区替身、坚果云 WebDAV 当对象存储替身、周计划走飞书表格）两族互不依赖、
可同时准备，启用条件是主通道在某台机器上实测不可用——全文见
[三机汇总备选通道调研](../research/三机汇总备选通道调研.md)。
