## 2. A10 逐条证据

| 判据 | 证据 |
| --- | --- |
| 中途结束进程后重开，已完成的那部分判断在库里 | 两处：① 子进程用例——子进程跑真 `suggest`，跑到一半（两个工作线程同时越过打断点，实测第 46–47 次同款比较）时 `os._exit(1)`（不跑 finally、不回滚，等价关窗／任务管理器结束进程）→ 重开库读到 25 条判断（一批）、不是 0 条；② 分析程序级彩排 `01-demo-rehearsal.py`——起真 `analyze.py --serve`、真 HTTP 接口与替身模型服务，第 30 次比较后硬结束进程 → 缓存里有 25 条判断 |
| 未完成的部分不留在库里，也不影响已完成部分 | 留下的判断条数是批大小（25）的整数倍；当前那一批整批回滚；断言 `evidence` 的版本集合恰好等于已提交 `judgments` 的版本集合——漏写方向（有判断、证据索引缺行）的回归会被它抓住；反方向（有证据没判断）在这条路径到不了（证据只与判断同批写），断言留着防回归 |

| 判断阶段一结束就落盘（余数批不悬着） | 用例 `test_judgment_phase_flushes_before_the_grouping_tail`：批 3、50 对判断，分组计算被打断后库里是全部 50 条（没有收尾提交就只剩 48） |

## 3. 提交粒度：固定批 25 条（取舍）与耗时对比

**取舍**：固定批，不设配置项。理由——这是内部的耐久性取舍（损失窗口 ↔ 提交开销），没有按机器
调整的语义；加一个配置键要连带示例配置、校验与文档，换来的只是把一个「一批几十秒」的窗口挪一挪。
一批 25 条按本机实测吞吐（约 1982 次调用／小时、并发 2）约合 40–60 秒的模型调用，中途退出最多
丢这个量级。

**耗时对比**（同一份工作量、同一台机、替身模型、口径交错各跑 3 轮取中位数）：

| 工作量 | 分批提交（每批 25） | 整批一次提交 | 差 |
| --- | --- | --- | --- |
| 400 件商品／约 2400 对判断 | 0.46 s | 0.41 s | +0.05 s |
| 800 件商品／约 4800 对判断 | 0.91 s | 0.83 s | +0.08 s |

原始输出与脚本：`.scratch/logs/tickets/judgment-set-sync/ticket01/`（`耗时对比-原始输出.txt`、
`measure-commit-overhead.py`；本地工单库，随票工单保存）。**读法**：多出来的是「每批一次提交」的
库侧开销，约 0.3 毫秒一次、总量几十毫秒；百分比看着大只是因为替身把模型调用抽掉了，总时长
只有一秒上下。真实一次分析约一小时，以模型调用为主，这个开销可忽略。

## 4. 演示路径的彩排（分析程序级）

票面演示路径「起一次分析 → 跑到一半结束进程 → 重开分析程序跑同一区间」的彩排脚本：
`.scratch/logs/tickets/judgment-set-sync/ticket01/01-demo-rehearsal.py`（输出 `演示路径-彩排输出.txt`）。
真的部分：`analyze.py --serve` 真进程（真 `ANALYSIS_LOCK`）、真 `POST /api/analysis` 接口与
Origin 校验、真库存库与判断缓存、真 HTTP 传输（`request_json` → `urlopen`）；替换的只有外部
模型（本机 127.0.0.1 的替身服务，每次调用睡 50 毫秒）。

一次实跑：60 件商品 → ① 冷跑比较 259 次、27 组；② 第 30 次比较后 `kill()` 进程 → 缓存里留下
25 条判断（1 批）与 18 个证据版本；③ 重开程序、同一区间再跑 → 比较 234 次（= 259 − 25），分组
与冷跑一致（27 组）。
