# 运行问题：记录与打包

在任意一台机器（采集机、纯汇总机都算）上操作程序时出的问题——报错、弹窗、拒绝、卡住、
结果不对——按本规范**完整记录并打成一个包**，拷到别的机器交给 Claude 排查。

- 工具：`tools/issue_bundle.py`（Windows 双击 `tools\issue_bundle.cmd`，等价于同一条命令）。
- 产出：一个记录目录 + 一个同名 `.zip`，落在 `<项目根>/.scratch/tool-output/issues/`。
- 一句话原则：**当时的那台机器上的东西才算证据**。日志会被轮转覆盖、截图和原始页面事后补不回来，
  所以发现问题的第一件事是跑工具，不是重启、不是清理。

---

## 一、怎么记（做的人按这五步）

1. **别动现场**：不关窗口、不重启程序、不删 `logs/`，先记下屏幕上的原文（能截图就截图）。
2. **跑工具**：
   - 双击 `tools\issue_bundle.cmd` → 提示「点题」时输入一句话（例：`交换台报错：raw-m1 push 被拒`）；
   - 或命令行：`python tools/issue_bundle.py --title "交换台报错：raw-m1 push 被拒"`。
   工具自动采集机器事实、日志尾部、库与交换区状态、最近截图与原始页面，并生成 `REPORT.md`。
3. **填 `REPORT.md`**：第一节「问题描述」七项，一项都不能空（工具会替你打开记事本）。七项是：
   现象 / 期望 / 复现步骤 / 发生时间 / 当时在做什么 / 最近改过什么 / 还能复现吗。
   拿不准的写「不知道」也比空着强——空着的一项就是事后必须再联系你一次的原因。
4. **打包**：双击流程里填完存盘、回到窗口按任意键即可；命令行是
   `python tools/issue_bundle.py --pack`（不带目录就打最新一份）。得到同名 `.zip`。
5. **交出去**：把 `.zip` 拷走（U 盘、聊天窗口都行）。`.scratch/` 不进代码仓，包里没有任何密钥。
   接收方在项目根跑一条命令就能解开并看到摘要（见 §五）。

已记过的记录可以 `python tools/issue_bundle.py --list` 查看（每条显示 REPORT.md 填没填、打没打包）。

## 二、包里有什么（收到包的 agent 先读这张表）

| 路径 | 是什么 | 什么时候看 |
| --- | --- | --- |
| `REPORT.md` | 人的描述（七项）+ 机器事实摘要 | 永远先读它 |
| `facts.json` | 全量机器事实：机器编号与角色、程序版本（git 提交/工作区脏不脏/三只壳的 sha256）、Python 与依赖版本、配置加载结果、逐份日志的采集情况、各目录体积与磁盘剩余、`missing`（缺什么）与 `warnings`（采的时候出了什么岔子） | 定位「哪台机器、哪个版本、什么配置」 |
| `state/db-state.json` | 库存库/分析草稿库/匹配缓存库的状态：各表行数、最近轮次的终态、采集身份行、停止请求、本周计划、导入口账、导入冲突、计划外采集、最近事件、`integrity_check` | 排查「为什么没抓/没收到/少数据」 |
| `state/exchange-state.json` | 交换区：各 `raw-*` 库与 `plan` 库的分支/提交/脏文件/远端/最近提交，已发布的包，最近的周报，机器名册 | 排查交换台问题 |
| `state/reports/*.md`、`state/plan/*` | 最近两周的周报原文、最新一两份周计划原文 | 与退出码/缺口/冲突/分工的说明对照 |
| `logs/runtime/`、`logs/repo/` | 运行根与项目根两处日志的尾部（每份最多 2000 行，是否截尾在 facts.json 里） | 找栈回溯与当时的时间线 |
| `config/` | `config.toml`、`analysis.toml`、`shops.csv` 的副本（`.toml` 已脱敏） | 看这台机器的实际配置 |
| `screenshots/` | 最近的介入/弹窗截图（最多 8 张） | 人看到的画面 |
| `raw-pages/` | 最近一轮解析失败的原始页面（最多 3 个） | 解析规则要不要调 |
| `diag/` | `data/diag/` 里最近的文件（最多 5 个） | 现成的诊断产物 |
| `MANIFEST.json` | 逐文件 sha256 与大小 | 校验传输有没有损坏 |

读的顺序建议：`REPORT.md` → `facts.json` 的 `missing`/`warnings`/版本事实 → `logs/` →
`state/` → 原始证据（截图、原始页面）。**先看 `missing`**：缺的东西不是"没有发生"，
是"这次没采到"，别据此下结论。

## 三、什么情况该记

- 程序报错、弹窗、拒绝启动（含壳的失败弹窗与启动器日志）；
- 行为与 README / 操作单写的不一样；
- 交换台退出码 2，或周报里「缺口」「冲突」「还没来的包」说不通；
- 采集异常停止、卡住、重跑不续；
- 分析结果明显不对（畅销品、同款、曲线）；
- 任何"偶发但还会再来"的现象——偶发才更需要当时那份现场。

不必记：程序已经明说清楚的正常状态（例：交换台退出码 1 且每条「需要看一眼」都有说明）。

## 四、不做什么（工具已内建，别手工绕过）

- **不碰运行中的东西**：数据库只读打开（连不上就记下来），不写库、不重启程序、不改配置。
- **不采密钥**：`config.toml` / `analysis.toml` 的副本过一遍脱敏（键名带 `secret`/`token`/
  `key` 一类的值换成 `<已脱敏>`；`key_env` 这种「值就是变量名」的保留）；环境变量只记「有没有设」；
  `~/.cos.yaml`、`secrets/`、`.env` 一律不读。
- **不无限增重**：日志按尾部截（每份 2000 行）、截图 8 张、原始页面 3 个、diag 5 个，
  超出部分在 `facts.json` 里留文件名与大小。整包通常在几百 KB 到几 MB。

## 五、交出去 / 收进来

- **交出去**：把 `issues/<包名>.zip` 整个拷走即可；只有 zip 不够用时（比如对方想直接看目录）
  也可以把同名目录整个拷走。
- **收进来**：在接收方的项目根跑一条命令，包解到 `.scratch/inbox/<包名>/`，
  并直接打印摘要（问题描述 + 没填的项 + 缺了什么）——接收的人/agent 先看这段再深挖：

```bash
python tools/issue_bundle.py --unpack <记录包.zip>
```

  不带 `--into` 就落在 `.scratch/inbox/`；包名已经带了日期、时刻与机器编号，不用再改名。
- 这是一条**人工通道**：包不自动上传、不进 Git、不过交换区。谁的问题谁打包，谁需要谁去拷。

## 六、与开发工单的分工

| | 本规范（运行时问题） | 开发工单（要改代码的事） |
| --- | --- | --- |
| 记录在哪 | `.scratch/tool-output/issues/`（每台机器各存各的） | `.scratch/<feature-slug>/issues/NN-*.md` |
| 怎么到别的机器 | 人工打包、人工拷 | 不流转（`.scratch/` 机器本地） |
| 谁写 | 出问题的机器的操作者 | 本机的开发会话 |

收到的包确认是缺陷后，由开发侧按 [docs/agents/issue-tracker.md](../agents/issue-tracker.md)
建票修复；票里引用包名（例：`2026-09-22-2033-m1-交换台报错`）即可回溯证据。
