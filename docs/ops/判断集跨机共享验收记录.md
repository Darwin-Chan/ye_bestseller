## 2. 五条判据逐条证据

输出编号（）= `验收演练-输出.txt` 里的步骤号。场景：A01 店铺四件商品（月牙杯 ×2、云朵杯、
贝壳杯），模型替身把两件月牙杯判成同款、把云朵杯与贝壳杯也判成同款。

### 判据 1：省钱路径（A01／A03）

**步骤**：（②）m1 跑分析 [09-14, 09-19]——模型调用 **7 次**（6 对判断 + 1 次图像核验）→
（③）m1 `--only publish`：判断 6 条 · 证据 4 条 · 人工决定 0 条 → `judged-m1 @ 8554bc2` →
（④）m4 `--only collect`（此刻 m4 还没有数据）→（⑤）m1 `--only export`；m4 整趟：新收 1 个包
（60 行）、图片拉回 4 张 →（⑥）m4 对同批证据版本跑同一区间。

**结果**：m4 模型调用 **0 次**；商品行全部「**缓存 · 来自 m1**」；状态行与 m1 一致
（`matching_summary` 逐字段相等：`{'judged': 4, 'failed': 0, 'retryable': 0, 'config': 0,
'missing_evidence': 0, 'disabled': 0}`）；两机分组对一眼一致（见 §3）。

**本机新增/变更的商品照常判**（⑬）：第二轮数据带来新商品海浪杯（55）与换过图的贝壳杯（44，版本变了）。
m4 再跑分析：10 对里 **3 对命中缓存**（旧版×旧版）、**7 对交模型**——交出去的每一对都含海浪杯或
贝壳杯（名单逐对打印：`[('云朵杯','海浪杯'), ('云朵杯','贝壳杯'), ('月牙杯','海浪杯') ×2,
('月牙杯','贝壳杯') ×2, ('海浪杯','贝壳杯')]`），调用 8 次（7 对 + 1 核验）。

### 判据 2：决定搬运（A04）

**步骤**：（⑧）m1 在分析页面上确认两组（月牙杯组、云朵杯+贝壳杯组）→ 保存 → `--only publish`：
人工决定 2 条 → `judged-m1 @ 7d71464` →（⑨）m4 `--only collect`。

**结果**：m4 周报第三节记着「**采纳：1 条人工决定（来自 m1）—— 已进本机账本**」；m4 账本里
月牙杯组的关系带 `machine_id: 'm1'`（云朵杯+贝壳杯那条与 m4 的排除对冲突，按判据 3 处理，不算采纳）；
m4 页面上该组是**已确认 · 由 m1 确认**（截图 01）。

### 判据 3：冲突暴露（A05）

**步骤**：（⑦）m4 用现有动作做出相反决定——把贝壳杯移出云朵杯组（记下排除对 (33,44)，来源 m4），
保存、`--only publish` → `judged-m4 @ 19f94f7`；（⑧）m1 的确认照发；（⑨）m4 收 m1 的、（⑩）m1 收 m4 的。

**结果**：**两边各自收取后都进了冲突账**——m4：`group_vs_exclusion`（外来的 m1 的组 vs 本机的 m4
的排除对）；m1：`group_vs_exclusion`（外来的 m4 的排除对 vs 本机的 m1 的组）。**两边的周报都点名双方**
（「冲突：一边并组、一边排除 —— 外来的 m1 的 组 vs 本机的 m4 的 排除对（商品 ["A01","33"]、["A01","44"]；
在分析页面上裁决）」），周报结果行的「判断集冲突 1」与退出码 1 同源。**两边的本机决定都不被静默改动**：
m1 账本一个字没动（两条关系原样），m4 的排除对原样。**分析页面把相关组落回待确认并标来源**（⑫）：
m1 的云朵杯+贝壳杯组显示「待确认（有冲突）」+ 说明「冲突：m4 把 云朵杯、贝壳杯 排除在外（不成组）；
本机 认为 云朵杯、贝壳杯 是一组。请人工裁决。」；m4 侧说明方向相反、点名 m1 与 m4；除冲突那一对外，
两边分组一致（`[(('11','22'), True)]`）。截图 02（m4）、03（m1）。

### 判据 4：幂等（A06）

**步骤**：（⑪）m1 同内容再发布、m4 再收取（两次收取分别在 ⑤ 与 ⑪）。

**结果**：m1 再发布——报告写「与已发布那份**同内容（无新提交）**」，`judged-m1` 的 HEAD 逐字节不变
（`7d71464`）；m4 再收取——报告写「**已收过**（…无变化）」，账本摘要、缓存摘要与冲突账的三元组
before/after 相等（`账本/缓存/冲突账无变化=True`）；⑤ 那次整趟里也见过「跳过 1 份已收过的判断集」。

### 判据 5：顺序（A07）

**世界一（判断先到、数据晚到）**：④ m4 在还没有 A01 数据时收取——判断 6 条进缓存（来源 m1）、
**闲置待用**，收取本身不报错（该趟退出码 1 的来由是数据那半的「还没来的包：m1」，与判断集无关，见 §6）；
此刻 m4 跑分析被如实拒绝（「该日期区间没有可分析的库存」）；⑤ 数据到齐后（⑥）判断全部命中缓存，
分组与 m1 一致。

**世界二（数据先到、判断晚到）**：② m4 先收数据（此刻 judged-m1 还没有判断集可收，报告如实写
「还没发布过判断集」；本机也「没有判断集可发布」）——**不报错**（退出码 0）；③ m4 跑分析照常调用
模型（7 次）；④ m1 跑分析并发布；⑤ m4 收取后再跑分析——**0 次新调用**，收取前后的分组不变
（`最终结果一致=True`）。

**两种顺序同一个收敛态**：世界一 m4 的收敛态（⑥）与世界二 m4 的收敛态（⑤）逐组相等
（`[(('11','22'), False), (('33','44'), False)]`），也等于 m1 第一次分析的结构。

## 3. 两条附加口径

- **两机在同一批数据上分析、同款分组对一眼一致**（三机验收口径）：⑥ 里 m1 与世界一 m4 的
  `group_shape`（成员集合＋确认态）相等、`matching_summary` 逐字段相等；⑭ 里两机交换集五表逐表一致
  （inventory 26 行、versions 26 行、products 5、skus 5，`shops` 两机都空）。差异只剩「商品行显示的
  结论来自哪台机器」（m1 显示「模型」、m4 显示「缓存 · 来自 m1」——这正是本功能要的）。
- **判断集与数据两条通道互不影响**：⑭ 的 HEAD 台账——`raw-m1` 在 ⑤ 导出后到 ⑪ 收完之间只有一个值
  `7253f45`（判断集的发布与收取一个字节没碰数据那半的库），只有第二次导出（⑬）才换值；`judged-m1`
  只随两次发布前进（`8554bc2 → 7d71464`），`judged-m4` 只随 m4 的两次发布前进（`bbd00d5 → 19f94f7`，
  ⑬ 的 `38dc1d2` 是 m4 把收到的判断转发出去的发布），各次收取一个提交都不加。纯汇总机（m4）的导出
  按角色跳过（报告写「本机是纯汇总机，跳过」），判断集照常发布。
- **读组的脚本一律 `.get(...)`，别下标读**：组的 dict 键集不齐——装配出的组是 `id`／`confirmed`／
  `members`（票 19 的「输出＝与现状同形」），reuse 与人工编辑建的组另带 `machine`（票 07 的来源列）；
  页面是防御式点读，工具脚本（含本记录引的演练脚本）照同一口径，直接下标读会 `KeyError`。
