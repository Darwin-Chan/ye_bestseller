Problem

ReadFailedVisit 把同一个事实写了两遍（.error 与构造时就等于 Observation.read_failed(exc) 的 .observation，detail_visit.py:128）， 两个调用方各取一半：点击路径 raise visit.error，补采路径 return visit.observation。 后果不是措辞差别，是同一个瞬时读失败，一边崩整轮、一边记一行。

Solution

访问开始只交回一次观测，「这趟意味着什么」收进一处：读失败是观测的一种 （read_failed 已在），编号未知也是（FailureKind 加一类）， 只有停止族与 deny 阈值才上抛。两条路径各自保留记事件与 deny 阶梯。

  • locality：「商品级异常不许掀翻整轮」从一侧收回一处
  • 两套并行词汇（.error / _LateDenied）一起消失
  • 瞬时读失败不再让整轮带 traceback 退出
  • 补采侧那句防御性 RuntimeError（:474）随之作废
与 ADR-0023 冲突，但值得重开。 ADR-0023 明写了「已知商品身份的补采消费 observation 进入尝试重试；身份未知的点击原样重抛 error」。 重开的依据：这条分叉的两个前提都站不住——(1) 「编号尚未可靠取得」只对 acquire 失败那一半成立；初次 guard 失败时 PlaywrightCard.acquire 早已把弹窗地址里的 offer_id 填好（click_listing.py:401-413），本仓自己的用例 也正是用 offer_id="11" 覆盖这条路的；(2) ADR-0023 决定的是「观测必须在 guard 之后读」，没决定「同一个读失败一边崩整轮一边记一行」。ADR 真正要的不变量（停止族原样穿透、不写商品失败行） 不受影响。

Problem

这三个工具的存在目的正是诊断生产点击路径，却各自维护一份副本：等待比生产宽一倍 （5000/4000 对 2500），并缺生产那条「无弹窗但页面已就地跳到详情」的分支—— 于是工具里复现不出的现象，可能正是生产失败的原因。 同时 browser_pw 为它们保留着八个下划线别名，注释里自己写明 「本文件自己不用它们」。

Solution

工具的页面装配一律走生产 seam：点击用 click_listing.click_card （它本来就为诊断交回页面原始状态），选择器与滚动原语走 listing， 介入判据走 guard。工具与 browser_pw 的接口都随之变窄。

  • deletion test：删副本，复杂度集中到 seam，不散往调用方
  • 漂移不可能再发生（等待只有一个来源）
  • browser_pw 的 interface 少八个只为外人存在的名字
  • 先例已在：sync_list_titles.py 早就这么调
核过的：三个副本的等待值分别是 5000 / 4000 / 4000（WAIT_POPUP_MS = 2500）； 「没有 import 障碍」有现成反例——tools/sync_list_titles.py:69 已经在调 click_listing.click_card；别名层只被 tools/ 与 一条钉住清单的用例（tests/test_browser_pw.py:55）使用。 ADR-0019 只管三个工具共用一个浏览器会话（调试端口 / profile / 收尾指纹），点击语义从未被它定过。

Strong ports & adapters

stop_request.py:171-176（Protocol） · :179-222（可脚本化 adapter） · :236-259（rebind 定义）

:415-427（tick 用 hasattr 探它） · gui.py:131-132, 245-247

今天 · interface 五个方法，编排器用第六个

StopRuntime（Protocol 声明的 interface）

bind observe terminate close_browser release

hasattr(self._runtime, "rebind") —— 编排器去探一个 interface 里没有的方法

rebind（只长在 ProcessStopRuntime 上）

ProcessStopRuntime · 生产

有 rebind

绑定被拒 → 下个 tick 重试

RecordingStopRuntime · 本 module 自带的测试 adapter

没 rebind

连「绑定暂时拿不到」这个状态都造不出来

于是这条路既没被走过，也写不出用例——而「interface 就是测试面」正是它该兑现的。

改完 · 恢复路径写进 interface

StopRuntime

bind observe terminate close_browser release rebind

ProcessStopRuntime

rebind = 重新 bind 冻结的那个目标

RecordingStopRuntime

rebind = bind（替身第一次能表达「暂时拿不到」）

tick 里那条 hasattr 分支消失； 重绑成了一件事：bind 拿不到就下个 tick 再来

测试 seam 现成：替身上加 fail_bind=True（或用现成的 BindFailure 形态）就能驱动「第一次被拒、第二次成功」。

Problem

bind 拿不到句柄时交回 capability=None （:245-250），此后每次 tick 都判 UNVERIFIABLE 并停在核验里——而 UNVERIFIABLE 的短路在 deadline 之前，窗口自己不会到点。 唯一的出路是 tick 里那次重绑，而 hasattr 把它挂在「这个 adapter 碰巧有没有这个方法」上：恢复能力取决于接线，不取决于不变量—— 正是 ADR-0024 当初要把这种差别收进 module 的理由。

Solution

把重绑写进 StopRuntime：两个 adapter 各实现一次， tick 无条件调用。interface 从「拿得到句柄时怎么办」扩成 「拿不到时怎么办」——后者才是这个 seam 真正要回答的问题。

  • depth：恢复语义进 interface，不再靠结构探测
  • 替身第一次能表达生产的状态，这条路有测试面
  • 新 adapter 不会静默失去重试
  • 删除面：hasattr 分支一处 + 一个隐式契约
核过的：全仓 grep rebind 只有三处，全在 stop_request.py（定义 / hasattr / 调用）， 测试里一次都没有；RecordingStopRuntime 是 StopWatch 测试唯一的 adapter （tests/test_stop_target.py 的四处构造全是它），它的 bind 恒给非空 capability，所以连「capability is None」这个前置状态都造不出来。 生产可达性也核过：ProcessStopRuntime.bind 在 OpenProcess 被拒、或目标没有 OS 创建证明时交回 None； 卡住的后果是界面那句「上一次停止仍在核验或收尾，请稍后重试」一直成立 （gui.py:245-247），新的采集起不来。

同轮被否掉 / 降级的

写下来是为了说明取舍不是没看见，也免得下一轮重新发现它们。没有一条够 Strong。

  • 补采侧没有 adapter seam：tests/test_p1.py:75-96 一个用例打五个桩（navigate_detail、ready_detail_page、 intervention_kind、is_deny_url、 extract_main_image），还断言 page.content.call_count == 2 ——即 ReadyDetailVisit 内部轮询了几圈；而点击侧一份桩都不用。 「值对但弱」：它说明 seam 的缺口（click_listing.py 的 docstring 自陈当初就是为这个拆的 adapter）， 但行为一字不变，够不上「摩擦是真的」那一条。
  • 降级：两个页面的进度各拼一遍（子代理报了 Strong）。 views.run_view 与 result_view 确实各拼一遍同 9 个键， 但口径本来就在 round_tally / _shop_breakdown / _round_counts 一处持有，两个页面调的是同一批——重复的只是组装那几行， 「一致由一条用例保证」的说法我核出是错的（用例钉的是口径，不是组装）。够不上加深。
  • retryable 有两个所有者，两个都没读者： StopStatus.retryable 由相算出（:135, 369-370）， 全仓含测试零读者；EffectResult.retryable 恒 True（四个构造点无一传 False）， 唯一读者是一条断言它 True 的用例；真正回答这个问题的是界面（gui.py 八处，六处写死 "retryable": True）。 09-19 的报告已经在候选 02 里把它记成「一处口径要收」，收口时没动它——记进挂账，下次动这条 seam 时一起。
  • 只写不读的字段：RuntimeFacts.error（真值枚举过： 它在与不在，_relation 的结论都相同）、 StopCommand.round_id（只有 PAUSE 分支读，ABORT 那半付了不用）、 StopInFlight.kind/target/state（重述 command，无读者）、 gui.start_ts（写两次，零读）。同一形状在 09-19 已当过候选，这次都是单字段规模，不单列。
  • browser_proc.close_browser(launched_by_us=)： 生产唯一调用点恒传 True（stop_request.py:311）， :170-172 那条分支只有用例走得到；port 自称「只为日志」。 形状与 09-19 候选 03 一模一样，但它守的是一个破坏性边界——删它得先论证「缺 pid/proof 一律拒绝」已经够， 而 ADR-0028 正说授权来自绑定。留给下一轮带上下文再判。
  • 界面会话事实（已抓时长）没有所有者：_current_elapsed 一处读、 start_run / resume_run / pause_run 三处写同一组字段（gui.py:141-145, 261-264, 300-303, 318-321）， CONTEXT.md 专门为「界面会话事实」立过词。深化的形状清楚（变更收成几个转换 + 一个读法）， 但没证明出可观察的错——够「值得探索」，不够这一轮的尺子。
  • 停止窗口只由界面推进：_stop_watch.tick(conn) 只在 gui.py 七处被调（171/187/245/278/326/363/429）， 「每个入口都要记得 tick」没有落点——忘了就是强杀永不触发、cleanup_pending 永不重试。没构造出真实漏 tick 的路径，故不列。
  • 另有三条子代理提出、我核后判为不成立：「这一轮该不该停有两个所有者」（判据只在 rounds.ensure_workable，其余是检查点）、 「db.py 该按组拆 module」（逐组 deletion test 都是搬家不是变小， 唯一例外正是 ADR-0027 挂起的候选 05）、「逐店 deny 是 N+1」（有专门索引，实测 0.80→0.09 秒）。
