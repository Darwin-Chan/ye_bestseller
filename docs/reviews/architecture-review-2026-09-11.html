问题
提交这一侧的 interface 仍偏 shallow：调用方要构造数据库行并遵守多步顺序，四处 implementation 已出现标题优先级差异。
改进
把 SKU 整理、商品写入、库存快照事务和成功收尾集中到一个 deep module，保留已有“最后一个商品提交后再终止”的行为。
删除检验
只加一层转发，删除它不会损失能力；真正有效的 module 删除后，完整提交约定会重新散落到四个调用方。
  • locality：提交规则一处维护
  • leverage：四处共享同一行为
  • interface 成为测试入口

证据与现有测试

test_db.py:69 先清失败再保存，顺序与生产路径相反；:154 只证明提交后抛终止异常，未覆盖其后的失败清理。

测试迁移

保留零库存、缺库存、库存差分和回滚断言；提交与收尾组合经同一 interface 验证，替换手工编排顺序的测试。

现有库存快照事务本身有价值；候选增加的是完整商品结果的 depth。浏览器导航、重试资格归候选 02，轮次终态归候选 03。

  • locality：补采规则集中
  • leverage：两种入口共享预算
