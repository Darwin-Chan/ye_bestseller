也就是说：判据认的那一幕是真的，仓库里有案。721 条 verification 事件全是 slider，一条 login 都没有——一个已经命中的判据 从没留下过它命中过的痕迹。

但那个循环本身还没在生产里跑过。 observe() 的循环是 2026-09-14（2d2cba1）才引进的， 而生产数据止于 09-13。旧代码只调一次 wait_for_resolution： 确认窗口里 resolved() 为真即静默丢弃、继续往下走—— 正好对上那 7 条的结局：detail_parse sku_count=0 + detail_fail，没有 click_deny、没有 verification 事件。

所以本轮的主张分两层：判据分叉与无出口是静态可证的（并已实跑复现）； 它在生产循环里挂住还没发生过——循环比数据年轻四天。

Problem

guard 对同一份页面证据给了两套判据：检测用三样，解决判定只用两样。 正文这一路因此成了「检测认、解除不认」的信号——判真的那一刻就被同一次判定自己否掉。 详情路径的那个循环拿不到出口；榜单路径（listing.py:240）走的是同一对调用， 症状相反：wait_for_resolution 空转一场，登录墙既不等人工、也不发 verification_appear，直接落成店铺失败。

Solution

guard 持有它认的全部证据，读一次给出一个页面验证态； 「要不要人介入」与「解决没有」都是这个状态的读数，不再各读一份子集。 形状是两套判据收成一份，不是给循环加超时——加了超时，正文命中的介入仍然 既等不到、也解不开。
收成一份之后确认窗口才回到它声明的职责：它存在是为了过滤 没有 DOM 落点的瞬时信号（ADR-0029 原话是 tmd/x5sec 上报那一类）。 正文是 DOM 落点，它本来就该挺过窗口、响铃、等人——而详情循环也才第一次拿到 continue 之后那个「页面真的变了」的状态。

  • locality：「什么算要人工、什么算好了」只在一处
  • leverage：两条调用路（详情 / 榜单）一次兑现
  • 详情循环第一次有终止保证
  • 测试 seam 现成：test_guard.py 的假页面

ADR-0029 已经看见过这个洞，只是把它记在了另一个信号名下。 那条 ADR「被否掉的方向」一节的原话：

「intervention_kind 为真 → _guard() → ready_detail_page 说页面可用（不是 deny）→ 重置可读窗口 → continue → 再判还是真…… → 不终止。 所以还得同时造一个「这条信号什么时候算解除」的判据。」

它把「再判还是真」归因于_punished 在 capability 里冻结、而 resolved() 又看不见它——这是对的，于是它选择删掉 punished。 但洞不在那条信号里，在「检测与解除读两份证据」这件事里： 正文命中的介入走的是同一条 continue， resolved() 同样看不见正文。删掉 punished 关掉了一个入口，另一个还开着——而 ADR-0029 自己写下的「缺的那条判据」，正是这条要补的东西。

口径收一句：这不是 0029 留下的缺口——它的「实现边界」明说不改三样证据、 也不碰 LOGIN_MARKERS 的长度门，所以它没走到这一步。 准确说法是：0029 之后的缺口，机制与它当时描述的那条同源。 本轮不是翻案，是把那条 ADR 指出的机制在另一个入口上兑现。

还没核实的：那 7 份存档里的正文长度是按去标签估的（真 inner_text 会更长）， captcha 是照存档 DOM 判的——两处都有约三倍余量，但不是真浏览器里量的。 另外，真实浏览器上「正文命中而页面又自己恢复」的频率没有样本，所以不宣称它必然挂住。

bestseller_monitor/stop_request.py:517 · :520 · :524 · :435 · :444 · :541 · :366 · bestseller_monitor/db.py:790 · docs/ui_live.html:282

Before · 一个自称可重试的相，只走一次

:435 的 GONE 短路 先于 :444 的 deadline 判定执行。 走到 close_browser 的前提正是「进程已证死」—— 于是下一次 tick 必然落到这条短路上。

After · 声明的重试有主体

cleanup_pending 从「只展示」变成「真重试」： interface（相 + retryable）与实现第一次一致， 而那条本来还能定位浏览器的精确绑定，活到重试成功之后。

Problem

_force 里唯一产出 CLEANUP_PENDING 的浏览器分支， 前提是进程已被证明退出；下一次 tick 因此必然判 GONE 并立刻结束窗口。 关浏览器每窗口最多试一次，而 _cleanup_target 反手把 browser_pid / browser_os_started 抹成 CLOSED——那正是唯一还能定位这个浏览器的绑定。 一次瞬时失败留下的孤儿浏览器继续占着 profile 与调试端口（IS-43 的原始症状）， 而界面在同一时刻说「正在重试收尾」。

Solution

给这个相补回它自己声明的那个主体：关系仍是 EXACT（或 A 的 browser binding 仍精确、且无 B 接手）时，tick 对 CLEANUP_PENDING 重试 close_browser；REPLACED 一到就结束旧重试并留警告。 不是把 GONE 当成重试的终点。

  • locality：「失败后怎么再试一次」从「无处」收回 StopWatch 一处
  • depth：相的 interface 与实现一致
  • 精确绑定活到重试成功，孤儿浏览器有主
  • 测试 seam 现成：RecordingStopRuntime.fail_close
承诺写下来了，但没有一条测试碰过它。 .scratch/stop-target/spec.md 的 :37 / :142 / :248 三处把它写成既有规则 （验收第 11 条还专门描述「browser cleanup pending 时出现 B 会停止旧重试」——而旧重试根本不存在）； docs/ui_live.html:282 写着「正在重试收尾」。 全仓 grep CLEANUP tests/ 只命中一条断言：适配器拒关时如实上报， 没有一条驱动过第二次尝试，也没有一条碰过替身上的 fail_close。
一处口径要收：stop_request.py:366-368 确实把 CLEANUP_PENDING 列为 retryable， 但这个字段生产里无人读——gui.py 那几处 "retryable": True 是它自己硬编码的，界面只按 stopping == "cleanup_pending" 出文案。 所以承诺的来源是规格与 UI 文案这两处，不是这个字段。
实跑（替身推时钟）：RecordingStopRuntime(fail_close=True) → tick 1 得 cleanup_pending / browser_close_failed， tick 2 直接回 IDLE； actions 记的是 [bind, terminate, close_browser, release]—— close_browser 只出现 1 次， 而 crawler_process 行已被删掉（浏览器事实先被写成 CLOSED）。 另一条进 CLEANUP_PENDING 的路（:529-537，DB 出错那条） 确实会重试——所以问题只出在关浏览器这一条上。 常态配置 config.toml:52 start_browser = true，所以这里真有浏览器可留。

Problem

reraise 从 begin_detail_visit 的形参， 经 ReadyDetailVisit 的冻结字段，再进 _read_raw_html， 在 7 处写成同一句没有作用的 except。 它的取值对任何输入都不改变结果——和候选 02 那次撤掉的 punished 形参是同一种形状，只是更宽：那一个穿五个 module， 这一个还额外把一个 import 环引了出来。

Solution

整条线撤掉：形参、冻结字段、_read_raw_html 的形参、7 句 except，以及 click_listing 那句延迟 import 与 pipeline 侧多出来的那个实参。 停止异常仍然原样上抛——它本来就是这样。

  • interface 变窄：两处形参 + 一个冻结字段消失
  • import 环消失：延迟 import 那句消失
  • 测试不再为保住机制而造异常类
  • deletion test 通过：删掉它，复杂度不挪给任何调用方
它的作用域比那 7 句还大，而且它只在一件事上有效。 复核时把一个同时落在两个集合里的 class WeirdIO(PlaywrightError) 传进 reraise： 删那 7 句之前它原样上抛，之后变成 ReadFailedVisit。也就是说这 7 句只在两集相交时才有用—— 而今天不相交，所以它们是惰性的。 对照：pipeline.py:319 是同款 except STOP_WITH_OUTCOME: raise，但后面跟着 except Exception 兜底，那句是活的。 惰性只源于 detail_visit 这一侧的兜底集比停止集窄。 删掉 reraise 等于放弃「万一将来 BROWSER_IO_ERRORS 放宽、或停止分类扩到 OSError」的那份保险——这是取舍，不是纯删。 .scratch/detail-visit-observation/spec.md:88-91 写过原样穿透的承诺， 但没有任何测试钉住这个不变量。
它是被一条测试养着的：test_detail_visit.py:57-68 用自造的 class Stop(Exception) 传进 reraise=(Stop,) 来验证「原样抛出」。而删掉那 7 句之后这条用例照样通过—— 因为 Stop 本就不是浏览器错误，它压根没被拦过。 它锁住的只是「形参还在」，锁不住行为；真正证明这件事的是隔壁那条 （真的六个停止异常、不传 reraise）。删机制就该连它一起删。
顺带作废一条旧论据：.scratch/dead-weight/spec.md:20 曾把 「两处 reraise」当作 STOP_WITH_OUTCOME 有活消费者的依据——本条举出的正是那两处。
