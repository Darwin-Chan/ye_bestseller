四个「等页面」循环收成一个等待原语：条件、上限、取消有一个家

Strong

bestseller_monitor/listing.py:59-70,195-214,73-81 · detail_visit.py:66-98 · browser_pw.py:123-131 · guard.py:250-284 · delay.py:23-34 · stop_request.py:358-359

Before · 四个循环，取消只长在睡眠这一支

listing.wait_until / wait_cards 10–18s，无取消
detail_visit.observe 可读轮询 10s，无取消
browser_pw 等调试端口 25s，无取消
guard wait_for_resolution / delay 分片 有 stop_request.check()

页面等待单次 10–45 秒 > 协作停止 8 秒窗口 →「暂停」在页面等待里几乎必然落成强制停止。

After · 一个原语管四件事

等待原语：条件 · 上限 · 轮询间隔 · 取消钩子

listing 的两支循环
detail_visit 的可读轮询
browser_pw 的端口等待
guard / delay 的等待

取消钩子 → stop_request.check()（与睡眠分片同一判据）

问题：一笔「等页面」的知识（条件、上限、轮询、能不能被打断）在四个 module 各写一份，停止请求只在睡眠那一支被认领。

解法：一个等待原语，四处循环都走它；取消钩子默认接已有的 stop_request.check()。

  • locality：等多久、能否中断收一处
  • leverage：4 循环 + 5 个 wait_cards 调用点
  • 测试：patch time.sleep → 注入轮询与取消
  • 暂停在页面等待内可被认领

证据：stop_request.check() 全仓仅 3 个调用点（delay.py:31、guard.py:252/274）；listing / detail_visit / browser_pw / click_listing 零 import stop_request；约 10 处测试靠 patch time.sleep（test_detail_visit.py:34…）。

ADR：无冲突。ADR-0009 / 0038 只承诺了长睡眠的切片——本条把同一条承诺补到页面等待上。
