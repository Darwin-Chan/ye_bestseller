## 1. 背景与目标

用户提供 10 家 1688 头部店铺；每日（手动触发一轮）在每家店铺内按「销量排序」浏览商品列表，每家店只翻前 10 页（每页 30 个商品，不足 10 页则全量），进入列表中的每个商品页采集全部 SKU 的编号/规格/库存/价格等字段。MVP 目标是验证「真实浏览器自动化」能否稳定完成「店铺榜单 → 详情快照 → 跨日差分」全流程，为识别畅销品提供数据基础。

成功标准：单账号、单固定 IP；单轮覆盖 10 店 × 每家店最多 10 页；每个店铺的榜单商品独立采集，同一商品出现在多家店铺时重复采集并保留店铺维度，单轮理论上限 10 店 × 300 = 3000 个详情页；页面解析成功率 ≥ 90%；能输出当轮榜单、SKU 库存差分、补货标记、新上榜/掉出榜清单；滑块/登录墙等异常可识别、暂停并人工接管。

## 2. 范围与核心流程

**范围（v0.2.1 做）**

- 输入：用户维护的店铺清单（CSV，含店铺名与店铺 URL），默认 10 家；
- 店铺榜单：用浏览器打开每家店铺的商品列表，切到「销量排序」；
  - 每家店最多翻 **前 10 页**；
  - 列表按 **每页 30 个商品** 计，10 页 × 30 = 最多 300 个商品；
  - 若不足 10 页（或末页不足 30 个）则全量抓取；
  - 记录每店实际翻页数与商品数；
- 详情采集：对榜单商品逐一打开详情页，抓取 **商品 URL、商品名称、SKU 名称、SKU 价格、SKU 库存量**（参考实际页面版式）；
- 店铺维度保留：同一商品若出现在多家店铺，当前 MVP 不做跨店去重，也不做跨店合并，按「店铺 → 榜单商品 → SKU」分别记录；跨店去重/合并留到 v0.3+；
- 存储与导出：SQLite 存原始数据；每轮导出 CSV，并生成 Excel 对账；
- 容错：断点续跑、失败重试、滑块/登录墙暂停等人；
- 差分：与最近一次「完整完成的上一轮」同商品 SKU 库存对比，并统计榜单排名变化。

**不做（v0.3+）**：3 账号并行、多 IP 轮换、自动定时、关键词/站内搜索选品、网页看板、相似 SKU 自动聚合、成交/销量字段采集（除排序本身外）、跨店去重与跨店合并、消息推送。

**核心流程**

1. 手动双击启动脚本，读取 `shops.csv`；
2. 复用单账号持久化浏览器登录态；会话失效则等待人工扫码/滑块；
3. 逐店处理：打开店铺商品列表 → 点击「销量排序」→ 翻页收集商品链接与榜内排名；
   - 最多翻到第 10 页；每页解析全部在售商品；
   - 页面不存在“下一页”或页数用尽即停止，按实际数量记录；
4. 对每家店的榜单商品逐页打开详情并抓取 SKU 数据；不做跨店去重，同一商品在多店出现时按店铺分别采集；
5. 遇滑块/登录墙：暂停该通道，人工处理后继续；失败商品重试 ≤ 2 次；
6. 整轮完成（或人工中断后下次续跑完成）后执行差分与导出，提示查看结果文件。

## 3. 输入、输出与数据设计

**输入 `shops.csv`（示例）**

```
shop_key,shop_name,shop_url
A01,XX日用百货旗舰,https://xxx.1688.com/
```

**榜单抓取参数（默认）**

- `list_max_pages_per_shop = 10`
- `list_items_per_page = 30`（用于估算；实际以页面渲染结果为准）
- `detail_requests_daily_cap = 3000`（跨店不合并，重复采集计入同一上限）

**SQLite 核心表（字段约定）**

- `rounds`：round_id、started_at、finished_at、status（进行中/完成/中断）、覆盖店铺数。
- `shop_rounds`：round_id、shop_key、list_pages_read、offer_count、list_status（待处理/完成）。
- `shop_offers`（榜单快照）：round_id、shop_key、rank、offer_id、list_title、list_price（列表页可见时记录）、是否在榜。
- `products`（详情主档）：offer_id 主键、product_url、product_name、首次发现时间（不承担跨店合并职责）。
- `snapshots`（SKU 快照）：round_id、shop_key、shop_url、shop_name、offer_id、product_url、product_name、sku_id、sku_name、sku_price、sku_stock、collected_at、stock_delta、page_status；保留 shop_key/shop_url/shop_name 以便未来做跨店合并，当前 MVP 直接按行记录、不合并同轮重复项。
- `stock_delta = 本期 sku_stock − 上期 sku_stock`（负值表示减少，用于估销；正值或出现的新 SKU 标记疑似补货）。差分按需实时计算，不单独落表。

**导出文件**

- `data/shop_offers_YYYYMMDD_HHMMSS.csv`：各店榜单快照（含每店实际页数）；
- `data/snapshots_YYYYMMDD_HHMMSS.csv`：SKU 全量快照；
- `output/日报_YYYYMMDD.xlsx`：Sheet1 店铺榜单（店/排名/商品）；Sheet2 SKU 库存差分（上期/本期/变化）；Sheet3 商品级汇总；Sheet4 疑似补货；Sheet5 新上榜/掉出榜；Sheet6 失败与待人工清单。

**采集字段口径**

- 单条快照记录字段：商品 URL、商品名称、SKU 名称、SKU 价格、SKU 库存量、店铺 URL、店铺名称、本次采集时间（collected_at）、距离上次抽取时间的库存量变化（stock_delta）。
- 商品 URL 与店铺 URL 只保存链接，不下载文件；Excel 中以可点击链接展示。

## 4. 反爬、容错与运行约束

- 有头真实浏览器、单账号独立 profile；所有节奏与延迟均走配置文件，禁止代码内硬编码固定值；
- **拟人化随机延迟策略（默认值可配置）**：

  | 位置 | 默认策略 | 说明 |
  |---|---|---|
  | 详情页之间 | 基础 5-9 秒，均匀随机 | 避免固定间隔；可在 4-8 秒基础上放宽 |
  | 每 8-15 个详情页 | 偶尔插入 15-30 秒停顿 | 制造自然间歇 |
  | 每约 200 页 | 休息 30-90 秒 | 打破长距离匀速 |
  | 翻页 / 点击排序前 | 1-3 秒随机等待 | 模拟寻找与点击动作 |
  | 页面加载完成后 | 停 1-2 秒再取数据 | 模拟读取页面 |
  | 失败重试 | 指数退避 + 随机抖动（5 秒起，×2，再加 0-3 秒随机） | 避免失败后立刻同节奏重来 |
  | 商品访问顺序 | 榜单顺序打乱后再访问 | 避免固定从第 1 名到第 300 名 |

- 抖动原则：采用「宽区间随机 + 大间隔」，不做「固定间隔 + 微小噪声」；延迟目的是改善访问节奏与行为真实性，而非单纯拉长单轮时间（3000 页按平均 6 秒约 5 小时），若需控制时长可压低页均到 4-6 秒并用批量休息补真实感；
- 作用边界说明：随机延迟降低「被行为识别」的概率，不根除由单账号、单 IP、单日请求量累积导致的滑块触发；需与「低并发、单账号、低频、数据仅自用」设计配套。
- 估算量级：10 店 × 最多 10 页列表（约 100-150 个列表请求）+ 最多约 3000 个详情请求（同一商品在多店出现会重复采集，同样计入该上限）；单轮预计 4-7 小时，允许中断续跑；
- 每轮为独立 round；未完成轮不参与差分；差分仅比较「两轮均完整抓到的同 (shop_key, offer_id, sku_id)」；
- 榜单语义：每轮按当日在榜前 10 页采集；不在前 10 页的商品当轮无详情快照，在 Sheet5 中标注「今日不在榜前 300」；
- 失败率/异常页占比超过 10% 时整轮暂停，提示人工决策，不自动重试循环；
- **同日去重跳过（按商品名，点前判断）**：`list_title`（列表页商品名）点前可读，故以 `inventory` 的 `(shop_key, product_name, 当日)` 是否存在判断；存在则该商品**在点进详情之前**即跳过（不弹窗、不读 SKU、不写快照），单商品可省一次弹窗加载（约 1 秒+）。若列表名取不到（空串），则回退到 `(shop_key, offer_id, 当日)` 弹窗后判断；详情阶段对已跳过商品补写一条 `page_status='成功'` 快照，避免计入失败或重复待处理。注意：按名称匹配对“同店同名商品”可能误判，需以同店数据可接受为前提。
- 运行机器为当前 Windows 电脑，日志不含 cookie/密码；浏览器 profile、数据库、导出文件加入 `.gitignore`；
- 风险声明：本方案属未获 1688 许可的自动化采集，单账号低频仍可能触发账号风控，数据仅个人研究使用。

## 5. 验收、里程碑与待补充信息

**验收场景**

- 离线：用录制的店铺列表页与详情页 HTML fixture 验证解析器；
- 小规模实测：真实账号跑 1 家店前 2 页（60 个商品），验证「销量排序 → 翻页 → 详情抓取 → 差分导出」；

- 安全：日志与仓库无敏感信息；中断后续跑、失败清单与补货标记均正确。

## 6. 当前延迟与节流参数（2026-09-04，均可在 config/config.toml 调整）

**配置驱动（拟人化随机延迟）**

| 项 | 参数 | 当前值 | 说明 |
|---|---|---|---|
| 商品/详情页之间 | `detail_delay_sec` | `[0.8, 2]` 秒 | 连续商品（点卡片进详情 popup）之间随机延迟 |
| 长停顿触发频率 | `long_pause_interval` | 每 `[12, 20]` 个商品 | 到达后插入一次长停顿 |
| 长停顿时长 | `long_pause_sec` | `[10, 20]` 秒 | 模拟自然间歇 |
| 批量休息 | `batch_size` / `batch_rest_sec` | 每 `300` 个，休 `[20, 40]` 秒 | 单轮很长时用 |
| 列表页之间 | `list_delay_sec` | `[1.5, 3]` 秒 | 翻页/加载更多之间 |
| 点击/操作前 | `action_delay_sec` | `[0.6, 1.5]` 秒 | 模拟找按钮 |
| 页面加载后读取前 | `read_delay_sec` | `[0.8, 1.5]` 秒 | 模拟读页面 |
| 失败重试退避 | `retry_base_sec` + `retry_jitter_sec` | `5` × 2^(n-1) + 随机 `[0, 2]` 秒 | 失败后不立刻同节奏重来 |
| 人工介入 | `human_pause_minutes` | `10` 分钟 | 持续响铃直到解决，超时安全暂停 |

**固定/页面加载等待（多在驱动代码内，未配置化）**

- 浏览器启动等待：约 `8` 秒；`page.goto` 后等待 `4` 秒；滚动触发懒加载每步约 `1.2` 秒；翻页/返回后约 `2` 秒；每条商品处理前约 `1` 秒。

说明：

- 所有“拟人化”延迟都走 `Humanizer`（`bestseller_monitor/delay.py`），区间随机、不宜用固定值。
- `before_detail`（商品间延迟）与 `list_delay`（列表页间）是当前起效最频繁的两个；`action_delay` 已定义但当前路径暂未额外调用。
- 人工介入时响应间隔约 `3` 秒，反复播放火警式音效，直到验证元素/验证页消失才停止。

## 7. 事件日志与延迟×验证关联分析（v0.3）

目的：为“验证触发原因”提供可量化数据。在抓取链路的每个关键步骤记录“时间戳 + 与上一完整事件的间隔”，并在滑块/物品识别/登录墙出现与解决时记录验证事件；积累足够数据后用脚本统计“间隔分桶 × 验证触发率”及相关性，反推 `config.toml` 应如何调延迟。

**新增表（与主数据同库 `data/bestseller.db`）**

- `event_log`（只追加，不更新不删除）：`round_id / shop_key / offer_id / sku_id / phase(listing·detail) / event / kind(delay·work·verification) / ts(UTC，含微秒) / prev_ts / interval_ms / verification_type(slider·item_captcha·login·none) / attempt / config_hash / note`。`interval_ms` 为相对同一 `(round_id, shop_key)` 上一条事件的毫秒间隔，首条为 NULL。
- `run_params`（按参数散列幂等，仅参数变化时新增）：`params_hash UNIQUE / captured_at / config_json`，保存本轮生效的延迟/反爬参数，便于追溯“哪天用了哪组配置”。

**埋点事件（`bestseller_monitor/browser_pw.py`）**

- 列表阶段：`list_load / list_sort / list_page / product_open / popup_open / detail_parse / popup_close`。
- 详情阶段：`detail_nav / detail_parse / detail_fail`。
- 验证：`verification_appear`（在 `intervention_kind` 判定需人工介入时记录，带类型与出现时刻）与 `verification_solved`（`_resolved` 为真时记录，note 记 `resolution_seconds`）。

**分析脚本（只读，`python tools/analyze_delay.py [--round N] [--chart]`）**

- 输出：按 `interval_ms` 分桶（`<0.5s / 0.5-1 / 1-2 / 2-3 / 3-5 / 5-10 / >10s`）的“桶内事件数/触发数/触发率”；`interval_ms` 与“下一步是否验证”的 Pearson + Spearman 相关系数；渠道内累计序号与触发相关性；按轮次/店铺/阶段/验证类型/北京时间小时分组。
- 产出：`output/延迟分析_YYYYMMDD_HHMMSS.txt`（报告）+ `.csv`（聚合），`--chart` 可生成柱状图（需 `matplotlib`）。
- 分析为“描述 + 相关性”，不做回归/预测模型。

说明：`verification_appear` 的 `interval_ms` 即“触发前一步到验证出现的间隔”，是判断“多快触发滑块”的直接指标；长间隔（长停顿/批量休息）会落入 `>10s` 桶，用于观察“休息后是否更容易触发”。
