# 0043. 分析运行与窗口：关窗＝真的停下，锁的寿命＝运行的寿命

- 状态：已接受（2026-09-23；票面与提交哈希见 `.scratch/matching-progress/issues/03-close-window-is-stop.md`）
- 日期：2026-09-23

## 背景

分析线的票 14 把「窗口锁」与「运行锁」合成了一把 `Local\bestseller_analysis`：锁取在
`analyze.py` 的 `main()` 里，放锁排在 `finally`。合锁的前提是「窗口与运行同生共死」，但
实现里窗口的寿命只到 `webview.start()` 返回（用户关窗那一刻），运行的寿命却到判断跑完
——判断在 HTTP 请求线程起的后台线程里跑，窗口关了它照跑，进程靠退出时 join 线程池工人
续命。于是**锁比工作先放**。

2026-09-23 17:51 那趟实测到了两条后果（全部证据在 [ADR-0044](0044-visible-progress-and-stop-for-long-judgment-runs.md) 的背景节）：

- 关窗即放锁，第二个实例拿得到锁、起来写同一份判断缓存，撞上 `database is locked`，
  第二次启动只看到「读取库存数据失败」；
- 关窗那一刻判断还在跑：305 条判断全部落库（钱没白花），但装配、推荐快照与页面响应
  都没发生，这一趟的结果没了；收尾瞬间请求线程被冻住，日志里「有 summary、无装配完成」。

这条坑 ADR-0008 点过名：采集线「界面不持有采集锁。否则关掉界面会释放采集锁而采集还在
跑。两把锁必须分开，这是实现时最容易踩错的一脚」——分析线那一脚正踩在它上面。区别在
处置：采集线把两把锁分开（关窗不打断采集、重开接上）；分析线选 F1——**关窗＝真的停下**
（ADR-0044 决策 4），于是「锁与工作同寿命」不需要两把锁也能成立。

判据：`.scratch/mutex-diag/repro_lock_short_window.py`（现状 RED：关窗后 0.5 秒第二个
实例探同一把锁即 ACQUIRED；把放锁推迟到收尾之后 GREEN），已转正为
`tests/test_analyze_entry.py` 的探针回归测试（对照臂＝放锁排在收尾之后）。

## 决策

**1. 关窗＝真的停下（F1）。** 窗口关闭事件挂 `closing` 钩子（pywebview 的 closing
处理器返回 False 即吞掉这次关闭；winforms 平台在 GUI 线程上同步调它）。匹配在跑时先弹
**原生确认框**（`MessageBoxW`，MB_OKCANCEL 形态，缺省焦点给「取消」）：「取消」＝吞掉
关闭、匹配照常；「关闭并停止」＝走与遮罩上「停止匹配」**同一个停止入口**
（`service.request_stop`）。

**2. 窗口留在「正在停止匹配…」态，直到收尾完成。** 确认之后钩子吞掉这次关闭，把
「`request_stop` → `wait_terminal` → `window.destroy()`」交给一个后台线程：GUI 线程不
在钩子里长等（不然整窗假死，Windows 5 秒后还会把它标成「无响应」）。收尾期间页面照常
轮询——进度读数绕开服务锁（ADR-0044 决策 2），「正在停止匹配…」因此是真的在动。收尾
完成后 `destroy()` 自己再过一次 closing，这次由钩子内部的标志放行。

**3. 锁的寿命＝运行的寿命。** 放锁仍在 `main()` 的 `finally`，但 `_open_window` 要等
窗口真的关了才返回，而窗口要等 `wait_terminal` 返回才关——放锁因此天然排在最后一次写入
之后。不拆两把锁（那是 F2 的结构，本次不做）。

**4. 兜底：关窗那一瞬才受理进来的运行。** 点 × 的同一瞬页面可能正好发出开始分析——
关窗检查看到「没有运行在跑」，等它登记进来时窗口已在关。这条夹缝由出口处兜住：
`server_close()`（会 join 完处理线程，之后不会再有新运行登记）之后、放锁之前，把还在
跑的运行停下、等它停写。窗口这一刻已经不在了：这趟的结果会没（与从前一致），但进程
不再带着没停的写入退出。

**5. 没有匹配在跑时关窗行为不变**：无确认框、直接退出 0；`--serve` 不受影响（无窗口，
不挂钩子）。

**6. 确认框的措辞取自原型，两处补充。** 正文前两段照原型「关窗确认」抄；原生 MessageBox
的按钮是系统标签（确定/取消），末行补按钮图例（「按「确定」＝关闭并停止匹配；按
「取消」＝继续匹配。」）；还没到逐对判断、或已经判完时报当前阶段（「当前在「冻结库存
数据」。」），不硬报 0/0 对。`BESTSELLER_NO_DIALOG=1`（与 `_notify` 同一约定）不弹窗、
按「关闭并停止」算——自动化场合没人可点；框弹不出来时按取消算（没问成就别关）。

**7. 钩子可重入。** 原生确认框跑在自己的嵌套消息泵上：框还开着时窗口的关窗消息会再进
一次钩子。钩子带一个「框开着」标志，重入只吞掉那次点击，不叠第二个框、不叠第二条收尾。

## 取舍

- **关窗最多多等一个模型超时（30 秒）**：等的是在途判断自己回来——这一等不设调用超时
  （设了要么白等一场、要么提前放锁重演旧坑），上界来自停止机制自己的在途超时
  （读数里的 `stop_timeout_sec`）。这段时间窗口留在「正在停止匹配…」态而不是立刻消失；
  换掉的是「窗口没了、进程还在、再开还说已经在跑」的困惑态。
- **遮罩上点过「停止匹配」之后点 × 仍会弹一次框**：不弹就等于静默丢弃这一趟还没保存的
  结果——「关窗拦一次」的代价原则对这条路径同样成立。
- **确认框缺省按钮是「取消」**：关窗丢的是这一趟结果，别让回车顺手关掉。
- **兜底那次收尾是看不见的**（窗口已关、过程在后台走完）：只保锁的纪律，不保结果。

## 没动的（挂账）

- F2（关窗后台继续、重开接上）与随之需要的「窗口锁＋运行锁」两把结构（ADR-0044 已挂）。
- `--serve` 下 Ctrl+C 的放锁时机：维持 `_serve` 返回即放锁的旧样；同一条夹缝（刚受理
  的运行）在 `--serve` 里仍按旧样放锁，见「取舍」。
- 收尾的读秒或进度展示：窗口里那句话是页面在说，不是钩子在说。
- 真机未执行：原生确认框的实际弹出与「正在停止匹配…」态的实机观感（本机测试全走假
  webview + 假确认框的缝）；待人工开一次程序、匹配期间点 × 走一遍。

## 结果与代价

- 关窗从「窗口消失＋锁即时释放」变成「请求停下 → 等收尾 → 关窗 → 放锁」，`analyze.py`
  多一个钩子、一个确认框与一条后台收尾路径；
- 收尾期间第二个实例照旧被锁拒之门外，而提示路径能真的把窗口叫到前面（窗口还在）；
- 判断缓存从 `wait_terminal` 返回起不再被写（票 02 的契约测试），锁的释放排在它之后
  （票 03 的探针回归测试）。

与 [ADR-0044](0044-visible-progress-and-stop-for-long-judgment-runs.md) 互引：0044 定
「关窗＝真的停下（F1）」与 `wait_terminal` 的硬语义（决策 4、5），本条定它的落地形状
（钩子、确认框、放锁时机、兜底）；两条共用一份规格与原型，实现分属两个会话。
