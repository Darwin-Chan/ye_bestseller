## 背景

交换区现在只搬**采集观测**：交换集是六张表（`shops`、`inventory`、`products`、`skus`、
`product_information_versions`、`product_image_assets`），模型判断缓存（`matching.cache`）与
人工决定账本（`analysis.store` 里那三张 `manual_*`）是各机本地的，从不外发。后果有两条：
别的机器要在同一批数据上得到同样的同款分组，得**自己再付一遍模型钱与时间**（m4 实测一次
分析约 1982 次模型调用、约一小时）；人工确认过的同款组在每台机器上要**各确认一遍**。现状里
「两台机器结果一致」的支点是数据收敛 + 各机重跑——同一份数据各跑一次分析，对一眼。

这件事值得做的底子，是判断数据的形状本来就适合搬运：

- **判断绑证据版本**：对级判断的键是版本对的内容摘要（`version()` = 名称 + 图片哈希），
  内容寻址、跨机可复现；账本的成员也随身带版本。分析快照与报告里用的版本行号 id 不跨机
  稳定（汇总会重排），但那不是判断的键。
- **结果里已有署名**：`judgments.result` 里有 `model`、`provider`、`vision_model`、
  `rule`——判断是**带署名的意见**，不是事实：同一对证据版本，不同模型或规则版本可能给出
  不同结论。人工决定则不同：它是**决定**，重做一次的成本是人的注意力。
- **判断本身没有来源**：`judgments` 没有时间戳、没有机器列；账本只有 `saved_at`。
  ADR-0031 决定「来源留在包这层、不加行级来源列」——那是对**观测**的裁决，判断与决定
  不吃这一条（理由见决策 6）。

## 决策

**判断集单立通道与语义：模型判断按署名并存、本机只消费同署名；人工决定不冲突即生效、
冲突一律回到人面前。**

1. **判断集与交换集并列**：模型判断缓存、视觉描述缓存、判断证据索引、人工决定账本合称
   「判断集」（词条在 `CONTEXT.md`）；`recommendations` 只写不读，不搬。
2. **通道独立**：每台生产机一个 `judged-<机器>` Gitee 私有库（镜像 `raw-<机器>` 的
   「各写各的」），clone 在交换区根下、复用 `git_channel.GitChannel`。发布形态是按批次的
   `.db.gz`，**身份 = 内容 SHA-256**：同内容重发是空操作、重复收取幂等（与周包同规）。
   判断集里没有图片字节——导出剥掉 `evidence.image_data` 这个只写不读的列；图片证据仍走
   COS，两条通道各管各的。
3. **凭据档位修订**：「纯汇总机只持只读凭据」修订为**只约束采集通道**（`raw-*` 与 COS）；
   判断库各写各的，与角色档位无关。不改这条，转角色后的 m4——恰好是分析的生产者——就
   只能收不能发。
4. **意见并存**：模型判断按 `(版本对, 署名摘要)` 并存（署名摘要 =
   `provider`+`model`+`vision_model`+`rule` 的摘要）；本机消费只认同署名（等于缓存命中），
   异署名只作参考、不驱动本机分组。为让并存成立，`judgments` 主键从 `pair` 扩成
   `(pair, 署名摘要)`。
5. **决定冲突暴露**：外来人工决定不冲突就自动生效（非冲突的并入本机账本）；冲突**不自动
   裁决**——进冲突账、回到人面前。账本里「未确认」的行不搬：撤回是本机的中间态，搬过去
   只会制造伪冲突。
6. **来源列**：`judgments` 与 `manual_*` 加来源机器列（只作显示、不参与键；判断行记第一次
   收到的来源）。**这破了 ADR-0031「不加行级来源列」的例**，理由写在这里：观测的来源能靠
   包重建（谁发的包就是谁的），而决定与判断的来源是**结论本身的一部分**——页面上要看得出
   「这条是谁在哪台机器上确认的」，冲突说明也需要它。
7. **触发与节奏**：交换台里两个独立动作「发布判断集」「收取判断集」，默认整趟包含、可
   单独跑；**不做**「跑完分析自动发布」——交换台是手工触发的独立小工具。
8. **两条通道互不设先后**：判断先到就闲置待用，版本引用等数据到了自然生效；找不到商品
   不报错（与账本「认领缺席成员」同规）。
9. **呈现分工**：交换台周报如实记账（收到谁的判断集、采纳几条、冲突几条）；分析页面负责
   裁决（冲突组落回待确认，并标出来源）。

## 没动的（挂账维持）

- **判断质量与署名治理**：换模型 = 换署名，旧署名的判断自然不再被消费；「旧署名要不要
  清、什么时候清」这条 ADR 不管。
- **不做中心索引与常驻同步**：判断集是私有库 + 各机手工收取，与交换区同规；机制文档
  「本期不做」清单不变。
- **`recommendations` 仍只写不读**：搬不搬它、要不要退役，是另一件事。

## 结果与代价

- **收益**：一台机器跑出的判断与人工确认，在别的机器上直接可用——同批证据版本的模型
  调用可归零，人工确认不再逐机重做。
- **代价一**：判断从此有两种来源，页面与报告要能说清「这条从哪来」（来源列 + 周报记账
  两处一起做才算数）。
- **代价二**：新增每台生产机一只私有库与一条凭据规则修订——上机向导/清单要多一步：建库 +
  该机可写自己那本、其余只读。
- **代价三**：破 ADR-0031 的例只针对判断与决定；将来观测若也要行级来源，得另写一条 ADR，
  不能拿这条推。
- **挂账（要单开票）**：判断缓存的持久性。2026-09-22 晚实测：1982 次调用跑完，进程退出时
  事务未提交、整体回滚，判断一条不留（journal 头完整即可判未提交）。判断集要以**已提交的
  判断**为搬运对象，所以「判断缓存增量提交」是这条路线的前置票。

## 验收判据（草案，落地时进票据）

1. **省钱路径**：m1 跑分析产出判断 → 发布 → m4 收取 → m4 对同批证据版本跑同一区间：
   模型调用为 0，页面状态行与 m1 一致（期间新增/变更的商品照常判）。
2. **决定搬运**：m1 确认一组 → m4 收取后该组已是已确认组，周报记「采纳 1 条（来自 m1）」。
3. **冲突暴露**：两台对同一对商品给出相反的人工决定 → 各自收取后冲突进冲突账、周报点出、
   分析页面把它落回待确认并标出来源。
4. **幂等**：同一判断集重复收取两次，账本与缓存不变。
5. **顺序用例**：判断先到、数据后到（或反之）——先到的判断闲置待用不报错，数据到齐后
   在分析里自然生效。
