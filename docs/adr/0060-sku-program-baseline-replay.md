# ADR-0060：SKU 程序基线的缓存回放边界

- 日期：2026-10-23
- 状态：已接受（研究阶段设计与只读实现已完成）
- 依据：[SKU 维度同款分组研究继续：缓存与回放核验](../research/SKU维度同款分组研究继续-缓存与回放核验-2026-10-23.md)、`.scratch/sku-grouping-research-update/spec.md`

## 背景

本轮研究需要在人工参照组开始前展示当前 SKU 流程的真实上下文。样本包有 34 个候选集，但当前运行库没有 SKU 判断、SKU 推荐或 SKU 导入缓存；已有商品级缓存的成员身份只有店铺与商品编号，不能补出 SKU 判断或 SKU 程序分组。现有商品级回放器也只消费商品级候选、判断边和组装逻辑。

如果把候选来源、商品级缓存或缺失的 SKU 判断解释成“程序暂时独立”，会把抽样输入、缓存缺失和程序结论混为一谈，也会污染后续人工参照组。另一方面，未来可能需要用当前固定配置实际运行 34 个候选集，但这会产生新的模型调用、费用和缓存结果，不能悄悄混入只读回放。

## 决定

### 一、候选输入边界由样本包固定

`sets.csv` 和 `members.csv` 定义此次基线的唯一候选输入边界。每个候选集只处理其 `set_id` 下的成员，成员身份使用店铺、商品编号和 SKU 编号。候选来源只记录抽样来源，不扩张候选集合；样本包字段作为展示主数据。

运行库只用于查找 SKU 缓存结果、验证证据版本以及取得生产回放所需证据。缺少成员或证据版本不匹配时报告缺失，不从相邻日期、同商品其他 SKU 或商品级缓存补齐。26–50 层跨商品候选集继续按候选集处理，并标记为跨商品构造，不解释为真实同款组。

### 二、区分两种程序基线

- **缓存程序基线**：从已有 SKU 判断、SKU 推荐缓存和可验证证据回放得到的结果。它可以是完整组装，也可以只包含明确标注为可安全回放的部分。
- **固定配置运行基线**：使用当前模型、提示词、证据格式和固定分析配置实际运行 34 个候选集得到的结果。它是独立阶段，必须单独记录真实调用、token、费用和耗时。

本 ADR 只规定两者的边界，不授权固定配置运行。

### 三、缺少 SKU 缓存使用明确状态

基线报告使用以下状态，不把缺失改写成程序判断：

- `no_sku_cache`：SKU 缓存表为空，或缓存库无法提供任何 SKU 结果。
- `candidate_set_cache_miss`：全局存在 SKU 缓存，但当前候选集没有命中。
- `evidence_unavailable`：缓存有结果，但当前样本证据版本无法验证，不能安全回放。

这些状态下，成员级程序组、判断结果、推荐结果保持空值，并在状态和备注中说明原因。模型未判断、缓存缺失和证据不可用都不等于不同款，也不等于程序暂时独立。缓存摘要同时分别记录 SKU 判断行、SKU 推荐行、当前配置署名命中行，以及证据和缓存表的存在性、列名和行数。

非空 SKU 缓存只有在样本成员显式提供生产 `evidence_version` 时才允许验证缓存键；展示字段不能冒充生产证据快照。若证据版本缺失，候选集使用 `evidence_unavailable`，并记录未验证成员数量和身份。

如果一个候选集只有部分成员具备可验证证据，候选集整体使用 `evidence_unavailable`；报告额外记录缺证据成员数量和身份。已有的有效判断边可以逐条展示，但缺证据成员的判断字段保持空值，不能把候选集标成完整回放。

### 四、回放必须复用生产 SKU seam

基线工具复用生产 SKU 的身份、编码合法性和人工约束、缓存键与规则版本、推荐语境与结果解析、以及在证据足够时的组装和刷新逻辑。工具不复制研究版的召回、边读取、编码或组装算法。

商品级候选、商品级判断边、商品级组装和商品级推荐快照不能直接套到 SKU 样本。若缺少完整分析快照而无法安全完成生产级组装，只报告无法取得 SKU 程序基线，不构造近似分组。

### 五、输出采用成员表加报告分工

`program_context.csv` 保持成员级，一名成员一行，记录当前程序组、判断状态、推荐状态、分数或置信度和缺失说明。候选集级汇总、分层汇总、候选边、命中、推荐、调用成本、版本和跨商品构造标记写入独立 JSON 报告。

第一阶段的报告必须能区分候选规模、候选来源、缓存命中、已判断边、推荐状态、缺失原因、代码版本、配置版本、缓存库摘要和生成时间。候选边数明确按样本包成员的两两组合统计，并记录该统计口径。没有调用时，候选集级和报告级的调用次数、token、费用和耗时字段明确表示为零或不可用的原因。

### 六、回放阶段只读且零新增模型调用

缓存程序基线提取和离线回放不写 `matching.sqlite`，不创建新的 SKU 判断或推荐缓存，不调用 LLM。未来固定配置运行必须作为单独工单和独立授权阶段，只能跑这 34 个候选集，固定当前模型、提示词、证据格式、`candidates=6`、`min_score=4` 和并发配置，不做参数搜索。

## 取舍与后果

- 只把已验证的 SKU 结论展示给人工，避免商品级缓存和候选来源污染人工真值；代价是当前没有 SKU 缓存时报告会明确显示缺口，而不是给出完整程序分组。
- 把缓存回放与固定配置运行分开，便于审计真实成本和版本；代价是需要后续单独授权和记录一轮小规模模型运行。
- 复用生产 seam，避免研究工具与生产规则漂移；代价是生产快照不足时必须报告无法安全回放。
- SKU 判断缓存的可查询键不保存历史成员身份或证据版本索引；当前 key 未命中时，报告只能说明“当前 key 未命中”，不能进一步区分旧证据版本与从未缓存。样本证据本身缺失仍单独报告为 `evidence_unavailable`。
- 保留成员级 CSV 与候选集级 JSON 两种输出，兼顾人工展示和可审计汇总；代价是需要维护两者的字段和版本一致性。

## 验收边界

本 ADR 的实现必须能够对 34 个候选集逐集报告缓存状态、成员状态、候选来源、边统计、推荐状态和成本字段，并按 1–10、11–25、26–50 分层汇总；必须明确标注 26–50 层的跨商品构造。实现前不得新增 LLM 调用或写运行库。

本 ADR 不决定 `candidates`、`min_score`、模型、提示词或编码规则的优化结果，不把 80%/80%/10% 测量目标变成上线门槛，也不把候选集或当前程序分组当作人工真值。
