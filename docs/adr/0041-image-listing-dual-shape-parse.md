# 0041. 图片清单按形态双认：表格首列 + URL 行，认不出就报错

- 状态：已接受（2026-09-23）
- 日期：2026-09-23

## 背景

导出侧「桶里已有的跳过」自票 08 上线起在本机从未生效。2026-09-23 在 m4 实测（桶
`bestseller-exchange-1-1493361400`；真机一屏样本落
`.scratch/multi-machine-collection-impl/ticket18/real-listing.txt`）：

- `cos_store.parse_listing` 只认含 `cos://` 的行——那是票 08 写的夹具形态，**零实测样本**
  （票 08 自己注明「coscli 的真机契约留待上机清单第 10 步与票据 12/13 实测」，实测从未回填）。
- coscli v1.0.9（上机手册 curl 钉住的版本）的真实输出是**表格**：数据行首列是裸 key，形如
  `  img/00/<sha>.jpg | MAZ_STANDARD | 2026-09-23T00:51:12+08:00 | "<etag>" | 160.88 KB |`，
  整行没有 `cos://`；末行 `TOTAL OBJECTS:  |      855`。实测走管道取回（无 TTY 差异）。
- 实测 `existing_keys()` 读到 **0** 个，桶里却有 855 个对象（854 张图 + 1 个 key 恰为 `img/`
  的零字节探察物）。
- 后果（`export.upload_new_images` 的 `if ref.key in existing:` 永不命中）：**每趟导出把清单里
  全部图片重传一遍**（`coscli.log` 里 2026-09-22 16:13 起逐条 `Upload …` 记录；09-23 W39
  重发实测重传 854 张 / 145.8 MB），周报「已有 N 张跳过」永远是 0。数据无害（内容寻址、
  同字节覆盖同一对象），是浪费 + 报告失真。
- 汇总侧不在此链上：「只拉缺失」的判据是本机资产表（`merge._pull_images` 按本地已有哈希
  过滤），不经 `existing_keys()`；`exchange` 的检查步只拿它当连通探针、结果丢弃。

## 决策

**`parse_listing` 认两种已知形态、认不出就报错**（都收在 `cos_store.parse_listing` 一处）：

1. **表格首列**（真机实测形态）：`|` 分栏行的第一格是裸 key；表头、分隔行、`TOTAL OBJECTS`
   汇总行的首格够不着 `img/`，自然落空。
2. **URL 行**（票 08 起写下的兼容面）：`cos://…` 行照旧认。
3. **防再静默的闸**：表格汇总行说有对象、却一个 key 都没认出来，抛 `ImageStoreError`——
   宁可按「图片这半没做成事」停下（导出照走、失败如实记进周报与日志），也不再悄悄全量重传。

夹具按真机一屏删节重录（`tests/test_image_store.py` 的 `LISTING`：真哈希换 `H1`/`H2`、行裁到
该屏的前三条、行尾空白割掉，汇总行与分隔行的列位照原样），空桶形态另存样本重录。两份原始
一屏留档在 ticket18：`real-listing.txt`（855 行全屏）与 `real-empty-listing.txt`（空前缀）——
用例钉形态、不钉规模，855 行原始一屏不进用例。回归三条：表格输出出 key（含探察物行）、
`existing_keys()` 对真机一屏非空、汇总行与数据行矛盾时报错。

## 被否掉的方向

- **换 coscli 的可解析输出参数**：v1.0.9 的 `ls` 没有 JSON/结构化输出参数（`coscli ls --help`
  实测；全局旗标里也没有），只有 `--limit`。不可行。
- **只认表格、删掉 URL 行分支**：最简，但把赌注全押在「所有机器的 coscli 都长这一种表格」上。
  m1/m2/m3 尚未上机，别的机器上的既有版本从本机核不了；某台机器形态一旦不同，症状与本次
  缺陷一模一样——静默全量重传。保留 URL 分支的成本是三个小函数里的三行，误认面很窄（要某行
  带 `cos://` 且桶名之后那段以 `img/` 开头）。
- **照旧只认 `cos://` 行、加宽子串碰运气**：形态就摆在那里，不猜。

## 结果与代价

- 真机复核（2026-09-23，修复后）：`existing_keys()` 读到 **855** 个，与 `TOTAL OBJECTS` 一致；
  导出从此只传新增，周报的「已有 N 张跳过」为真数。
- 行为变化（有意）：coscli 输出形态再漂移时，`existing_keys()` 报 `ImageStoreError`——导出把
  它如实记成「图片这半没做成事」（图片这趟不传、包照发），而不再是「认不出 → 照传」。
  两道线都是「停下并如实记」，不再有第三种静默态。
- 探察物 `img/`（零字节）照常算进 key 集：它是桶里真实存在的对象，且永远不可能是图片 key
  （图片 key 形如 `img/<2 位>/<64 位哈希>.<扩展名>`），匹配不受影响。

## 挂账

- **部分漂移不设闸**：闸只在「汇总行有总数、key 零命中」时响；「总数 855、只认出 100 个」这种
  半认出状态不报错（不认识的行按「不是 key」处理是既定口径，半认出仍只多传）。要更严得先有
  样本。
- **桶超过 1000 个对象时 `ls` 是否截断没验**：v1.0.9 的 `--limit` 标注 0~1000，默认值行为未知
  （本次 855 < 1000，分辨不出）。真截断也只是少认 key → 多传，无害方向；桶逼近 1000 前要复验。
- **`img/` 探察物的来历没人认领**：不是向导留下的（向导的探察 key 是 `img/wizard-check-<pid>.txt`
  且用完就删）；多半是上机第 10 步手工验证时传到了 `cos://<桶>/img/` 这个「没有文件名」的路径。
  无害，不追。
