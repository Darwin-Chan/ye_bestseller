# 0031. 跨机合并的胜负由包侧的（采集时刻, 机器）定序

- 状态：已接受（设计定于 2026-09-20，实现未落地）
- 日期：2026-09-20

## 背景

三台采集机各自采自己那份、各自把自己的包收进本机库，最后要收敛到同一份全量库
（地图前提 3）。这要求合并是**顺序无关的确定性运算**：两台机器以不同顺序导入同一批包，
必须算出同一份库。

现有写入路径全部不满足这一点，而且都是**按到达顺序**定的：

- `_upsert_inventory` 对 `(shop_key, offer_id, sku_id, date)` 冲突**七列全量覆盖**，谁后写谁赢；
- `products` / `skus` 的 `first_seen_at` **冻结在首次插入**（谁先插谁的），`last_seen_at`
  被后写者**无条件**覆盖；
- `shops.first_seen_at` 同理。

更硬的是：`inventory` 的主键是 `(shop_key, offer_id, sku_id, date)`，**没有任何时刻列**
（`date` 只是北京日历日）；全库也没有机器标识。两台机器采同一天同一店时，
**行本身从数据上分不出谁更晚**。判据只能由包从外面补进来。

考虑过给观测表加行级 `machine_id` + `collected_at`，实测后否掉：`inventory` 行均负载 126 字节，
两列约 27 字节（**+21%**）；而且这些行经 `analysis.py` 的 `SELECT i.*` 原样进分析快照、
被 `analysis_http` `json.dumps` 推给浏览器，会改掉另一个 effort 的接口形状与体积。
关键判断是：**来源信息本来就在包这一层**——一机一库、`data/<年>/<周>-<机器>.db.gz`、
包元数据含机器标识、历史永久保留。"这一行是谁采的"永远可以从"它在哪个包里"重建，
行级列买到的是**查询便利**，不是信息来源。

## 决策

- **取胜单位是「一个 (日期, 店铺) 的一次采集」**，判据取
  `(该店该日最后一次成功采集时刻, machine_id)` 的**全序**。时刻不单独存：
  它就是该 `(shop_key, observed_date)` 在 `product_information_versions.observed_at` 上的最大值，
  包侧与本机侧跑**同一段推导代码**。本机的采集同样按这个口径算出自己的 claim，
  所以"本机 10:00 采的"不会被"别人的 09:00 包"覆盖。
- **观测表（`inventory` / `product_information_versions`）行级只在键相同时由取胜方整行落库**，
  键不相同的行一律保留（"不重复部分都保留"）。同一个 `(店铺, 商品, 日期)` 上出现**相反粒度**的
  两个观测时**整组取胜**——行级并集会把两种粒度留在同一天，而
  `analysis.py` 遇到同日混合形态直接 `raise ValueError`，会让分析读不了这个库。
  这与既有的 `_clear_other_granularity` 同一条规则。
- **身份表（`products` / `skus` / `shops`）不用「后到者赢」，用交换律合成**：
  `first_seen_at` 取 MIN、`last_seen_at` 取 MAX，描述列（`product_name`、`product_url`、
  `main_image_url`、`sku_name`）按最近一次观测取胜，平局按 `machine_id` 定序。
  它们是跨店共享的身份表而不是观测，物理上 `first_seen_at` 就该是 MIN。
  这一条沿用仓库里唯一的交换律合并先例：`_skus_primary_key_on_sku_id` 迁移的
  `MIN(first_seen_at) / MAX(last_seen_at)`。
- **不给观测表加行级来源列。** 来源留在包这一层；库里若要直接回答"这条是谁采的"，
  那是另一件事，另开一张票。
- **导入一律显式投影列**，不做 `INSERT ... SELECT *`：包的列集与本地不必相同
  （`inventory.diff` 退役后旧包就多一列，`SELECT *` 会直接报列数不匹配）。

## 被否掉的方向

- **行级 `machine_id` + `collected_at`**：见背景。三档方案的判据质量完全一样（都是
  `(时刻, 机器)` 全序），行级多买的只有查询便利，代价却是 21% 体积、采集热路径、
  包格式（要重开已决的票据 03）与分析接口外溢——为雾区里的一条付三处代价。
- **只用包级 `generated_at`（导出时刻）**：判据稳定但语义错——周一采的周五才导出，
  会赢过周四采周三导出的包。它衡量的是"谁想起来导出得晚"。
- **按 (日期, 店铺) 整块取胜**（败方不重复的行也丢）：与"不重复部分都保留"冲突；
  一台机器中途被 deny、预算耗尽或只采了一半时，它的那半会抹掉另一台已经采到的成果。
- **键冲突时逐列补齐**（非空覆盖、空值由败方填）：观测是不可拼接的整体，
  半新半旧的行会让"这条观测是哪一次采的"变成回答不了的问题。
- **重算 `inventory.diff` 来绕开基准问题**：见 [ADR-0032](0032-retire-inventory-diff.md)——
  那一问不是被回答了，是被取消了。

## 结果

- 合并结果**与导入顺序无关**：各机重放同一批包收敛到同一份库。
- 交换集的表结构与包格式**一个字没动**（票 03 已决的结论保持有效）。
- `inventory.diff` 退役之后，合并的正确性**全部压在 `stock` 序列上**。
  分析侧的 `prior` / `fallback` 规则意味着区间起点前最近的那条观测决定首日销量，
  所以"合并时漏了一行"不是"少一行数据"，它会改变分析结果——缺口必须如实报告。
- 冲突（同一 (日期, 店铺) 上两个不同 `machine_id` 的 claim）在本机导入账里留痕，
  报告从账里读。判据确定性保证了"谁赢"在各机结论一致，但"我见过这个冲突吗"
  取决于该机导入过哪些包，所以报告是**本机视角**的。
