# 0006. 中断时的已发现商品必须落库为残缺榜单

- 状态：已接受
- 日期：2026-09-12

## 背景

点击式列表在**遍历卡片的途中**就把商品详情写进快照与库存，榜单行却等到**整店遍历结束**才一次性写入。任何在两者之间离开榜单阶段的路径，都会让已写入的快照找不到对应的榜单行。

第 27 轮（北京时间 2026-09-12）店铺 A01 是最完整的一次现场：该店因 deny 跳店，榜单 0 行、已发现商品数 0，同时本轮快照已有 180 个商品、1038 行成功库存。后果是失败率的分母失真、汇总工具同时显示「榜单 0 个商品」和「成功 180 个商品」，任何以榜单为基准 join 快照的分析都会丢掉当天这批数据。

早先只有详情预算耗尽一条路径做了补救（把已发现商品随异常带出，由调用方先落库）。用对账脚本回看全库：**11 处店铺×轮次、1062 个孤儿商品**，最早出现在第 13 轮——说明这不是某一条路径的疏漏，而是写入顺序本身的问题。

## 决策

- 不变量改由写入侧保证：**商品在列表遍历中被发现的那一刻就写榜单行**，并即时维护该店本轮已发现商品数。整店遍历正常结束时仍用完整榜单整体替换。
- 榜单行因此有两种诚实含义。完整榜单是该店本轮列表的权威快照；**残缺榜单**是本轮在该店已发现的商品集合，只增不减。
- 店铺状态收敛为三态：本轮未开始（`待处理`）、尝试过但没拿到完整榜单（`失败`）、拿到完整榜单（`完成`）。失败态且已发现商品数大于零，即为残缺榜单。
- 榜单阶段的每条退出路径统一收口：店铺 deny 跳店、整轮 deny 中止、跨天中止、人工介入超时、详情预算耗尽都把店铺记为 `失败` 并留下原因；**未预期异常不做状态伪装**——异常照旧上抛，店铺状态不动，数据只靠增量落库保住。
- 没有数据库句柄时只记内存；`shop_offers` **不新增唯一约束**，原语用「先查后写」保持幂等，既有库不需要人工迁移。

## 结果

已发生的孤儿不再产生，历史孤儿不回填、只由只读对账脚本报出。

代价有两处。其一，库里会出现「有榜单行但店铺未完成」的组合，读方必须看店铺状态才知道榜单不完整——这正是 [CONTEXT.md](../../CONTEXT.md) 要定义「残缺榜单」的原因。其二，每发现一个商品多一次写库与计数查询；完整榜单路径仍是单次批量插入，所以只有中断频繁的轮次才会感到差别。

被否掉的替代方案是把读取端改成以快照为准、容忍榜单行缺失。那会把「商品的 rank、列表标题、商品 URL 从哪来」这个不变量散到失败率、补采、汇总工具和两个分析脚本里各处理一遍；榜单行本来就是「本轮发现过这个商品」的事实记录，中断并不否定这个事实，只是它不完整。

相关词汇见 [CONTEXT.md](../../CONTEXT.md) 的「残缺榜单」「榜单状态」；实现见 `Database.remember_shop_offer()` 与 `bestseller_monitor/pipeline.py` 的 `_record_incomplete_listing()`；对账工具为 `tools/check_orphans.py`，工单为 IS-45（IS-46/47/48 分片落地）。
