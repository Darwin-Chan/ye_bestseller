# 0034. 本机定编 m4：过渡期临时采集，采集机角色可退役转纯汇总机

- 状态：已接受（2026-09-22）
- 日期：2026-09-22

## 背景

三机分工定下后，本机的终局是纯汇总机；但三台采集机还没到位，而「采集 → 导出 → 汇总 →
分析」这条真通道需要先跑起来（此前演练用的是本地裸库当 Gitee 替身，真 Gitee / 腾讯云
COS 通道一次都没走过）。于是本机要临时扮演采集机。两件事因此要定：本机取什么编号；
一台先采集、后汇总的机器，换角色要付什么代价。

两条既有事实决定了这个决定的分量：

- **编号是身份**：跨机合并按「该店该日最后一次采集时刻，平局按编号字典序」定胜负
  （[ADR-0031](0031-cross-machine-merge-decided-by-package-claim.md)），编号还写进冲突账与
  取胜方账；改编号但沿用旧库，会出现「自己的组被判成别人的」（本机侧取值优先用账里记的
  编号，与配置里的编号不一致时分叉）。
- **自己的包不收**：交换台不收本机编号那条 raw 库的包（`exchange.py` 的口径）——本机采集史
  只存在于本机库里，换库就没有任何路径把它装回来。

## 决策

1. **本机永久编号 m4**（汇总机编号），m1/m2/m3 留给三台采集机；编号一经定下不再改。
2. **过渡期按采集机跑**：进名册、按计划采本机份额、走真通道导出（含 2026-09-05 起的补发）。
   测试期的观测就是真观测，留在交换区与库里、不特意抹掉——包里自描述（覆盖声明、残缺榜单），
   系统里没有「测试包」这个概念；抹了，那几天在所有人的库里就是永久空白。
3. **转角色那天按序四件事**：名册先撤（在册即份额，先撤免得出现「计划里归本机、但本机已不采」
   的空档周）→ 改配置（`role = merge_only`、两个凭据档位 `read_only`）→ 凭据真换（Gitee 部署
   公钥、COS 只读 AK）→ 行为自证（push 被拒、上传被拒）。代码对所有档位开关不设闸门
   （配置只把档位读进来，没有一处消费方），所以只改记录等于没有判据——档位必须靠行为证明。
4. **库沿用不换**，归档只作备份（`<data_dir>/backup/`）。换新库等于基线永远回不到本机正式库
   （见背景第二条）。
5. **身份不随角色走**：1688 账号与专用 profile 留在这台机器上，不删、不移交；将来若要再采，
   改回 `collector` 即可。
6. **交换库一次建齐五只**（raw-m1、raw-m2、raw-m3、raw-m4、plan）；每台机器只 clone 自己那条
   raw 库 + `plan` + 名册里其它机器的库（后者的库还没建是常态，不算失败）。

## 被否掉的方向

- **永久 m1**（本机就是第一台采集机，退役后 m1 这个编号退休）：未来三台采集机只能占 m2/m3/m4，
  与 CONTEXT「机器…以 m1/m2/m3 标识」和 `config.example.toml`「汇总机自取一个（如 m4）」
  冲突；而且「m1」在文档里会同时指这台机器和第一台采集机。
- **先取临时编号、转汇总时再改 m4**：改编号要付账——平局定序变化、冲突账里新旧编号并存、
  「自己的组被判成别人的」。
- **转角色时换新库**：基线不可回灌（自己的包不收），本机正式库会永远缺 09-05..09-13 那段。
- **把测试期的包从 raw 库 HEAD 里删掉**：库存是当日观测，过去了采不回来；删掉就是永久缺。
- **只改配置档位、不换凭据**：纯汇总机「只持只读凭据」是域定义，而代码不校验档位——
  留着可写凭据，就没有任何判据能证明档位正确。

## 结果与代价

- `tools/setup_wizard.sh` 承接两种模式：默认「上机配置」（库清单按名册动态发现）；
  `--role-change` 走转角色的四件事与归档、自证。
- 代价，说在明处：m1..m3 三个编号在真机器到位前是空的（库先建着、没有内容）；过渡期的周报
  会把本机缺的天数如实记出来——这是预期，不是故障。
- CONTEXT 同步：新增「转角色」词条；「纯汇总机」词条写明「角色是档位、可随时间变，身份不随
  角色变」。
