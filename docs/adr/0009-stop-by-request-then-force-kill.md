# 0009. 停止采集：先请求协作停止，超时再强杀

- 状态：已接受
- 日期：2026-09-12

## 背景

界面上的「暂停」一直是 `Popen.terminate()`（`gui.py` 的 `_kill_proc()`）。Windows 上这是 TerminateProcess：抓取进程的 `finally` 一个都不执行——不关它启动的浏览器、不清身份行、不释放采集锁，全部由界面事后补。IS-43 记录的这个组合最完整：暂停留下的 Edge 占着 profile 与调试端口，之后每一轮新起的 `Popen` 秒退交接给那个旧实例，收尾静默跳过，用户必须手工关掉整个浏览器窗口（ROUND26，2026-09-11 23:53–23:55；第 27 轮 2026-09-12 00:40–00:49 真机复现）。

IS-43 已经把这一枪挡掉：收尾按**归属**关闭浏览器（先问 CDP 要真实 browser PID，取不到再退到调试端口占用者；`start_browser=false` 时不动用户自己的浏览器），并有真机证据。强杀本身留了下来——它是界面今天唯一能停掉采集的手段。

强杀的残余代价比看上去小，所以这条工单一直是 P2：SQLite 跑在 WAL 模式，已提交的快照保留、进行中的事务整条回滚；已占用的详情机会按商品编号或卡片位置去重，续跑会复用而不是漏掉；身份行由界面惰性清理。也就是说强杀是「脏但不坏」。

但留在强杀路径上的三处缺口是真实的：

1. **浏览器已拉起、调试端口还没监听**的那几秒里按暂停：界面只重试 3 秒（`_BROWSER_CLOSE_RETRY_SEC`）就放弃关闭，而抓取进程已经被强杀——随后端口起来了也没人关它。
2. `_kill_browser()` 用的是界面**当前**的 `attach_port`，与抓取进程启动时的配置不一致（改过 `config.toml`、或那一轮用了 `--config`）就关不掉。
3. 任何界面侧收尾逻辑失效的情形（界面自己崩溃、被结束进程）都没有第二道。

而协作停止的通道早就存在：轮次一旦有终态，`Round.stops_work()` 就为真，采集进程在下一个检查点抛 `DayBoundaryReached` 干净退出，走完自己的收尾。`.scratch/gui-single-flight/issues/03` 的「拿不到可用的 PID 时只写终态，采集进程在下一个检查点停下」依赖的正是这条。`abort_run()` 却是**先杀进程、再写终态**，所以这条通道在生产里从未被走过，也没有人验证过它的时延。

时延的上界由检查点密度决定：检查点在一家店开始前、每张卡片点开前、每个详情进入前与提交后；不在检查点也不能被打断的是 `Humanizer.sleep` 的整段（长停顿 10–20 秒、批量休息 20–40 秒、deny 退避 30/60 秒）、人工介入等待（最长 `human_pause_minutes` = 10 分钟）和单次页面操作（`timeout_ms` = 45 秒）。

## 决策

- **两种停止都先请求，强杀退回兜底。** 暂停＝写下停止请求（非终态，轮次保持进行中、可续跑）；中止＝先把轮次收尾为「人工放弃」，终态本身就是停止信号。两者都在窗口内等采集进程自己停下，超时才强制停止。
- **停止请求按目标进程识别，不按轮次**：请求行记目标 PID 与启动时刻（取自 `crawler_process` 身份行）。消费即删；身份对不上一律无视。新起的进程与命令行续跑因此不会被表里的旧请求影响，PID 复用也不会误伤。这条与 ADR-0008 把「谁在跑」交给环境事实是同一个取向。
- **采集端在自己的检查点上读请求**（与 `rounds.ensure_workable()` 同一处），并把长睡眠切成不超过 1 秒的片、逐片问一次；读到就回写一次「已收到」，随后照常走它的收尾：关掉本次启动的浏览器、清身份行、释放采集锁。
- **窗口**：没收到回执 8 秒；收到回执之后再给 10 秒。到期仍在跑就强制停止，顺序是：强杀进程（本界面自有子进程，另有身份行则先做镜像名校验再杀）→ 按归属收尾浏览器 → 删掉这条已无人消费的请求 → 状态落地。`gui.log` 与 `run.log` 两侧各留一行，事后能分清「在检查点干净停下」与「超时被砍」。
- **暂停打断的那家店记 `失败` 并写「用户在界面暂停，本店未完成」**，不再沿用「人工介入未完成」——那是人工验证超时的原因，写在这里是错因。
- **界面请求即返回**，由既有的约 2 秒轮询驱动倒计时与超时兜底，横幅显示「正在停止…」/「正在收尾…」。不新增后台线程，也不让一次 js_api 调用阻塞 8 秒——`pause_run()` 持锁，阻塞会把 IS-38 那条取数链一起拖住。
- **本期不做「暂停别处起的采集」入口。** 请求按进程识别之后，暂停外来的采集在技术上已经安全（浏览器由采集进程自己收尾，界面不需要去动别人正在用的调试端口），但用户预期不同：中止＝放弃，谁点都合理；暂停＝待会儿接着跑，而那一轮的进度视图在命令行那边。记为后续可选项。

## 结果

常见情况下采集进程自己收尾，浏览器不再只靠界面按端口找回来关；强杀从唯一手段变成兜底。关窗不打断采集这条不变，而且更好：停止请求写在库里，界面即便关掉，采集进程也会自己读到并停下——只是那一次没有超时强杀这道兜底。

代价有三处。其一，停止不再瞬时：按下后最多 8 秒（已确认收尾时最多 18 秒）才保证结束，界面必须如实显示在等什么。其二，暂停之后结果页会多出一条 `失败` 店铺备注，而今天强杀只留下 `待处理`——这是有意的可观测性提升，读方要习惯。其三，停止请求表成为第二个「运行中事实」（与 `crawler_process` 并列）；靠「按进程身份匹配 + 消费即删」让它天然惰性，不需要额外的清理规则。

回执救不了卡在单次页面操作里的情形（`timeout_ms` 45 秒）——那种时候到不了检查点，仍然落强杀兜底。

被否掉的方向：

- **控制台控制事件**（`CREATE_NEW_PROCESS_GROUP` + `CTRL_BREAK_EVENT`）：投递要求发起方与目标共享控制台，而界面可能由 `pythonw` 或打包壳（无控制台）拉起，要先 `AttachConsole` 再发信号，行为还随 Windows 版本与 `CREATE_NO_WINDOW` 的组合而变。这是把一个明确的失败模式换成一组不明确的失败模式。
- **只在「中止」上做协作**：缺口 1、2 都长在暂停路径上，只修中止等于把根因留着。
- **请求按轮次而不按进程**：命令行续跑会被表里一条旧请求立刻停掉，得靠「启动前先清」这条规则兜住，而这条规则又会擦掉用户在启动瞬间点的暂停。
- **只在强杀前睡 8 秒等它自己停**：采集端看不见请求，8 秒白等，窗口一到还是强杀。
