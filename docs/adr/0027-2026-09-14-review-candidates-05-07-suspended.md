# 0027. 2026-09-14 审查的候选 05–07 挂起

- 状态：已接受（挂起，不是否决）
- 日期：2026-09-18

## 背景

2026-09-14 的架构审查（[architecture-review-2026-09-14.html](../reviews/architecture-review-2026-09-14.html)）
提了 7 个候选：01–03 已落地（ADR-0023 / 0024 / 0025），04 已落地（ADR-0026）。剩下三个没开始：

- **05 详情机会账本收起存储原语**：让 `dedupe` 的规则与它下面的 SQLite 原语成为同一个 module，
  收起 `Database` 上那七个只为它存在的细粒度方法。
- **06 让店铺进度保留完整榜单的事实**：`list_status` 一列同时表示榜单完整性、是否跑完、续跑动作
  与界面分组；补采撞阈值时连已完成的榜单也失去「完成」事实，续跑会重扫榜单。这一条要**重开
  ADR-0020 有意的取舍**。
- **07 让轮次时刻从采集入口进入**：轮次日期、去重日期、提交时刻各读各的挂钟，时间成了隐藏
  interface，测试必须知道内部恰好调用几次 `utcnow()`。

## 决定

三个都挂起，理由：**影响程度不大，暂不处理。**

逐条为什么算「影响不大」：

- 05 是 **locality 的改善，不是行为缺陷**。规则本来就已经集中在 `dedupe` 里，没有已知的生产错，
  报告自己也没证明存在性能问题（「这里主要改善 locality，未证明性能问题」）。剩下的是它下面那层
  存储 seam 偏宽——难看，但不咬人。
- 06 动的是 **ADR-0020 刚定下的一条有意取舍**。重开的依据（完整榜单事实被抹平）成立，但它要求先
  推翻一条刚落地的决定，并重新论证「补采中断后整店算不算完成」。收益与代价目前不成比例。
- 07 是**测试债务的架构形态**。报告本身写明「不宣称新发现了生产跨日故障」；它影响的是测试能不能
  自己控制时间，不是采集行为。

## 后果

- **将来的架构审查不应把这三条当作新发现重提**；要提，就得先说清它们的前提变了。
- 三条都仍然是真实摩擦，不是被否决的：受影响的路径真要改时（07 的时间注入、06 的榜单完成语义、
  05 的存储 seam），应当回来重开本条。
- 报告本身保持归档原样，不加落地注解——沿用本项目自 2026-09-15 起的做法：落地与挂起记在
  ADR 与 spec 里，报告归档即终稿。

## 附：候选 07 目前唯一被观察到的表现

2026-09-18 做候选 04 时，一次全套运行报出 39 个错误：那次跑到本地时钟跨过午夜，而
`tests/helpers.py:new_round` 用的是 `cst_date()`，套件跑到一半北京时间换了日，`rounds.open`
按跨天逻辑收尾旧轮、新建一轮，一批用例因此失败。跨日前后各跑一次都是全绿。

这是候选 07 那条债务的现场版，也正是它「影响不大」这条判断的边界：它伤的是**测试**在每天
23:55–24:00 那一小段窗口里的稳定性（报告记的 `DAY_CUTOFF=(23,55)`），不是生产行为。哪天要动
测试的时间注入，这里就是入口。
