# 0008. 界面单实例与采集进程互斥

- 状态：已接受
- 日期：2026-09-12

## 背景

界面与采集此前都是「谁都能起一份」，而它们操作同一份资源：同一个 CDP 端口（`config/config.toml` 的 `attach_port = 9222`）、同一个 SQLite 库、同一个按「同日期 + 同范围」复用的轮次。双击两次 exe 就得到两个界面；界面只看得见自己拉起的采集子进程（`self.proc`）——命令行起的采集、上一个界面关掉后仍在跑的采集，它一概不知道，于是会再起一个。

两个采集进程撞在一起不是各跑各的，而是互相踩：`rounds.open()` 会把它俩并进同一轮同时推进，重复读详情、重复消耗同一个详情预算、同一轮被两侧各写各的提前收尾，还会抢同一个页面与同一把库写锁。

轮次身份那期把这件事明确排除了（`.scratch/round-identity/spec.md` 的 Out of Scope：「不引入跨进程锁、并发采集或多账号；同一时刻多轮的防御不在本期」）。现在翻案，直接原因是三条事实同时成立：

- 数据污染的代价是可验证的（并进同一轮、共用端口与库），不只是理论风险；
- IS-24 的剩余部分（跨会话的放弃入口）需要「现在有没有采集在跑、是哪一个」这个事实；
- 今天唯一的兜底绕路是「先点开始拉起一个进程、再到过程页中止」，而这条绕路恰恰会被本决策堵死——不一起解决，界面上就会出现「有进程在跑、但我从这里中止不了它」的死角。

## 决策

- **两把会话级命名互斥体**（`ctypes` 的 `CreateMutexW`，前缀 `Local\`）：界面锁 `Local\bestseller_gui` 由 `gui.py` 的 `main()` 持有，采集锁 `Local\bestseller_crawler` 由采集进程持有。进程被强杀时由内核释放，不需要清理残留；不同 Windows 会话互不干扰。
- **界面不持有采集锁。** 否则关掉界面会释放采集锁而采集还在跑。两把锁必须分开，这是实现时最容易踩错的一脚。
- **抢不到界面锁的实例由 `gui.py` 自己**弹中文 `MessageBoxW`、尝试把已有窗口前置、然后 `sys.exit(0)`。退出码 0 让 `gui_launcher.py` 保持安静，**exe 不需要重新打包**——ADR-0007 那条「改界面不用重打包」的性质因此得以保留。
- **采集锁是「有没有采集在跑」的唯一权威判据**，界面探测它、子进程自己抢它，命令行与界面共用同一把。
- **采集进程在库里登记身份**（`pid`、`round_id`、`started_at`、命令行摘要），启动时写、正常退出时清。它只负责显示与处置；与互斥体不一致时以互斥体为准，并清掉残留行。
- **子进程抢不到锁时**可读地说明原因并以专用退出码退出（避开现有的 2 = 无有效店铺、3 = 范围不符），界面据此提示而不是把它当一轮正常结束。
- **收尾幂等**：轮次已有终态时，采集流程的收尾不覆盖、不抛错、正常退出 0。
- **关窗不打断采集**，但如实告知"采集会在后台继续，重新打开界面可以中止它"。

## 结果

数据不再可能被两个进程同时推进；「有没有任务在跑」从各人自己记的变量变成环境事实；跨会话中止有了落脚点；界面单实例不需要重新打包 exe。

代价与边界：

- 互斥只在本机同一个 Windows 会话内生效，跨会话/跨用户不互斥（本项目就是单机单用户单账号）。
- 关窗继续跑意味着「孤儿采集进程」是常态，所以「重新打开界面能看见并中止它」是这条决策的必要部分，不是附加项。
- `tools/diag_*.py` 也抢 9222，不在这把锁的管辖内，另行处理。

被否掉的方向：

- **只在界面层拦**（把判据换成"库里今天有没有进行中的轮次"）：拦不住命令行并存，而且会把暂停之后的「继续/续跑」一起拦死——那正是轮次模块既有的核心语义。
- **用 PID 文件判断在跑**：残留文件与 PID 复用都要额外处理，不如内核对象可靠。
- **让 launcher 认专用退出码来做单实例提示**：要重新打包 exe，破掉 ADR-0007 的性质。
- **关窗即中止采集**：误关窗口会白跑一轮。

相关规格与工单见 `.scratch/gui-single-flight/`；来源工单为 IS-24（跨会话的放弃入口）与 IS-39（关窗时的任务处置）。
