# 0052. 判断来源清单由 m4 单点维护：Gitee API 生成、经 plan 通道发布

- 状态：已接受（设计）；票 01 实现生成与发布，票 02–04 实现接收侧，票 05 真机验收。本 ADR 记录已确认的方向，不宣称任何票已落地。
- 日期：2026-10-09（Asia/Shanghai）
- 范围：判断集（`judged-*`）的来源发现契约；不重解释 2026-09-24 m1 事件的归因，不改交换集通道。

## 背景

判断集按 [ADR-0039](0039-cross-machine-judgment-set.md) 走独立通道：每台生产机一本 `judged-<机器>`
私有库，各写各的。但「收谁的」这条契约一直是**本地口径**——`judgment_set.collect()` 只枚举交换区里
**实际存在**的 `judged-*` 目录（`judged_repos`），不会因为远端多了一本来源就去把它补下来。

2026-09-24 m1 的现场问题正落在这个缺口上：m4 发布了判断集，m1 的交换区里却没有任何 `judged-*`
克隆，来源枚举为空、收取结果为空。恢复 `judged-m4` 克隆后同一最小包就能导入——说明缺的不是解析能力，
而是**「远端该有哪些来源」这条事实没有落到接收机上**。

接收机要自动补齐本地克隆，前提是先知道「预期来源与可信远端地址」。这份事实不能由每台机器各自扫
Gitee 得到（那会把 API token 复制到每台机器），也不能靠采集名册（`machines.json`）推——判断的生产者
集合与采集机集合本就解耦（ADR-0039 决策 2、决策 3）。

## 决策

**来源清单成为一份共享事实：m4 经 Gitee API 生成、发布到 plan 库；接收机读它决定收谁。**

1. **单点维护**：m4 是来源清单唯一的生成者，也是唯一持有该用途 Gitee API token 的机器。token 不进
   仓库、不进快照、不进日志；m1/m2/m3 只读共享清单，不各自维护 token，也不直接扫 Gitee。
2. **快照通道**：清单落在共享 `plan` 库根下的 `judged-sources.json`（与 `shops.csv`、`machines.json`
   并列，同为「各机读取的共享事实」），走 `GitChannel` 的提交/推送与判断集同规。快照含格式版本、
   可信 owner、生成机器、生成时间与逐条来源（机器编号、库名、已批准远端地址）；**不含**任何凭据、
   密钥、Cookie、包内容。发布信息（哪一笔 plan 提交）**不进**快照——快照写不进它自己那一笔提交，
   消费方读 plan 提交即得关联（生成提交不自引用未来 commit SHA）。
3. **包含范围**：只纳入可信 owner 下、**私有**且名称严格匹配 `judged-<machine_id>`、且机器编号符合
   正式编号规则（`m<正整数>`，即 m1/m2/m3 与自取的汇总机编号）的库。`judged-test`、`judged-old`、
   `judged-demo` 这类不合规名称**不自动纳入**。**库存在即入列**——远端库即使还没有判断集包，也代表
   该来源应接入（空库不是失败）。
4. **刷新时机**：只在实际交换任务启动时刷新（`exchange.run_once` 的任一动作：整趟、只收取、只发布、
   只导出、只汇总，都在任务启动时刷一次）。打开交换窗口、启动分析都不刷新——它们不调用 `run_once`，
   因此天然不触发。
5. **查询完整性**：API 分页必须完整。任一页查询失败、或翻页没能确认到底，都算「查不全」，**不覆盖**
   上一版有效快照，并给可读告警（交换台上按「本机没做成事」记，退出码 2）。列仓库前先核对 token
   账号（`GET /user` 的 `login`）与可信 owner **逐字一致**，不一致同样按查询失败处理——空列表必须
   能区分「真没有」与「看错了地方」。
6. **缩减与改址保护**：相对上一版有效快照，来源**减少**或某来源的**远端地址变化**都先报告、保留
   上一版、等人确认，不自动覆盖（交换台上按「有需要人看一眼的」记，退出码 1）；确认的出口是交换台的
   `--confirm-source-shrink`，不加就每趟都保留上一版。上一版快照**读不动**也**不覆盖**（读不动 ≠
   没有上一版）。**无变化不产生提交**（同内容空操作，与周包/判断包同规）。
7. **快照语义**：清单是快照，不是「必须与此相同」的强约束——某来源从清单消失，**不**触发接收机删除
   已有本地克隆（删克隆另属人工）。
8. **plan 拉取失败时**：接收机可用最近一次**有效**本地快照，处理**已有且匹配**的来源，并给出显式
   告警；**不**从过期快照发现新来源或创建新克隆（票 02 落接收侧）。
9. **本地落点由接收机定**：来源的本地目录固定为 `<exchange_root>\judged-<machine_id>`，由接收机的
   配置与机器编号推出；清单不能指定任意本地路径（票 02）。

## 被否掉的方向

- **每台机器各自扫 Gitee**：要求把 API token 复制到 m1/m2/m3——凭据面随机器数扩张，且与 ADR-0039
  决策 3「token 不进接收机」相抵。
- **用采集名册（`machines.json`）当来源声明**：判断的生产者集合 ≠ 采集机集合（纯汇总机 m4 不采却产判断）。
- **接收时从「缺失的目录」凭空发现来源**：目录不存在时无从得到可信远端地址；这正是原事件里 m1 收不到的空洞。
- **把来源清单做成中心服务或常驻同步**：与「手工触发的独立小工具、Gitee 私有库」的既有选择相抵。

## 结果与代价

- **收益**：来源事实只维护一处（m4），接收机按清单自动补齐——「远端有、本地没有克隆」这个缺口从
  契约上被堵住；token 面收敛到一台。
- **代价一**：判断集通道多出一个「m4 必须在线刷新过」的前置。m4 没刷过清单时，接收机只能按
  「通道未就绪」如实报，不能伪装成「没有新判断集」。
- **代价二**：来源清单成为又一份要保鲜的共享事实；plan 拉取失败时接收侧按第 8 条降级（不发现新来源）。
- **代价三**：来源消失是合法的（人工退库），但产品选择**不自动**响应消失（保护 + 等人确认），
  代价是一条来源真的退役时需要人工确认这一步。
