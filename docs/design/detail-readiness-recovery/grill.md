## 2. 问题定性

已确认的控制流原因是：取得详情页后，页面证据在现有初次就绪窗口内一直无法可靠判读；窗口结束后再次判读抛出 `PageEvidenceUnavailable`，按既有规则停止整轮并保留残缺榜单。

已确认的说明缺口是：这一原因被通用停止映射包装成“人工介入未完成”，而它没有进入正式人工校验等待；记录还缺少出错商品/卡片与页面的可靠关联。

需要设计决定的行为是：现有窗口之后，是否增加有界自动恢复；恢复失败是否授予一种明确来源的可续跑暂停；使用者怎样检查问题。不能把这些决定写成“已查明原因为慢页面”。

## 3. 领域边界

下表沿用现有 [CONTEXT](../../../CONTEXT.md)。其中页面状态描述不自动成为新增领域术语。

| 概念 | 本问题中的含义与边界 |
| --- | --- |
| 慢渲染 / 暂时不可识别 | 对真实页面状态的候选解释；只有随后读到可靠页面，才能确认本次在有限等待内恢复，仍未必知道物理根因。 |
| 页面上下文未知 | 当前页面证据不足以确认目标业务页面可用；不等于已确认滑块、deny、页面崩溃或浏览器归属未知。 |
| deny | 现有页面判据已识别的拒绝；保持原有记账、降温、店铺/整轮阈值及后果。 |
| 人工校验 | 已识别的滑块、登录墙或身份验证等，进入各自既有确认和等待规则。未知页面不能冒充已识别校验。 |
| 采集失败 | 商品观测/尝试及失败记录的业务结果；本次控制流停止不能悄悄变成商品普通失败、耗尽尝试或已处理。 |
| 轮次暂停 | 要区分异常导致采集停止与普通 GUI 明确授予的暂停资格；未终态、进程消失、日志出现“暂停”均不足以证明能点继续。 |
| 主动停顿 | 自动节奏控制的等待；不等于用户主动暂停，也不等于本次异常停止。 |
| 残缺榜单 | 榜单未遍历完成时保留的已发现商品集合；中断及再次中断均不应抹掉先前发现的行。 |
| 详情阶段 | 完整榜单保存后的详情补采。本次是在榜单过程中打开商品详情，不能据此把 A09 置为“详情阶段中断”。 |
| 店铺阶段事实 | 榜单完整性与详情阶段独立。完整榜单后的详情中断不能把榜单降为失败。 |
| 续跑 | 同一未结束轮、同一北京时间日期、冻结原店铺范围；未完成榜单会重新遍历该店，完整榜单直接补详情。没有页/卡片断点承诺。 |
| 浏览器归属 | 独立的会话资源责任证明；页面未知不能放宽 PID / creation proof / 清理门槛。 |

## 4. 当前代码实际做了什么

### 4.1 共享详情访问

[`detail_visit.py`](../../../bestseller_monitor/detail_visit.py) 的 `begin_detail_visit` / `_settle_detail_page` 已经为点击打开详情和完整榜单后的补采共用初次就绪流程：

1. 取得页面前检查主动停顿；真实取得页面后记一次详情访问。
2. 先判读 deny 与人工介入，保持既有顺序。
3. 只有 `PageEvidenceUnavailable` 进入初次就绪轮询，现为 10 秒、约 0.25 秒一轮。
4. 期间可靠恢复即可继续；识别出 deny / 校验则立即交给相应流程。
5. 窗口用完再原样判读一次；仍未知则上抛，不刷新，也没有额外恢复窗口。

这已经有“反复检查”，因此候选方案必须区分：继续轮询、增加等待窗口、刷新造成的新页面请求。不能笼统写成当前完全不重试。

初次可靠后还有 `ReadyDetailVisit.observe()` 的可读等待。晚到的已识别人工介入解除后会重新给一个完整可读窗口；晚到的未知页面没有与初次相同的恢复包装。当前可读超时会读取当下 HTML 再按现状观测，不自动等同于本次初次未知异常。

### 4.2 页面判读与人工流程

[`guard.py`](../../../bestseller_monitor/guard.py) 的 `_page_evidence` / `intervention_detail` / `ready_detail_page` / `wait_for_resolution` 负责唯一判据与介入顺序。

当前已包含 10 月 11 日加入的 gallery 业务标记，不能在缺少异常 HTML 时认定是该旧缺陷复发。已识别介入有既有确认、可能的刷新、正式事件与响铃等待；身份验证还受固定截止时间及原访问目标恢复证明约束。

恢复期间如果识别出真实 deny / 校验，应回到既有流程；不得用新窗口重新计时身份验证，不得将未知状态算作验证已解除。

### 4.3 商品关联与页面关闭

[`click_listing.py`](../../../bestseller_monitor/click_listing.py) 的 `_card_identity` / `_visit_card` / `_enter_detail` / `capture` / `_ingest`，以及 `PlaywrightCard.acquire` / `click_card` / `close_popup_or_back` 是点击链路。

卡片打开前已有页号/索引和可能的目标链接；可靠商品身份未必在异常前取得，缺编号应记录卡片定位与“未知”，不能借用上一商品。取得页面前的 popup/load-state 错误与本次取得后无法判读不是同一触发点；不能顺手扩成所有浏览器 IO 失败重试。

页面关闭由取得页面的一侧负责；轮次退出最终进入 [`browser_pw.py`](../../../bestseller_monitor/browser_pw.py) 的会话收尾。当前不能承诺异常页签会留给操作者查看；借用浏览器与本任务创建浏览器仍按各自归属处理。

### 4.4 停止、阶段事实和 GUI 继续

[`pipeline.py`](../../../bestseller_monitor/pipeline.py) 的停止映射将 `RoundPauseRequired` 统一写为“人工介入未完成”，是 A09 店铺说明的误导来源。当前轮次通用日志已改为“采集已停止”，和现场旧版“本轮暂停”有差别；GUI 与 CLI 的下一步建议也已分开。

`_record_shop_stop` 与 [`shop_progress.py`](../../../bestseller_monitor/shop_progress.py) 区分榜单未完和完整榜单后的详情中断，保持两套事实。

[`views.py`](../../../bestseller_monitor/views.py) 的 `_round_can_resume` 与入口 [`gui.py`](../../../gui.py) 的 `resume_run` 要求本 GUI 明确主动暂停了该轮，并满足同日、无运行采集及安全收尾等门槛。异常停止本身不会授予这个资格。

因此“本次未知页面恢复失败后，可以点继续”是一项需要明确批准的新行为，不能靠改一句提示实现，也不能泛化成所有异常都允许继续。

## 5. 当前证据支持的结论与候选方案

事实结论：一次有限窗口内的未知页面会停止整轮；这不是这次识别出了滑块或 deny。原始页面证据不足，物理根因未定；现有停止说明与出错目标关联不足。

建议讨论的方向，全部待确认：

- 在共享详情访问处，为未知页面增加有界恢复；保留第一判读与 deny / 校验优先级。
- 初次 10 秒窗口之后，至多刷新一次目标详情页并等待可靠恢复；禁止无限刷新或重建浏览器会话。具体窗口、总时限、刷新前目标核验和 late-unknown 预算待下一轮决定。
- 恢复成功后照常读取当下页面；单个商品恢复失败时记录“详情页未就绪”，跳过该商品并继续下一个商品，不冒充人工校验等待。
- 连续三个商品详情访问失败后，明确中止整轮；“连续”按本轮相邻商品失败计算，成功完成一个商品后清零。失败计数是否只针对本 feature 的详情页未就绪，需在依赖问题中钉死。
- 达到连续三次失败阈值后不授予本 GUI 的系统暂停或续跑资格；这是中止结果，已发现商品保留，但需要重新开始新的采集轮次。
- 恢复中和单商品跳过时，界面提供店铺、已知商品或卡片位置、可靠目标链接与原因；区分正在恢复和已跳过，不承诺原页签仍存活。达到连续三次失败并中止后，界面只显示类似 deny 超限的文字中止原因，不额外展示失败商品、URL、证据路径或恢复明细；详细信息仍留在后台事件和诊断证据中。
- 在刷新前和最终仍未知时存诊断证据；使用者可据链接重新检查，开发者可据证据复盘。证据读取/写入失败不得阻断正确停止或改变判定。

这些方向不是 spec，没有得到用户批准。增加刷新会涉及主动停顿记账；连续失败中止会涉及终止原因、已发现数据保留和新轮次边界；截图、分次留档和新事件会涉及既有证据约定，均不可默认实施。

## 6. 设计树与第一轮问题

本轮前置事实已查清；Q1–Q5 已得到用户决定，仍需在 to-spec 中收敛连续失败定义、等待预算、证据格式和中止终态边界。

### Q1：覆盖范围（已决定）

用户决定采用建议：同样的未知页面，覆盖榜单过程中打开商品、完整榜单后的详情补采，以及详情页已经可用后再次变未知的情况。

边界保持：只恢复无法确认页面证据的状态，不扩大到所有网络错误、解析失败或浏览器会话异常。两个详情访问入口共享这条恢复规则，但后续仍需明确恢复次数和等待预算是否共享。

后续依赖：两阶段之间恢复预算是否共享、晚到未知的触发门槛、浏览器/页签已关闭的出口。

### Q2：自动恢复方式（已决定）

用户决定采用建议：现有 10 秒轮询仍无可靠结论后，最多刷新一次仍属于原访问目标的详情页，并给有界的再次判读窗口；不反复刷新。真实 deny / 人工校验出现时立即服从既有处理。

尚待细化：刷新前是否再加纯等待、刷新后窗口、包含导航超时的总时限、目标无法确认时是否禁用刷新，以及每次恢复如何记账与记录。

### Q3：恢复失败后的单商品处置、轮次阈值和续跑（已决定部分行为）

用户决定：单个商品详情恢复失败后，跳过该商品，继续尝试下一个商品；连续 3 个商品都失败后，停止该轮。

因此，单次失败不再直接中止整轮；已发现商品继续保留，失败商品必须记录，后续商品仍按原榜单流程尝试。达到连续三次失败阈值时，整轮以明确的“详情页未就绪连续失败”原因中止，并保留已发现商品。

待细化的定义：

- “商品失败”是否只指本 feature 的详情页未知在恢复后仍失败，还是也包括详情导航、页面关闭、解析失败等其他详情错误；
- 商品身份未知时如何关联失败记录，以及是否允许把同一张卡片的重复尝试算作多个商品；
- 哪些成功事件会把连续失败计数清零（至少需要一个商品详情成功）；
- 达到阈值后的中止记录如何落库和展示，并与用户主动中止、deny 中止、人工校验超时区分；
- 中止后不提供本轮 GUI 续跑资格；使用者若要继续，需启动新的采集轮次。新轮次如何处理已保留的残缺榜单，属于既有新轮次规则，不在本次详情恢复行为中扩展。

其他异常、终态和身份验证超时不应因这个阈值自动获得同一资格，除非后续明确决定。

后续依赖：中止原因保存、防止与用户主动中止或 deny 中止混淆、连续失败计数持久化边界、失败商品记录与收尾失败的处理。

### Q4：界面上的处置方式（已决定）

用户决定：

- 恢复中和单商品跳过时，按建议显示恢复进度、店铺、可靠商品编号或卡片位置、目标链接与当前原因；编号未知时不能借用上一个商品。
- 单个商品失败后继续运行，不进入滑块式持续响铃等待。
- 连续 3 个商品失败导致本轮中止时，不播放声音。
- 中止后只显示文字中止原因，语义类似 deny 次数超限；不额外展示失败商品清单、URL、证据路径、恢复次数或其他诊断明细。
- 失败商品、目标 URL、恢复次数、判定原因和 HTML/截图仍写入后台事件与诊断证据，供开发侧复盘，但不作为中止结果页的额外展示内容。
- 浏览器按正常归属规则收尾，不为保留异常页签延迟清理，也不承诺原页签仍可供检查。

中止原因需要与 deny、滑块、登录墙、身份验证和用户主动中止区分；本轮不提供继续按钮。

### Q5：应保存多少现场证据（已决定；历史共用范围已盘点）

用户决定采用建议：只在未知异常路径的刷新前与最终失败点，尽力保存 HTML 和页面截图，并关联轮次、店铺、商品或卡片、目标/当前 URL、判读原因与恢复次数；读不到也明确记录原因。正常轮询不逐次存图，证据失败不改变采集控制流。

根据用户追加要求，已盘点历史运行问题。适合共用同一异常页面取证能力的范围包括：本次未知详情页、滑块/登录墙/身份验证页，以及 2026-10-04 和 2026-10-08 的 deny 拦截页。共同点是异常页面无法回看；只共用证据保存，不合并 deny 计数、阈值、人工等待或暂停语义。盘点详情见 [历史异常页面取证盘点](historical-evidence-audit-2026-10-25.md)。

这会触及 [ADR-0057](../../adr/0057-intervention-archive-landing-and-boundary.md) 既有的“不引入截图”决定；to-spec 阶段必须明确修订证据范围和 ADR。`ADR-0059` 的访问结果与判定边界仍需保持，不能让取证模块改变详情访问语义。

后续依赖：异常类型和取证时点、命名与关联事件、覆盖/保留、截图及 HTML 读取时限、打包选取与体积上限、证据保存失败记录、ADR 修订。

### 后续轮次才可定稿的联合问题

1. 自动恢复次数和等待总预算按一次详情访问限制，还是可被初次/晚到未知分别重开；避免未知/可用反复切换导致无限恢复。
2. 刷新是一次真实请求时，主动停顿额度如何检查和记账；不得混同于商品机会、详情预算或业务失败尝试。
3. 用户停止、关闭、跨天或 deny / 校验在恢复中出现时的优先级；身份验证固定截止时间不能被重开。
4. 当前 URL 与冻结访问目标不一致、链接缺失、页面关闭或读取超时，应如何有界退出；不得刷新列表页、错误目标或另一个用户页签。
5. 恢复成功、失败暂停及续跑后的共同验收与可观测证据；不把代码日志文本等同于真实页面复现证据。
