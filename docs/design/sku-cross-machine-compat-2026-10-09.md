# SKU 跨机共享兼容说明（2026-10-09，票 08）

## 格式与路径

- SKU 判断集：`judged-<机器>` 库内的 `data/sku-judgments.db.gz`（口径版本 `sku-v1`），含 SKU 判断、候选推荐与 SKU 人工决定。
- 旧商品级判断集：同库 `data/judgments.db.gz`（v2），**一字未改**，继续按原样发布与收取。
- 两者同库不同文件；新程序两条通道都走，旧程序只认旧路径。

## 旧版本实测（结论：结构性隔离，不会静默误用）

- 实测对象是**真实旧代码**：旧通道四个模块（`judgment_set.py`、`export.py`、`merge.py`、`git_channel.py`）与 main（已部署版本）逐字节一致（`judgment_set.py` 由测试以 `git diff --quiet main` 断言锚定，其余三个经审查复核 diff 为空；`judgment_set` 依赖的 `matching.py` 与 main 的差异来自票 05–07 的 SKU 改动、不在旧通道路径上）。共存测试直接调用真实的旧发布与旧收取函数操作含新文件的交换区与克隆。
- 实测结论：旧发布只覆盖 `data/judgments.db.gz`，新文件在远端与工作树都一个字节不改；旧收取只读旧路径、不建也不碰 SKU 表。旧程序对新格式既读不到也写不到——不存在「静默误用」的通路。
- 反向闸门在新程序里：新收取遇未知的 SKU 格式版本（如未来 `sku-v2`）**明确拒绝**、一行不导并点名升级；新发布遇远端是更新的格式版本时**拒绝覆盖**（覆盖会毁掉新机器发布的数据，如实报错要求先升级本机）。

## 部署顺序与发布约束

- 升级顺序任意：旧通道新旧互通不受影响；SKU 结论只在**已升级的机器之间**流动，未升级机器看不到、也不会破坏它们。
- 旧机器发布旧包不会丢失 SKU 数据（不同路径）；新机器发布不改动旧包（除非本机旧判断集真有新内容，那本是旧通道的正常更新）。
- 建议顺序（非强制）：把各机器升级到含本票的版本后，再依赖 SKU 跨机复用；升级期间不必停交换台、不必清任何库。

## 已知缺口与口径

- 冲突账只记不展示：SKU 冲突（收取期与回放期两类）落在草稿库 `sku_decision_conflicts` 并在交换台周报计数，SKU 确认页暂不展示（商品侧有页面裁决面；SKU 侧留后续）。
- 同一决定（同成员集）先到的来源保留，同内容后到跳过；来源只作说明与冲突溯源，不参与键。
- 远端是更新的 SKU 格式时新程序选择**不工作并报错**而不是降级发布；全部机器升级后再互通。
- 证据（图片字节）不走本通道（与判断集既定口径一致，图片仍走对象存储通道）；判断命中要求两端证据摘要一致，本机缺证据自然不命中。
- 挂账（不在本票范围）：`export.py` 的 `pack_gzip` docstring 称商品判断集共用它，实际 `judgment_set.py` 仍自带一份同名私有函数——该文件被「与 main 逐字节一致」冻结，属旧注释失真，解冻旧通道时一并修。
