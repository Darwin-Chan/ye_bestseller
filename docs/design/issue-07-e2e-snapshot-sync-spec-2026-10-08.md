# Issue 07：e2e 保存后快照同步与换长区间验收规格

Status: ready-for-agent
Feature: issue-07-e2e-snapshot-sync
Date: 2026-10-08（Asia/Shanghai）
Stage: to-spec；访谈已由用户确认，尚未拆票或实施。

本规格依据已确认的 D1–D4；ready-for-agent 只表示需求已明确，不表示修复、验收或原机复验已经完成。待 to-tickets 形成纵向切片与阻塞关系后再实施。

## Problem Statement

维护者运行“换更长日期区间后复用人工确认并重算销量”的端到端测试时，可能看到测试要求“畅销品”结果页，页面却停在“确认同款”。已定位的失败发生在真正换长区间之前，不能据此认定长区间销量算法出错。

原测试仅等待地址出现分析号，然后直接在后台并组、确认和保存。分析号出现早于最终快照读取完成；后台修改不会自动更新浏览器已持有的快照。后台保存早于页面读取时可能通过，页面先读取时则仍持旧状态。测试把“后台已保存”当成了“页面已读到并应用保存后的状态”。

既有隔离诊断：自然执行 11/11 通过；固定页面先读旧快照后，原断言稳定失败。同一分析 ID 下，浏览器 confirmed=[false,false]，服务端 confirmed=[true] 且 dirty=false。保存后 reload、最终 GET 延后至保存之后的完整对照通过；正常 UI 确认与保存的最小对照通过。这证明测试竞态，不是本次修复交付证据，也没有还原原 m2 的调度和环境。

## Solution

保留测试直接调用后台代办并组、确认和保存的方式。测试先证明页面已经取得本次初始快照，随后在后台完成保存；保存成功后主动刷新同一分析页面一次，再通过“保存返回状态、刷新读取内容、页面实际呈现”三层核对证明同步完成。之后才使用页面继续换区间或断言结果。

完整场景保留日期选择、分析读取、结果页呈现和换长区间的真实页面流程。专门回归固定“先读旧快照、后后台保存”的顺序，通过本地公共 API 操作及真实刷新验证同步边界。另有正常 UI 操作对照，证明现有用户流程仍可用，但不把完整业务场景改成全程 UI 操作。

共用一个测试侧的小范围刷新/核对辅助函数；不增加产品自动同步、修订号或测试专用接口。当前范围是测试修复；若发现已应用正确快照仍有独立产品错误，先单独证明、另拆 ticket，不在本规格下顺手改变业务语义。

## User Stories

1. As a 测试维护者, I want 以确定顺序重现页面先读取旧快照的情况, so that 回归不依赖机器速度和偶然调度。
2. As a 测试维护者, I want 保留后台代办并组、确认和保存, so that 完整场景继续聚焦确认复用和销量重算。
3. As a 测试维护者, I want 区分取得分析号与页面完成读取, so that 不在分析尚未呈现时继续操作。
4. As a 测试维护者, I want 核对后台保存调用的完成和返回内容, so that 未保存的数据不会被误当成已保存。
5. As a 测试维护者, I want 保存后明确刷新同一分析一次, so that 页面重新读取状态而不依赖不存在的自动更新。
6. As a 测试维护者, I want 捕获本次刷新产生的实际快照响应, so that 历史请求或其他分析的响应不能充当同步证据。
7. As a 测试维护者, I want 比较响应中的分组成员、确认和保存状态, so that 同一分析 ID 的旧内容不能误通过。
8. As a 测试维护者, I want 核对页面实际展示的分组和销量, so that 网络成功但页面未应用内容时仍会失败。
9. As a 分析使用者, I want 已保存且全部确认的本场景进入“畅销品”, so that 能查看同款组排名与构成。
10. As a 分析使用者, I want 更长区间复用适用的已保存人工确认, so that 不必对相同商品证据重复确认。
11. As a 分析使用者, I want 新区间重新计算商品和组销量, so that 结果不是旧区间数值的复制。
12. As a 分析使用者, I want 旧分析保持原日期区间和销量, so that 新分析不覆盖已有结果。
13. As a 测试维护者, I want 新区间按新分析完成条件验收, so that 不错误要求其具有旧分析的保存时间。
14. As a 测试维护者, I want 未保存状态不能通过保存后同步检查, so that dirty=false 的初始状态也不会被误认作保存成功。
15. As a 测试维护者, I want 仍有未确认组时不能通过已全部确认的结果验收, so that 不以保存成功替代人工确认。
16. As a 测试维护者, I want 真实 UI 确认和保存有独立对照, so that 后台 fixture 不掩盖正常用户流程的回归。
17. As a 测试维护者, I want 失败报告区分保存、读取、呈现和落屏阶段, so that 不必从同一个标题超时猜测根因。
18. As a 测试维护者, I want 共用有限范围的测试辅助函数, so that 两个场景不会各自维护不同的同步标准。
19. As a 项目维护者, I want 在临时本地数据和可控外部替身上验证, so that 不使用生产数据、真实账号或外部远端服务。
20. As a 项目维护者, I want 保留红绿、完整场景、全量和审查证据, so that 诊断完成和偶然通过不会被当成修复完成。
21. As a 项目维护者, I want 区分本地交付与原 m2 复验, so that 台账只记录实际完成的验收。

## Implementation Decisions

### 1. 写入范围与公共接缝

- 修改范围为端到端测试及其必要的测试辅助代码；不因本次同步修复改变页面、分析服务、数据库、保存协议、人工决定账本或销量算法。
- 完整场景保留通过分析服务的公开方法代办并组、确认、保存。同步保存方法正常返回是该调用完成点；不得仅发起调用便继续刷新。
- 专门时序回归通过现有本地 HTTP API 完成后台修改与保存，使用实际服务和临时库存、草稿存储，遵守现有请求校验，不绕过公共接口保护。
- 页面通过真实进入分析和刷新路径读取快照。正常路径不伪造成功快照、不直接赋值浏览器快照变量、不调用页面内部渲染或落屏函数。
- 库存铺数和模型响应替身属于允许的 fixture。请求拦截只用于明确的时序控制或反例，不替换正常验收中的真实保存与读取。

### 2. 初始页面完成条件

- 分析 ID、日期区间与本次选择对应；最终快照读取完成，页面已经呈现对应的分组内容，且分析等待遮罩不再阻止后续操作。
- 地址 hash、进度 ready、页面导航完成或任意标题可见，均不能单独作为初始快照已应用的依据。
- 专门旧快照场景在后台修改前，明确证明页面当前呈现初始未确认分组；此后才允许触发后台修改，不能用等待固定毫秒数建立顺序。

### 3. 保存后同步合同

依次建立下列完成点，前一步不成立不得继续业务操作：

| 完成点 | 充分证据 | 不充分的替代物 |
| --- | --- | --- |
| S：保存完成 | 保存成功返回；分析身份和区间正确；成员及确认状态符合 fixture；dirty=false；saved_at 非空 | 只调用了保存、只查到 ID、初始 dirty=false |
| R：刷新读取完成 | S 之后触发一次同分析 reload，捕获该导航触发的目标 GET；成功响应的身份、区间、分组成员、确认、保存标记及预期销量与 S 的快照一致 | 保存前的响应、测试自己额外发 GET、仅响应 200、仅时间戳相等 |
| U：页面呈现完成 | 新文档展示与 R 对应的分组及销量；“畅销品”结果屏实际可见；通过正常返回确认页操作可核对已确认组和成员 | 收到响应但未核对呈现、只看标题、检查隐藏旧 DOM |

- 保存返回值形成独立的预期记录；测试不得用后来读到的响应反过来覆盖预期，让旧状态自己证明自己正确。
- 请求监听在触发刷新之前建立，按本地来源、请求方法、分析 ID 和本次刷新生命周期关联；等待响应正文可解析后再核对。
- 比较业务相关字段，成员按稳定身份核对；不要求将所有可能随读取变化的展示辅助字段做逐字节全量比较。
- 新鲜性的证据是因果顺序和内容，而不是“saved_at 比旧值大”。saved_at 是秒级时间戳，不能充当唯一修订号。
- 保存到持久层与页面刷新是两件事；页面 reload 可从服务内存取得状态，不把 reload 冒充服务重启或磁盘恢复验收。

### 4. 新区间合同与业务不变量

- 从旧分析结果页经真实页面返回、重新选择日期，取得不同的新分析 ID，等待新分析最终快照读取及页面呈现完成。
- 新分析复用适用的已保存人工确认，不在新分析中再次后台确认或保存来强行制造通过。
- 新区间快照不要求拥有旧分析的 saved_at，也不必满足“本分析刚保存过”；按本场景的完成状态、确认状态及既有结果页门禁验收。
- 两店各一商品，商品证据不变：短区间为 2026-09-07 至 2026-09-14，库存各自从 100 降至 95，两商品销量各 5、组销量 10。
- 长区间至 2026-09-21，结束库存分别为 75 与 65；两商品销量分别为 25 与 35，组销量为 60。确认组仍包含这两件商品，组销量等于成员销量之和，不仅断言“与原来不同”。
- 旧分析仍保留短区间、原分组及组销量 10；新分析有一个已确认组，页面可见两个商品，最终确实进入“畅销品”。

### 5. 测试辅助函数边界

- 在测试侧提供有限复用的“刷新并核对保存后状态”操作，接收目标页面、分析身份及独立保存预期，供完整场景和专门旧快照回归共用。
- 它不代办并组、确认或保存；不重复刷新、不延长超时直到通过、不自动把失败分支转成成功。
- 条件等待可设置有界超时和使用现有断言的条件轮询，但不得把重新执行保存、刷新、整场景或固定 sleep 作为成功策略。
- 失败信息至少给出阶段、预期/实际分析 ID、区间、保存标记、成员/确认摘要、当前可见屏幕以及响应状态（适用时）。正常 UI 路径仍按真实保存回包和页面切换等待，不强加刷新。

## Testing Decisions

### 测试原则与先例

- 最高验证接缝为真实浏览器页面、实际本地 HTTP 服务和临时数据库的组合；只测辅助函数或直接读取私有浏览器变量不构成交付。
- 既有完整浏览器验收用例提供日期选择、分组、确认、保存和返回确认页的先例；既有分析复用用例提供跨区间人工决定、证据变更和旧分析不变的服务层边界。保留它们的职责，不复制全套服务层测试。
- 允许浏览器内部状态用于额外失败诊断，不把它作为唯一完成信号或正式通过依据。
- 固定数据、小场景、明确事件顺序优先于重复运行次数。正常通过路径不吞断言；专用负例只能捕获并断言它明确预期的失败阶段。

### 可验收条件

| 编号 | 场景 / 动作 | 必须观察到的结果 |
| --- | --- | --- |
| AC01 | 原测试受控重放：先完成页面初始读取，再后台代办并保存；不补刷新 | 原“畅销品”断言红；同一分析下服务端已保存确认、页面仍旧，证据可定位失败阶段。此红是开发证据，不作为永久失败用例提交。 |
| AC02 | 在同样顺序中加入已定义同步操作 | 保存后一次刷新，S/R/U 全部成立，进入结果页；只改变同步方式，不改业务逻辑。 |
| AC03 | 刻意延后快照 GET 的放行 | GET 未完成时不得开始下一步业务操作或宣告同步成功；按事件放行后内容和呈现正确，不使用固定延时。 |
| AC04 | 刷新读回同 ID 的旧快照 | 即便请求 200、分析 ID 正确，也因成员/确认/保存内容不符而不能通过；归类为刷新读取不成立。仅专用反例允许回放先前真实捕获的旧响应。 |
| AC05 | 对其他分析 ID 或其他日期区间的响应进行同步核对 | 不得被当成本次响应或本次分析就绪证据；不能仅凭已有页面标题放行。 |
| AC06 | 后台存在未保存编辑，或保存没有成功完成 | 不得进入“保存后同步成功”；脏状态不进结果屏；缺少成功保存事实不能被初始 dirty=false 代替。 |
| AC07 | 保存成功但仍有未确认组 | 真实保存/读取可成立，但“全部确认且进入结果页”的验收不得成立；保留确认页，不能删去 confirmed 检查使其通过。 |
| AC08 | 保存及目标 GET 内容正确，但页面未完成应用或未进入正确屏幕 | 不能以网络成功放行；诊断区分页面呈现不成立与结果页转换不成立。不是预设产品有此缺陷。 |
| AC09 | 完整短区间后台代办并保存、同步 | 两件商品合一组且已确认；短区间各 5、合计 10；页面确实进入“畅销品”。 |
| AC10 | 真实页面扩大日期区间 | 新 ID、新区间、最终 GET 及呈现对应；不得依赖 hash 即就绪。 |
| AC11 | 新区间复用 | 原两成员同组且已确认，不再次确认；正常落到“畅销品”。 |
| AC12 | 新区间重算 | 两商品销量 25、35，组销量 60，页面与快照一致；不能只验证不相等。 |
| AC13 | 再读旧分析 | 短区间和组销量 10 保持不变，不被新分析覆盖。 |
| AC14 | 结果页返回确认页核对名单 | 新分析显示两个商品、一个已确认组，成员身份正确，而非只有组计数碰巧相同。 |
| AC15 | 最小正常 UI 路径 | 真正点击确认和“保存分组并查看畅销品”，等待实际成功回包和呈现后通过；不用后台确认或额外刷新代替该路径。 |
| AC16 | 共用测试辅助函数及故障提示 | 正向两场景使用同一同步标准；负例能按保存、读取、呈现/落屏阶段区分，不全部退化为标题超时。 |
| AC17 | 静态检查本 issue 差异 | 未加入固定 sleep、无条件超时等待、盲目刷新/重跑、吞断言、删结果页断言或无关产品改动。 |
| AC18 | 目标回归与收尾 | 目标测试及既有分析复用相关回归通过；隔离分段全量完成且对账；Standards / Spec 审查完成并处理阻塞发现，证据可追溯。 |

AC03/AC08 的时序或故障控制只能存在于测试边界，不能为制造证据而新增产品开关。具体控制方式在实施时选现有最高公共接缝；未能取得可区分证据时报告验收缺口，不冒称通过。

### 红绿及执行次序

1. 固定来源提交和本次待测文件，建立隔离测试环境；记录初始快照先于后台修改的证据。
2. 对原行为取得 AC01 的稳定红证据并最小化；保存原断言和原始失败日志，不仅引用历史诊断或自然通过。
3. 逐条红→绿实现同步辅助函数及旧快照回归，覆盖 AC02–AC08、AC16；不先写完所有实现再补测试。
4. 恢复完整原业务验收 AC09–AC14，并验证正常 UI 对照 AC15；已存在的相关测试先复用或补强，不重复制造同义测试。
5. 审查差异 AC17，运行目标测试与服务层相关回归；收尾运行一次分段全量，然后执行双维 code-review。若审查引入代码变动，补受影响回归，按最终变动重新判断全量证据是否仍有效，不把旧版本结果冒作新版本验收。
6. 最终通过的套件不保留故意失败的测试；红能力以保留的重放方法/最小测试差异和原始日志证明，正式反例断言同步契约拒绝错误状态。

## Out of Scope

- 产品自动刷新、订阅、推送、多窗口状态同步、单调 revision 或测试专用端点。
- 改变人工确认、分组复用、商品证据版本、人工决定账本、销量计算或结果页业务门禁。
- 把完整场景改成全程 UI 点击；把真实 UI 对照取消或用后台保存替代。
- 延长固定等待、偶然重试、放宽或删除“畅销品”断言，以自然运行通过代替受控红绿。
- 全仓测试等待框架、批量改造其他场景、顺带修复数据库/采集流程/SKU 分组等工作。
- 外部模型或图像真实网络调用、真实账号、生产数据库、真实业务采集或交换远端。
- 无独立证据的产品修复；原 m2 的锁/原生弹窗等另一路环境问题不因本 issue 的本地通过而关闭。
- 仅通过刷新证明服务重启持久化正确；该问题不是新增重启恢复验收。
- 暂存、提交、回滚、清理无关工作或自动删除隔离副本。
