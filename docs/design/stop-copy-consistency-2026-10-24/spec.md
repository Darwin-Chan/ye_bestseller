# 停止原因文案一致性：规格

Status: done

2026-10-24：用户已批准全部文案建议，并以“按建议”确认测试入口与三张工单拆分。按 01→02→03 实施。

## Problem Statement

采集与分析的停止提示有些只说状态，有些把命令行续跑建议混入 GUI 原因，部分把用户操作和运行停止混在一起。失败原因在不同页面和交换报告之间缺失；未知记录容易被误读为已知的意外中止。用户需要看到停止或失败的原因、数据是否保留和当前入口允许的下一步。

## Solution

实施已批准对照表的全部建议：保留已完成的超时原因与失败率超限修正，落实剩余 23 项。原因取自本次可靠记录，缺失显示“未记录”；事实原因与入口操作建议分开，最初停止原因与收尾失败原因分开。暂停、终态、处置目标、续跑及重试规则均沿用现状。

## User Stories

1. 作为采集操作者，我希望滑块和登录墙超时提示写明介入类型，以便知道为什么停止。
2. 作为采集操作者，我希望没有可靠原因时明确显示“未记录”，以便区分未知原因和已知故障。
3. 作为采集操作者，我希望跨天事实与最初停止原因分别显示，以便不误判停机原因。
4. 作为采集操作者，我希望失败率超限显示为中止并说明不可续跑，以便选择开始新轮。
5. 作为界面使用者，我希望暂停提示说明来自用户主动操作，以便离开操作上下文后仍能理解状态。
6. 作为界面使用者，我希望启动页、过程页、结果页对同一停止给出一致原因，以便不被互相冲突的提示误导。
7. 作为界面使用者，我希望继续受阻时同时看到暂停来源和受阻原因，以便知道下一步要处理什么。
8. 作为界面使用者，我希望继续启动失败后仍明确保留原轮暂停资格，以便知道能否重试。
9. 作为界面使用者，我希望单轮和多轮摘要都能说明用户主动暂停，以便逐轮处置。
10. 作为采集操作者，我希望停止进度保留原请求原因，以便区分暂停、中止和关闭窗口。
11. 作为采集操作者，我希望暂停、中止和关窗的日志反映实际请求类型，以便不会把中止误读成可继续的暂停。
12. 作为采集操作者，我希望停止原因与收尾失败原因分别显示，以便处理浏览器关闭或进程核验失败。
13. 作为采集操作者，我希望停止过程中更换进程或浏览器也不会改变原请求的来源和处置目标，以便提示与实际处置一致。
14. 作为命令行使用者，我希望非终态停止提示说明同日同范围重跑的续跑条件，以便保留现有命令行能力。
15. 作为 GUI 使用者，我希望共用异常只包含事实原因，以便不会看到命令行的续跑建议与 GUI 的中止要求冲突。
16. 作为采集操作者，我希望榜单和详情阶段未完成时保留未完成店铺清单，以便定位剩余工作。
17. 作为采集操作者，我希望即将跨天时明确下一次开始新轮，以便不把它理解为原轮继续。
18. 作为采集操作者，我希望中止按钮与确认标题使用同一术语，以便确认操作含义。
19. 作为分析操作者，我希望区分点击停止匹配与确认关窗停止，以便知道是谁触发了停止。
20. 作为分析操作者，我希望等待框、完成摘要和未完成任务说明展示同一停止原因，以便追踪本次运行。
21. 作为分析操作者，我希望因停止而未判断的商品对明确标为可重试的失败状态，以便不误以为模型已判断失败。
22. 作为分析操作者，我希望 SKU 未完成任务显示具体停止来源，以便不再看到“用户/运行”混合原因。
23. 作为分析操作者，我希望历史记录仍能识别和重试，且已完成判断与缓存保持保留，以便文案调整不增加重复判断。
24. 作为采集操作者，我希望启动失败显示本轮可靠失败详情，以便定位初始化问题。
25. 作为交换报告阅读者，我希望启动失败报告显示已有失败详情，以便理解当天数据缺口。
26. 作为交换报告阅读者，我希望旧数据终态不详时明确原因未记录，以便不把缺记录当作已知中止。
27. 作为维护者，我希望上述提示通过真实服务与页面验证，以便原因传递、续跑资格和重试行为一起得到验证。

## Implementation Decisions

- 使用既有领域词：用户主动暂停保留原轮的暂停资格；中止为结束本轮；单纯进程退出不授予 GUI 继续资格。失败率超限沿用既有终态。
- 覆盖对照表 C1–C4、D1–D8、E1–E5、F1–F4、G1–G2；A1–A4、B1 作为已完成行为保留并回归。静态、动态、单轮、多轮及重复确认标题均覆盖。
- 停止展示使用有来源的请求类型或本轮失败记录，不根据进程消失、未知终态或“stopped”状态反推用户操作。缺少记录一律“未记录”。
- 采集原因优先复用既有停止请求类型、轮次备注和本次执行事件。暂停、中止、关窗来源在请求发起时确定并跟随原停止目标，失败重试不覆盖。
- 采集进程识别停止请求时保留实际请求类型，避免暂停与中止共用异常后都输出暂停。该调整仅修正说明，不改变是否写终态、检查点和超时兜底。
- GUI 与命令行分别生成后续操作：GUI 沿用明确暂停资格与收尾闸门，命令行沿用同日同范围开放轮续跑规则。榜单及详情异常只留下阶段和店铺事实，入口补充操作建议。
- 分析停止来源作为本次运行的观测信息经既有服务读数传到等待框与结果；按钮停止和确认关窗分别记录，兼容未传来源的旧调用。原因只认实际记录，重复请求不得把已有来源改成另一来源。
- 商品对当前停止文案参与状态识别，增加原因说明时维持旧记录识别和可重试失败分类；优先把展示与稳定状态事实分开，不以新句子改变重试资格。SKU 沿用已有任务状态，只补原因。
- 分析进度与停止标志继续仅在本进程观测；不新增跨机运行进度或统一采集与分析停止机制。既有任务记录可携带可选说明，旧记录无来源时显示未记录。
- 启动失败和未知终态展示读取本轮可靠备注或对应事件；交换报告只使用本地已有可靠轮次记录。无记录不补猜测，不扩展交换包格式。
- 用户可见异常详情按文本渲染，避免异常内容被当成页面 HTML。
- 不增设停止原因输入框，不要求用户填写个人放弃理由；不改变浏览器归属与进程身份核验规则。

## Testing Decisions

用户已确认以下测试入口：

1. 采集：优先从 GUI 动作到开始/过程/结果取数及真实 HTML 横幅断言，使用真实临时数据库、可推进时钟和既有模拟进程/浏览器环境。命令行经现有轮次执行入口验证最终操作者输出。直接状态机测试仅用于原请求身份与收尾边界。
2. 分析：从真实分析服务发起运行、请求停止、读取进度和结果、执行重试；真实本地服务和页面使用可控假模型。验证按钮与关窗来源、旧状态兼容、重试只补未完成项，以及终态后无继续写入。
3. 交换：经现有缺口原因与报告生成入口构造带详情、无详情、旧终态及当天无记录等情况，验证最终报告文本和原有缺口判定。
4. 不为每条纯字符串替换写一个镜像测试。新增测试集中在原因传递、来源保持、缺失兜底、跨执行隔离、入口建议区分和重试兼容等外部行为。
5. 单文件定向测试随各票运行；类型检查沿用项目现有配置。三个实施切片结束后，仅跑一次分段全量，段集合与加载总数对账；在按仓库规范创建的隔离副本运行，证据写回主仓。
6. 完成后按 code-review 做 Standards 与 Spec 双轴审查，处理结论后提交到当前分支。委派遵守本仓最小上下文、任务文件、只读审查与干净工作区约束。

## Out of Scope

开放 GUI 异常停机后的续跑资格；修改失败率超限终态；变更暂停/中止/强制停止时机；调整浏览器归属规则；改变模型重试策略、缓存键、失败分类或计费行为；推断历史未知原因；新增跨机同步字段；采集与分析停止机制合并；构建或发布安装包；清理既有隔离副本。
