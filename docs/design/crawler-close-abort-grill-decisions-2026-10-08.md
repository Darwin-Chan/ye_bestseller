# 采集界面关闭确认与中止：需求澄清

- 日期：2026-10-08（Asia/Shanghai）
- 状态：需求与共同理解已最终确认；全部暂停相关状态先确认、确认后中止；待实现与验收。
- 来源：用户要求采集中关闭先确认，确认后效果同“中止本轮”；前两轮分别回复“全部按建议”，随后修订暂停完成后的关窗规则，并回复“Q9按建议”。
- 政策决策：`docs/adr/0048-crawler-close-confirms-abort-and-waits.md`（已接受，待实现与验收）。

## 原始需求

1. 当前采集正在进行时，点击窗口右上角关闭按钮，提示关闭将中止采集并请求确认。
2. 用户确认后中止采集，效果与“中止本轮（放弃）”按钮相同。

## 已确认决策（Q1–Q4）

1. 当前有采集进程，或本轮处于明确暂停状态（包括暂停停止中、进程已退出但暂停收尾中、暂停已完成）时，正常关窗均先弹确认。提示按真实状态区分采集中、暂停中与已暂停，不把已暂停误报为仍在采集。用户确认后，将对应轮次中止为人工放弃，已提交数据保留、本轮不可续跑；有未完成停止或收尾则等待完成后关闭。已完成且无待完成收尾时仍直接关闭，保留真实终态。
2. 确认后显示“正在中止采集，请稍候…”；停止与既有收尾完成后自动关闭。等待期间界面保持响应，不允许开始或续跑；重复关窗不重复弹框或发起中止。
3. 覆盖本机当前识别的采集进程，包括本界面启动、命令行启动、先前界面留下的采集；与现有中止入口的目标范围一致。
4. 所有正常关窗入口统一处理，包括右上角 ×、Alt+F4、任务栏菜单关闭。任务管理器强制结束、断电等不属于可保证范围。
5. 中止沿用现有领域含义：轮次收尾为人工放弃、不可续跑；已提交数据保留；先协作停止，超时再走原停止目标保护下的强制停止。不是暂停，也不是立即杀进程。
6. 用户取消或关闭确认框时，窗口保留，不因这次关窗中止本轮或改变原状态：采集中继续采集，已暂停仍保持暂停，暂停收尾中继续原暂停收尾；不自动恢复采集。

## 已确认边界（Q5–Q8）

### Q5：中止失败

目标暂不可确认、数据库写入失败或强制停止失败等异常时，保留窗口，显示原因，允许重试；不静默退出，不绕过进程身份保护。既有停止核验与收尾继续驱动。若已写入人工放弃终态，不回滚成可续跑状态；提示中止不能撤销，不能把停止失败描述为暂停成功。

### Q6：确认期间状态变化

确认仅授权弹框时的采集目标或明确暂停的轮次。原采集自然完成时保留其真实终态，不改成人工放弃；无新目标、无待完成收尾时直接关闭。原目标被替换时不沿用旧确认处置新目标，保留窗口，提示采集状态变化并要求重新确认。确认后等待至自动关闭的阶段同样不得扩张旧授权。

### Q7：暂停或中止正在收尾

- 暂停中、采集进程仍在：仍弹关窗确认；确认后由暂停升级为中止，本轮不可续跑。
- 已在中止中：不重复确认、不重新发起中止，等待现有收尾完成后自动关闭。
- 采集进程已退出、暂停收尾尚未完成：先弹关窗确认；用户确认后才升级为中止，将该轮次写为人工放弃，继续驱动原收尾，等收尾完成后自动关闭。不另起停止任务，不扩大目标或浏览器处置范围。用户取消则不升级，原暂停收尾继续。

### Q8：确认框安全默认值

文案必须明确已采数据保留、本轮不可续跑，默认选中取消。取消或关闭确认框都不触发中止；无法显示确认框时保留主窗口，不自动确认。按钮清楚表达“中止并关闭”和“取消”；若采用系统按钮标签，应补足其动作解释。

采集中建议确认文案：

> 采集正在进行中。
>
> 关闭程序将中止本轮采集，效果与“中止本轮（放弃）”相同。已采集的数据将保留，本轮不可续跑。
>
> 是否确认中止并关闭？

暂停相关确认框同样说明人工放弃的后果，但首句按真实状态显示“本轮正在暂停，采集进程正在停止”“本轮正在完成暂停收尾”或“本轮已暂停”，不写成“采集正在进行中”。共同正文为：“关闭程序将中止本轮采集，效果与‘中止本轮（放弃）’相同。已采集的数据将保留，本轮不可续跑。是否确认中止并关闭？”

## 行为与验收矩阵（待实现验证）

| 场景 | 预期行为 |
| --- | --- |
| 有采集，点 × / Alt+F4 / 任务栏关闭 | 先确认；窗口不能提前消失 |
| 确认框取消、关闭或无法显示 | 主窗口保留，不请求中止、不升级暂停、不自动恢复采集；已有暂停收尾不受影响 |
| 用户确认 | 先写人工放弃并复用现有停止链路，显示等待，完成后自动关闭 |
| 协作停止超时 | 继续驱动既有身份保护下的强制停止，不因关窗丢失兜底 |
| 重复点关闭 | 不叠确认框、不重复中止任务 |
| 停止核验与收尾期间开始/续跑 | 拒绝，不启动新采集 |
| 当前进程来自命令行或前次界面 | 正常确认后对该目标使用同一中止语义 |
| 已暂停、无采集、无待完成收尾 | 先弹确认；确认后将该暂停轮次写为人工放弃，成功后关闭；取消则保留暂停与续跑机会 |
| 已完成、无采集、无待完成收尾 | 直接关闭，保留真实终态 |
| 弹框期间原采集自然结束 | 不改写终态，核对无新目标及待完成收尾后关闭 |
| 弹框或等待期间目标被替换 | 不伤害新目标；保留窗口并重新确认 |
| 暂停正在停止，采集仍在 | 关窗确认后升级为中止 |
| 已在中止收尾 | 不重复确认或重启中止；完成后关闭 |
| 进程已退出但暂停收尾未完成 | 先弹确认；确认后升级为人工放弃，继续原收尾，完成后关闭；取消则维持原暂停收尾 |
| 目标不可确认、写库失败、强制停止失败 | 保留窗口、提示原因、允许重试，不绕过安全检查 |
| 已写人工放弃后停止失败 | 不回滚终态，不误报可续跑或停止成功 |
| 浏览器归属不属于原目标 | 不擅自关闭，不扩大中止按钮的既有处置范围 |

以上为需求验收标准，不表示已执行测试或已通过。

## 现有实现事实与政策冲突

- `gui.py` 的 closing 当前调用 `_warn_crawler_keeps_running`，告知后台继续采集后放行关窗。
- `Api.abort_run` 先写人工放弃终态，再通过 StopWatch 停止目标；可返回目标暂不可确认的可重试错误。现有入口仍需按本需求补足关窗授权的竞态保护，不能假定直接调用即满足全部边界。
- 现有停止核验和超时兜底由查询中的 tick 驱动，不能仅发送一次请求就退出 GUI，声称停止链路已完成。
- ADR-0008 与 CONTEXT 的关窗继续政策，以及 ADR-0009 结果段的同类描述，与新需求冲突；ADR-0048 仅拟替代关窗政策，不替代双锁、终态不可覆盖或停止目标归属规则。
- ADR-0024 / ADR-0028 的冻结目标、核验与浏览器归属保护保持不变。
- 既有浏览器收尾重试有上限并可能记录放弃收尾；同中止按钮不等于保证关闭所有浏览器，不在此扩大收尾机制。
- 分析程序已有独立政策（ADR-0043），交换程序也不属于本需求。

## 已确认修订（含 Q9）

用户明确修改：已暂停、无采集进程且无待完成收尾时，不再保留可续跑状态；关闭窗口升级为中止。此规则替代第一轮 Q1 的暂停完成后关窗规则。

- 没有进程可停不代表无需中止：本分支的核心是正确给该暂停轮次写入人工放弃终态，然后关闭。
- 若写入失败，沿用 Q5 保留窗口、说明原因并允许重试，不先关闭或假报中止成功。
- 只处理明确的暂停轮次，不把任何无进程、无终态的轮次都推断为暂停；已完成轮次不改写终态。
- 当前 `abort_run` 在本界面未记住轮次且无当前身份时会提前返回成功；实现不能用该成功返回代替本需求要求的终态确认。此为静态代码事实，不是本轮新复现或修复。
- Q9 已确认并经用户澄清：采集进程已退出但暂停收尾尚未完成时点关闭，先弹确认，确认后才升级为中止；先写人工放弃并继续驱动原收尾，等收尾完成后关闭，不另起停止任务、不扩大浏览器处置范围。该规则替代 Q7 原来的“等收尾但不升级”决定；用户澄清同时纠正助手此前“不弹确认”的误解。
