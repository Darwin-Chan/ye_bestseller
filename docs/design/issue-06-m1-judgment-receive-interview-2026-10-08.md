## 第三轮确认（2026-10-08）

用户确认：采用方案 B。当前机器 m4 作为 Gitee API 来源维护点，维护 API token；由 m4 查询实际存在的 `judged-*` 远端库，并把来源清单发布到共享配置通道。其他机器不各自维护 Gitee API token，而是读取共享来源清单；接收机仍可在收取时自动创建缺少的本地克隆。

## 第四至第八轮确认汇总（2026-10-09）

用户确认以下建议全部采用：

### 来源清单刷新与来源范围

- m4 仅在实际交换任务启动时刷新来源清单；打开交换台窗口或启动分析不刷新。
- m4 是 Gitee API token 的唯一维护点；其他机器只读取共享 `plan/judged-sources.json`，不各自维护 token，也不直接扫描 Gitee。
- 仅纳入可信 owner 下、名称严格匹配 `judged-<machine_id>` 且 machine_id 符合正式机器编号规则的私有库；空库也属于应接入来源；测试、演示和旧库不自动纳入。
- API 分页必须完整；来源减少或远端地址变化时先报告、保留上一版有效清单并等待维护人确认；无变化不制造提交。
- plan 拉取失败时可用最近一次有效清单处理已有且匹配的本地来源，但不能从过期清单发现和创建新来源；清单移除不触发本地 clone 自动删除。

### 接收机 clone 与失败边界

- 本地目标固定为配置的 `exchange_root\\judged-<machine_id>`；清单不能指定任意本地路径；拒绝路径穿越和越界路径。
- 目标不存在时自动 clone；已有正确仓库时只允许快进更新。
- 脏工作区、远端不匹配、仓库损坏或 clone/pull 失败时，按来源阻断；不自动 merge、reset、删除重建、修改 origin、配置 SSH 或等待密码。
- 失败按来源隔离；其他来源继续处理；整趟明确为部分失败。没有任何可用来源时报告“接收通道未就绪”，不能报告为“没有新判断集”。
- 空远端库报告为“来源已接入但当前没有判断集包”，不视为故障。

### 门禁、冲突与审计

- 包格式不支持、包内容摘要或证据摘要校验失败时拒绝包并记录原因。
- 证据版本或模型署名不匹配时允许为追溯保留接收/导入记录，但标为不可采用，不能静默驱动当前分析。
- 人工决定冲突保留双方和来源，写入冲突账，不自动裁决；冲突项不进入当前分析，其他无冲突数据可继续。
- 明确区分 source connected、package discovered/received、imported、gated/gated_out、conflicted、adopted；导入数量不等于当前采用数量。
- 日志与导入账记录清单版本、来源、远端 URL、提交 SHA、包 digest、发现/接收/导入/门禁/冲突/采用数量及失败原因；不得记录 token、私钥、Cookie、密码或完整敏感远端信息。

### 真实 m1 验收

- 由人工核实 m1 当前运行根、exchange_root、machine_id、配置文件和配置键；不能沿用历史包中的路径。
- 人工在 m4 完成来源清单刷新和发布，在 m1 验证自动 clone、pull、包发现、导入账和第二次幂等收取。
- 现场使用受控最小验收包或隔离验收库，不要求开发 agent 写入真实业务数据库。
- 隔离副本验证版本/摘要/模型门禁和冲突分支；真实 m1 验收证明部署、权限、clone/pull、收取、导入、幂等和审计链路。
- 只有真实 m1 证据齐全，issue 06 才能从未处理改为已处理。
