## 第一轮已确认决策

用户回答原文：『Q1还是由测试直接调用后台代办，Q2按推荐』。

### D1：完整业务测试保留后台代办

- 不采纳把完整场景的并组、确认、保存全部改为 UI 点击的建议。
- 完整业务场景保留测试直接调用后台代办人工操作的方式。
- 页面仍负责真实进入分析、读取状态、结果页呈现与重新选择更长日期区间。
- 库存数据和模型响应保持测试夹具，不使用真实生产数据、账号或外部远端。
- 此决定不取消用户最初要求的正常 UI 操作路径对照，但该对照不替代完整场景，也不要求完整场景全部走 UI。

### D2：后台保存后主动刷新，作为预定义同步步骤

- 保存完成后，由测试主动 reload 同一分析页面，重新读取并应用快照；不依赖页面自动更新。
- reload 是预先定义、执行一次的流程步骤，不是失败后反复刷新的重试手段。
- 专门的时序回归先固定页面已读到旧快照，再通过本地公共 API 完成修改与保存；之后刷新、验证新快照及结果页。
- 完整场景同样在后台保存完成后刷新，不再拿旧 DOM 继续操作或断言。
- 不因此给产品增加自动轮询、推送或跨页面同步功能。

## 第二轮已确认决策

用户对 Q3（三层核对）与 Q4（测试辅助函数）回答：『按推荐』。

### D3：保存、读取、页面呈现三层核对

1. 后台保存调用成功返回；返回快照中的分析 ID、分组成员、确认状态符合预期，dirty=false 且有 saved_at。
2. 保存成功后主动刷新同一分析，捕获本次刷新产生的快照 GET；核对分析 ID、日期区间、分组成员、确认状态及保存标记，与保存返回值一致。
3. 验证页面实际呈现：不止看响应成功或“畅销品”标题，还检查结果中的分组与销量；返回确认页后核对已确认组名单，保留原有业务断言。

证据是“保存先完成、刷新后读取”的确定顺序与业务内容一致，不是单独等待 dirty=false、saved_at 或标题可见。不新增产品 revision，不把秒级 saved_at 当唯一版本号。

失败信息按阶段区分后台保存不成立、刷新读取不成立、页面呈现或结果页转换不成立。具体断言和诊断内容在 spec 中细化，不用泛化的标题超时报错掩盖差异。

### D4：有限复用的测试辅助函数

- 完整业务场景与专门的旧快照回归共用“刷新并核对保存后状态”的辅助函数，只放在测试侧。
- 辅助函数不代办并组或保存，不内置反复刷新，不扩展成全仓测试框架。
- 产品 API、数据库和页面逻辑不因该辅助函数而修改。
- 新区间按新分析完成条件核对，不要求新分析携带旧分析的保存时间；新分析就绪与旧分析保存后同步不是同一个判定。
