### 1. 一个固定上下文的准备持有者

拟新增 `bestseller_monitor/preparation.py`，以 `Preparation` 持有准备知识；名称是本轮建议，尚非已实施事实。
一个实例固定绑定一份配置和调用方提供的连接能力，并接收业务日期时刻来源与准备专用运行 adapter。
它调用既有 plan_step 的准备/扫描业务，不导入 connect 自行按数据库路径开库，不创建独立数据库权力。
调用方的连接能力必须稳定对应约定上下文；无法也不尝试检查任意闭包内部是否偷偷换库。

不建“配置指纹 → owner”缓存或通用 context registry：当前真实路径只有固定正式上下文与试采切换。
Api 保存正式 owner；进入试采选择绑定试采配置的 bypass owner；回到原正式配置时恢复同一正式 owner。
新的正式配置/机器/数据库能力对应新的 owner（现有生产路径通常即新 Api）；不新增热重载入口。
切模式时保留现有路径校验、进程归属和停止守卫；准备运行中（含超预算）仍不能切。

### 2. 状态与结局分开

不可变 `PreparationSnapshot` 对外解释为以下五种状态；底层运行事实与时钟判断只在 owner 中维护：

| 状态 | 准备还在运行 | 确认预算内 | 当前准备结局 |
| --- | --- | --- | --- |
| 未开始 | 否 | 否 | 无 |
| 运行中、预算内 | 是 | 是 | 无 |
| 运行中、预算耗尽 | 是 | 否 | 无；不是结束或取消 |
| 已落定 | 否 | 否 | PrepResult 或明确的异常失败 |
| 试采绕过 | 否 | 否 | 无正式结局，也不启动正式准备 |

快照提供 phase、派生的 running/confirming、当前 result、失败类别和上一份可用作历史的 result。
“有 result”不等于“可以开轮”：READY/READY_FROM_CACHE/REFUSED/汇总跳过仍沿用计划业务解释；
没有本周本地计划仍守闸门。发生异常时已落定但没有本次 PrepResult，不能回填旧 READY。

只保留解释当前尝试所需的一份旧 result，不建设完整历史日志。新尝试开始时当前 result 清空；
前一份 result 保留为历史。失败重试不会抹掉那份历史，也不会把它变成本次成功。

快照中“预算内/耗尽”每次按同一单调截止点推导，不依赖一个定时器去改状态。
30 秒整即耗尽；超预算的 worker 最终完成后快照成为已落定，并可消费它真实产生的新 result。
若等待者取锁时结果已经落定，返回真实落定状态，不人为保留一个过期的“仍在超时”状态。

### 3. 公开 interface：接纳一次，再区分两种等待

| 拟定入口 | 调用者需要知道的契约 |
| --- | --- |
| `request()` | 原子接纳一次准备并安排后台执行；返回明确的接纳决定和不透明运行凭据。未落定时拒绝，不排队、不重置截止点。试采直接返回绕过；执行 adapter 启动失败返回明确失败。 |
| `wait_for_open(run)` | 只等指定运行落定或用尽该运行剩余预算，返回它的快照；不含缺口扫描，不接受调用方另给一份 30 秒。 |
| `wait_for_finish(run)` | 为现有同步 prepare 兼容：等指定后台工作连同后置扫描结束，返回该次 result 或 None；不用于开窗，不限制为 30 秒，不重新安排任务。 |
| `snapshot()` | 一次读取当前运行的不可变事实；views 和闸门不分别调用时钟、判断旧结果或拼四个字段。 |

拒绝决定可以携带已在运行的凭据，方便明确选择“等已有那次”；这不等于请求被接纳，更不触发隐式重跑。
陌生 owner 的运行凭据被拒绝，不自动退化成等待当前那次。

保留两种等待是因为现有同步 `Api.prepare()` 返回前还会完成扫描，而 main 只应等落定。
不为了少一个方法偷偷改变同步调用语义，也不把事件或线程对象交给 main 操作。
所有实际执行都由 owner 安排；同步 prepare 也经 request + wait_for_finish，避免另一条入口再实现接纳。

### 4. 为什么需要运行身份，但不需要通用任务框架

采用仅在进程内有效的不透明运行凭据，每次被接纳的运行各有自己的落定/完成信号及结果。
不是 UUID 注册表、可取消任务系统或跨进程作业模型。

必要场景：A 已落定、扫描仍在跑，B 已被接纳；此时 A 的旧等待者、迟到扫描或后台结束都必须仍属于 A。
`wait_for_open(A)` 不得误等 B 的预算，`wait_for_finish(A)` 不得返回 B 的结果。
旧扫描只使用 A 冻结的 cfg/连接能力/week，不能给当前 B 写快照。新运行仅在 A 已落定后接纳，
所以不主动支持两个未落定的准备并发；无需以取消/抢占旧运行作为正常控制流。

状态发布与落定信号在同一同步保护下完成；等待时不持有状态锁，唤醒后重读指定运行并重算剩余预算。
每次运行的信号独立，不复用旧的已置位 Event。普通异常和派发失败也发布终态并唤醒；
worker 的 finally 保证结束信号有出处。不可捕获的进程终止不承诺在进程内唤醒。
对于 BaseException 这类终止信号，先做可执行的落定/唤醒清理，再保留传播语义，不伪装为成功。
落定后的扫描异常、告警异常只记收尾失败，不撤销 result，不修改后续运行；不自动重试。

### 5. Api/main/views/plan_step 的最小接线

- Api 在既有模式切换同步区内选定 owner 并完成 request 的接纳，随后释放 Api 锁再等待。
  后台工作不回读可变的 Api.cfg/_open_conn，不占用整段 Api 锁，避免阻塞页面取数和停止控制。
- `Api.prepare()` 保留同步 PrepResult/None 形状；重复准备明确拒绝、记录理由并返回 None，不等待或重跑。
  `retry_prepare()` 保留现有 ok/error JSON；仅接纳成功返回 ok，重复或派发失败返回 error。
- main 改用 Api 的公开开窗准备入口，由它 request 并调用 wait_for_open；不直接起准备线程、碰私有 Event
  或另起一个预算。若已有运行，这个“开窗等待”入口只明确等待已有那次，不重复接纳。
- UiState 用一份 PreparationSnapshot 取代 prep/plan_confirming/plan_waiting 三份分散事实。
  页面 JSON 的 plan_confirming/plan_waiting/plan_gate/plan_locked/plan_retry 键保留；不改前端重画机制。
  confirming_now/prepare_running 如需保留为现有 Python interface，只转读快照，不保留计时实现。
- start_run 在读取一致快照后优先执行已确认的预算内拒绝，再沿用角色/本地计划/已有轮次等既有规则；
  不修改过程页 resume_run 的停止与续跑模型。
- plan_step 保留本地计划、stale、拒绝理由与跨周规则。它只从快照的当前 result 判定本次确认；
  历史 result 仅允许提供“窗口原先确认哪一周”的提示。可给 start_plan 增加可选的历史输入，
  使 API/views 都只转交事实、不各自选择旧结局；原有调用者默认无历史输入，行为保持。
  不通过假造 PrepResult 来保留跨周提示，也不把旧 READY 当作当前 READY。

### 6. 准备专用的测试 seam

沿用现有 `Api(cfg, now, open_conn, ...)`，增加单个可选的准备运行 adapter 注入口。
这个 adapter 只替换三件环境能力：单调读时、安排一次后台执行、按秒等待给定通知。
生产 adapter 使用 time.monotonic / daemon Thread / Event.wait；可控测试 adapter 能推进同一时钟、
延后派发并在模拟等待时推进或唤醒。接纳/预算/结果规则不下放给 adapter。
它只服务这个 module，不创建通用线程框架、通用时钟库、调度队列或取消机制。
