# 1688 账号密码自动登录调研

研究日期：2026-09-18。范围：用户授权使用自己的账号，在本机现有库存采集程序中完成网页登录。本文是研究与接入建议，未实现功能、未提交真实凭据、未验证真实账号的登录成功率。

## 结论

建议采用 **现有 Edge 专用用户目录 + Playwright/CDP + 自动填写密码登录表单 + 必要时人工验证 + 登录状态复用**。

自动填写账号、密码和点击登录有现成浏览器自动化能力；但“提供账号密码”不能作为“一定全程无人值守”的承诺。只有登录页提供密码入口、凭据有效且本次未要求额外验证时，才可能自动完成整个流程。具体账号的验证码触发率与登录状态有效期需要实测，不能从文档推算。

本项目已经拥有浏览器接管与状态复用基础，无需先重写浏览器驱动。下面把已核实事实、工程建议与待实测项分别标明。

## 方案比较

| 方案 | 对当前需求的作用 | 结论与证据边界 |
|---|---|---|
| 在真实浏览器中填账号密码 | 直接操作网站现有登录表单 | 推荐验证；Playwright 支持填表与点击，但其能力不保证 1688 服务端接受本次登录。[P1][P3] |
| 复用已登录的专用浏览器目录 | 下次启动优先沿用登录状态 | 推荐与上一项组合；项目已经这样工作。状态失效后仍需重新登录。[L1][L2] |
| 手动扫码后复用目录 | 避免程序保存账号密码 | 保留为降级入口；项目现有登录脚本已经提供这一流程。[L1] |
| HTTP 直接提交账号密码 | 绕开页面直接实现登录协议 | 本次未确认公开、稳定的 1688 网页密码登录 API，不建议作为首个实现；不能把浏览器内部请求当成官方支持接口。 |
| 开放平台授权与 API | 如果业务接口覆盖需求，可用 API 获取数据 | 需单独核实应用资格、授权范围、目标店铺及 SKU 库存接口；不能直接假定授权 token 等于网页会话。官方资料核查见后文。 |

## 1688 官方页面核查

2026-09-18 对 [1688 官方登录入口](https://login.1688.com/member/signin.htm) 发起不带账号凭据的只读 HTTP 请求，跟随服务端跳转后返回 HTTP 200。最终域名为 `https://login.taobao.com`，查询参数含 `from=1688web`。页面 HTML 中提取到以下公开配置：[S1]

```json
{
  "defaultView": "password",
  "extraView": "qrcode",
  "machineVerifyType": "nocaptcha",
  "login_types": ["password", "qrcode"]
}
```

这是服务端 HTML 配置证据，证明本次响应配置了密码与扫码入口、机器验证能力；**不是浏览器渲染及真实提交成功的证据**。`nocaptcha` 这个内部名称不能解读为“不需要验证码”。是否触发滑块、短信或其他确认，需要以目标账号实际页面为准。

此重定向也说明不能把 `login.taobao.com` 一概当作错误入口；应从已核实的 1688 官方入口跟随合法跳转，再验证目的页面及 frame 来源。不能把这项观察扩展成信任任意淘宝链接。

[1688 开放平台首页](https://open.1688.com/) 同样可通过只读 HTTP 请求取得，页面包含商品、会员、交易等 API 文档分类链接。[S2] 但本次未取得可核实的 OAuth 说明正文，不能确认当前授权参数、token 有效期、开发者准入和库存接口权限；也没有证据表明 API token 能换取当前网页的登录 Cookie。API 路线因此只列为待核实替代方案，不提供未经验证的接口调用代码。

访问限制：研究工具直接打开上述页面失败，本机受限网络请求也被套接字权限阻止；获准的只读请求随后取得登录页及开放平台首页。前两类失败是访问工具限制，不能解释为 1688 故障或账号被拦截。没有提交登录、读取用户现有 Cookie 或操作已登录浏览器。

## 已核实的工具能力

- Playwright 官方认证文档演示了填写用户名、密码并提交登录，以及复用认证状态；同时说明状态文件可能包含足以冒用账号的敏感内容，不应提交到仓库。[P1]
- `connect_over_cdp()` 可以连接已有 Chromium 浏览器并访问默认 context；官方提示这种连接的功能完整度低于 Playwright 自有协议，不应推导出它可以避免网站识别自动化。[P2]
- Playwright 可定位 iframe 内的表单，`fill()` 可填写文本框。1688 的实际 frame、输入框和按钮定位需要在当前页面核验，本文不提供未经验证的固定选择器。[P3][P4]
- Microsoft 官方支持以远程调试端口连接 Edge，也支持通过单独的用户数据目录启动独立实例。这证明接管方式有官方技术基础，不证明网站会无条件放行。[P5]

## 仓库现状与接入位置

本节依据本仓库源码，不把历史项目说明当作当前 1688 规则。

1. `login_chrome.py` 使用配置中的 `user_data_path` 启动 Edge，打开 1688 首页，提示用户手动登录后关闭窗口；目前没有密码自动填写或成功确认。[L1]
2. `browser_pw.open_session()` 以普通进程启动 Edge，经本地调试端口连接，复用 `br.contexts[0]` 并创建页面；`close_session()` 管理资源收尾。应复用这对接口，不另写一套进程管理。[L2]
3. `config/config.toml` 已使用仓库外的专用 Edge 用户目录，驱动为 `pw_cdp`；当前没有账号密码配置。[L3]
4. `guard.py` 已有登录墙、滑块及 deny 判断和人工等待。但 `resolved()` 主要检查 URL 与验证容器消失，不能证明已经登录到指定账号；`wait_for_resolution()` 还会先刷新一次页面。[L4]

**接入建议：**新增独立的登录流程模块，在需要认证时调用；`open_session()` 继续只负责浏览器生命周期。登录模块统一回答“已登录到目标账号 / 需要人工 / 凭据失败 / 页面不支持或超时”，避免采集层各自猜测。

登录中的短信、扫码或滑块验证应等待当前挑战完成，避免直接套用现有刷新逻辑而使挑战失效。现有 guard 可复用事件通知、暂停检查和等待节拍，但需要单独的登录成功判据。

## 推荐流程（设计建议，尚未实现）

```text
打开或接管专用浏览器
  → 检查当前登录身份
      → 已是目标账号：验证目标页面可用后继续采集
      → 已是其他账号：提示账号不匹配，停止自动操作
      → 未登录：从官方入口打开登录页
          → 检查页面/iframe 来源及密码登录入口
          → 填账号密码，只提交一次
              → 登录成功：确认身份，回到目标页验证可用性
              → 需要验证：等待用户处理，完成后重新确认身份
              → 密码错误/账号受限：停止并提示
              → 未知页面/超时：停止并保留可诊断状态
```

关键约束：

- 先检查已有登录状态，避免每次启动都重新提交密码。不能仅凭 Cookie 存在、HTTP 200、跳离登录 URL 或页面出现商品就认定已登录。
- 登录成功至少需要可信的当前账号身份信号；目标榜单或详情页面可用性作为独立业务检查。账号昵称如何映射到用户输入的手机号/会员名仍需实测。
- 登录后仍可能遇到采集限制；登录成功与库存读取成功分别记录。
- 验证等待期间响应项目现有停止请求；超时不无限重复提交，不自动退出或切换其他已登录账号。
- 凭据只填写到核实过的 HTTPS 登录页面及 frame。官方跨域跳转应逐个核实来源，不用字符串包含 `1688` 作为信任依据。

## 凭据与状态保存（设计建议）

首次验证可由本机密码输入框或终端隐藏输入接收密码，仅用于本次登录。若需要重启后自动补登录，可增加“记住密码”，使用 Windows 用户范围 DPAPI 加密保存，避免明文写入 TOML、数据库、命令行参数或日志。Microsoft 文档说明 DPAPI 默认通常绑定加密用户与计算机；它不是对同一用户下恶意进程的隔离保证。[P6]

优先复用现有专用 profile；不为实现自动登录而导出一份额外 Cookie 文件。不记录登录请求体、密码、完整 Cookie 或带凭证的跳转 URL；登录阶段的 trace、HAR、截图与页面转储需单独控制。保存的认证状态同样属于敏感数据。[P1]

## 最小验证计划

以下是后续原型的验收项，本次没有执行真实登录：

| 场景 | 期望行为 |
|---|---|
| 专用目录已经登录目标账号 | 不输入密码、不重复登录，直接检查目标页 |
| 未登录且密码登录入口存在 | 自动切换入口、填表、提交；记录是否需要人工 |
| 出现短信、滑块或手机确认 | 显示准确状态，等待人工，处理后继续 |
| 密码错误或账号受限 | 停止自动提交，不循环重试 |
| 已登录其他账号 | 提示不匹配，不自动操作该账号 |
| 登录状态失效 | 进入一次受控补登录流程 |
| 页面改版、iframe 尚未加载或网络失败 | 报告具体失败，不能误报密码错误或登录成功 |
| 人工验证过程中点击暂停 | 及时响应，按现有会话归属规则收尾 |
| 关闭再启动浏览器 | 检查登录状态是否可复用；隔日继续观察 |

原型应记录总登录尝试数、无人工成功次数、人工验证次数、失败原因和耗时；少量成功样本只能证明可行，不能承诺长期无人值守。不要通过反复登出登录制造大量试验。
